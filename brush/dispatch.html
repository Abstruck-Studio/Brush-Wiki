派发层与事件

派发层把「薄注入」与「mod 能用的语义事件」连起来：vanilla 方法体内只有一条 Dispatcher.fire(...)，所有决策逻辑落在我们自己的派发表里。页面覆盖 fire 的重载形态、L1 钩子与 L2 语义事件的分层、监听器的注册 / 注销与线程语义、事件载荷的类型化契约、派发表的调试能力，以及一条事件从 vanilla 到 mod 监听器的完整链路。

上游见 注入层；每个方法只准有一个注入点、一条指令的理由见 最小改动原则与禁止清单。

调用形态与重载

派发器是 org.abstruck.brush.transform.Dispatcher，全静态、普通 Java 代码。fire 目前有 5 个重载，参数个数决定是否要建参数数组：

重载参数数组典型用途
fire(HookEvent)共享常量空数组 NO_ARGS，不分配热路径首选 —— client.tick / client.run / 各注册窗口
fire(HookEvent, Object)有监听器时才 new Object[]{arg}crash.report.details
fire(HookEvent, Object, Object)同上hud.extract、input.key.press、network.payload
fire(HookEvent, Object, Object, Object)同上network.server.payload（Reply / Identifier / byte[]）
fire(HookEvent, Object, Object, Object, Object)同上creative.tab.output

三参重载是 2026-10-15 才补上的：此前只有 0 / 1 / 2 / 4 参，而 network.server.payload 改成 (Reply, id, data) 后恰为 3 参（Dispatcher javadoc）。

热路径的零开销短路

fire 的第一动作是 TABLE.get(event.id()) 加空判断：事件无人注册时直接返回 —— 零分配、不进循环、不建数组。这是「每帧 tick 上注入一条指令」可安全成立的量化依据。对照被否方案：若走「每次调用都构造事件对象」，每帧都会产生分配压力；我们的事件 id 是常量（HookEvent），无此成本。监听器全部注销后，该事件键会从表中移除，回到最短路径。

注册、注销与开关

// 注册（order 升序；同 order 按注册先后）
Dispatcher.Registration reg = Dispatcher.register(HookEvents.CLIENT_TICK, listener);
Dispatcher.Registration reg2 = Dispatcher.register(HookEvents.CLIENT_TICK, 100, listener);

// 开关（只跳过自身，不阻断他人）/ 注销（幂等；也可 try-with-resources）
reg.setEnabled(false);
reg.isEnabled();
reg.unregister();
try (var r = Dispatcher.register(HookEvents.CLIENT_TICK, listener)) { /* ... */ }
  • 表结构：ConcurrentHashMap<String, CopyOnWriteArrayList<Registration>>，按 (order, 注册序号) 升序插入；Registration 自带 volatile 开关位与注销位。
  • 可链式：同一事件可注册任意多监听器，彼此独立；不提供任何独占语义。注册 / 注销 / 开关可在任意线程。
  • 异常不吞：监听器抛出的异常被包一层带事件 id / order / seq 的 IllegalStateException 立即上抛 —— 快速失败，绝不让 hook 错误静默消失。

L1 hook 与 L2 语义事件的分层

两层共用同一张派发表；L2 只是类型化包装，不是第二套引擎。

vanilla 方法体
  └─ [唯一的 1 条注入指令] Dispatcher.fire(HookEvents.X, 原始参数...)
        │
        ▼
  派发表（Dispatcher，普通 Java 代码）
        ├─ L1 监听器：CoreHooks 的计数 / 证据日志 / 内部机制
        └─ L2 桥接监听器（每事件 1 条）──► mod 的类型化监听器（api.BrushEvents）
L1
HookEvents 里的常量，类型为 HookEvent（record HookEvent(String id)）。id 是 L1 内部标识，可随版本调整；常量收敛在 HookEvents 一处，拼错在编译期即失败。派发表内部仍以 id 字符串为键，键值与类型化之前逐字节一致，台账 / 日志 / 自检报告按它核对。
L2
org.abstruck.brush.api.BrushEvents 的 Event<XxxListener> 常量。每个 Event 持有「承载它的 L1 id」+ 一个桥接函数。Event 的构造器是包私有的：对 mod 而言事件是封闭集合，mod 看不到派发表内部结构。
分层的意义
vanilla 一改参数，改的是 L1 那几行适配代码与桥接 lambda；L2 的签名与语义不动，mod 不用动 —— 这是加载器自身「原始钩子层 / 语义层」的实现约定。
注册入口
mod 只经 Event.register(listener)，返回 EventRegistration。注册动作只触碰 Dispatcher，不解析任何 MC 类型 —— api 包的 MC 类型引用一律是惰性的，因此 mod 入口类构造期即可安全注册。

事件载荷的类型化契约

L1 的 Object[] args 是弱类型走廊，因此每个事件都用常量 javadoc 逐位钉死载荷，桥接处做唯一一次强转。几条当前契约：

事件载荷（按 args 下标）
input.key.press[0] KeyEvent record（key / scancode / modifiers）、[1] Integer GLFW action；不携带窗口句柄
input.mouse.button[0] MouseButtonInfo record、[1] Integer GLFW action（0=RELEASE / 1=PRESS）
input.mouse.scroll[0] Double xOffset、[1] Double yOffset
network.payload[0] Identifier、[1] byte[]—— 2026-10-15 由「单个 BrushPayload」改成 (Identifier, byte[])：核心 L2 桥从此不再持有具体载荷类型，为网络引擎整体搬进库模组铺路
network.server.payload[0] ServerPayloadEvent.Reply、[1] Identifier、[2] byte[] —— mod 侧因此看不到任何 vanilla 网络类型
creative.tab.output[0] ResourceKey<CreativeModeTab>、[1] ItemDisplayParameters、[2] Collection<ItemStack>、[3] Set<ItemStack>
crash.report.details[0] StringBuilder—— handler 只许追加，不得清空 / 重排
data.reload[0] MinecraftServer、[1] Optional<Throwable>

不派发事件的注入点也存在：CustomPacketPayload$1#findCodec 的 RETURN 包装只换 codec，目的 token 记为 network.channel-codec，同 creative.tab.phantom-suppress 的非事件先例。

线程语义

总原则：派发在触发线程上同步执行。注册 / 注销 / 开关可在任意线程；派发路径无锁。需要区分的是「异线程」事件：

事件触发线程 / 时机
client.run / client.tick / screen.init / screen.resize / hud.extract / input.*游戏主线程
registries.bootstrap / client.registration执行 bootstrap 的线程；因运行时而异 —— S1 = main，S2 = 被推迟到 Minecraft 构造期，S3 = FML 在其 bootstrap 内完成
bootstrap.earlyS1 = main；S2 = main；S3 = 宿主 bootstrap 内的工作线程
packs.registered构造资源包仓库的线程
data.loaded构造该服务器的线程
data.reload异步 —— 重载 future 的完成线程；监听器不得触碰屏幕 / 渲染 / 未同步的游戏状态。派发位于 whenComplete 回调：该上下文重抛会被 CompletableFuture 静默吞掉，因此引擎在回调体内 catch + ERROR，这是本工程唯一一处有意偏离「异常立即上抛」的点
client.stoppingJVM 关闭线程；且它不是注入点 —— 事件源是 CoreHooks 安装的 JVM shutdown hook，仅在客户端确实启动过时派发

一条事件的完整链路

以最常被观测的每帧事件为例，从上到下的六步：

#发生什么证据
1vanilla 进 Minecraft.tick()，方法体 HEAD 处执行我们织入的唯一指令MinecraftMixin：@Inject(method="tick()V", at=@At("HEAD"), require=1)
2该指令调用 Dispatcher.fire(HookEvents.CLIENT_TICK)注入的字节码里只有这一条调用
3fire 查表；无监听器则立即返回Dispatcher.fire(HookEvent) 首行
4按 (order, seq) 升序遍历监听器：先 L1，后 L2 桥接Dispatcher.dispatch
5L1 监听器：CoreHooks 计数 + 节流打印 hook fired: client.tick (hit #N)CoreHooks.install() 内该事件的注册
6L2 桥接把类型化监听器取出：BrushEvents.CLIENT_TICK 以无载荷单例 ClientTickEvent.INSTANCE 送达 mod 的 onClientTick(...)BrushEvents.CLIENT_TICK 的桥接 lambda

同一形状换事件即可：bootstrap.early 的第 1 步是 Bootstrap.bootStrap() HEAD 上的 EarlyBoot.onBootstrap()；crash.report.details 的第 1 步是 CrashReport#getDetails(StringBuilder) 的 TAIL，第 5 步的监听器把 Brush 段追加进 StringBuilder。

加一个 hook 不需要重新 transform。 注入进字节码的永远只有那一条 fire 调用；新增订阅只动派发表。这正是「footprint 不随 hook 数量增长」的含义，也是「新增注入点前先评估能否复用已有注入点」这条纪律的底气。

调试能力：计数、dump 与日志怎么读

派发表是活对象

  • Dispatcher.listenerCount(HookEvent) / listenerCount(String)：某事件当前监听器数。String 重载是给自检源集回查用的走廊，新代码一律用 HookEvent 版本。
  • Dispatcher.listenerCounts()：全表快照。这就是「dump 派发表」的公开形态。
  • 计数快照在 CoreHooks 侧：hitCounts()、infoHitCounts()、stoppingHits()、creativeTabHits()。自检报告读的就是这些，并与台账的数字并列展示。
  • mixin 侧另有被动审计：BrushAuditTrail 实现 sponge-mixin 的 IMixinAuditTrail，在每次真实施加时收一条 Applied(target, mixin)，记录串形如 <config>:<mixin FQN> from mod <modid>。它不改变任何变换决策；S2/S3 下 mixin 子系统归宿主，本记录保持空集。

hook fired 日志行怎么读

[12:59:10] [main/INFO]: [brush]   mixin config registered: brush.mixins.json
[12:59:10] [main/INFO]: [brush]   injection points: 21, injected vanilla classes: 16 (footprint ledger: …)
[12:59:10] [main/INFO]: [brush] hook fired: bootstrap.early (hit #1)
[12:59:15] [Render thread/INFO]: [brush] hook fired: client.run (hit #1)
[12:59:15] [Render thread/INFO]: [brush] hook fired: client.tick (hit #1)
[13:00:05] [Render thread/INFO]: [brush] hook fired: client.tick (hit #1000)
  • 行内三要素：hook fired: + 事件 id 字符串+ (hit #N) 触发计数。
  • 时间戳与线程名在行首：main / Render thread 等是判断「这个事件在哪个线程触发」的第一手证据。上例中 mixin 配置注册与注入面数字都发生在 main，而 client.run / client.tick 在 Render thread。
  • 节流频率：client.tick 与 hud.extract 是「第 1 次 + 之后每 1000 次一行」；输入三键每 512 次；creative.tab.output 与网络每 64 次；注册窗口 / bootstrap.early / packs.registered / data.loaded / data.reload / crash.report.details 是每次触发都打印。因此「hit #1000 之后没有新行」不代表 hook 停了。
  • 注入面两行合看：mixin config registered 证明配置入了待选队列，injection points: N, injected vanilla classes: M 是设计侧数字。设计侧命中不等于运行期真触发 —— 后者由 hook fired 行自证：派发链断开就等不到这一行。
  • client.stopping 的证据行不走 log4j 而走 RawStdout：触发时游戏侧 log4j 已关闭，经 System.out 的输出会被静默丢弃。
