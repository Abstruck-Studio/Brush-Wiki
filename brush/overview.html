定位与整体架构

Brush 是一个 Minecraft 26.1.2 的自研模组加载器，目标是「一个加载器 + 一个 mod jar 跑三种运行时」。本页给出定位边界、三运行时对照、分层架构与贯穿全项目的工程纪律；具体机制见启动管线与三运行时与宿主适配两页。

Brush 是什么，不是什么

Brush 是加载器本体：自己解析版本元数据、自己装配依赖、用自己的 ClassLoader 加载 Minecraft、自己完成注入与模组加载。它不是 Fabric / NeoForge 的插件或衍生品，也不是 Architectury 那种「多模块编译出多个 jar」的抽象层。

边界一侧是「是」：加载器注入层派发层模组加载API 层。另一侧是明确不做：

  • 不做服务端运行时。
  • 不做 GUI 安装器、模组市场、自动更新、跨版本兼容。
  • 不做同一实例内 Fabric mod 与 Neo mod 并存：不存在两个 loader 平起平坐的并列共存，一个实例只能装一个宿主，真做这件事等于另立一个移植工程。
  • 不做任何形式的重映射：vanilla 侧与 mod 侧都不做。
Brush 的独特价值是 standalone 运行时（S1）+ 跨平台单 jar 分发。在宿主下启动、Mixin、冲突检测这些事由宿主提供，因此下面的三运行时定位必须讲清楚，否则叠加模式的价值会被误读为「变薄」。

三运行时对照

场景形态目标状态
S1原版 MC + Brush加载我们生态的 mod已达成
S2Fabric 版 MC + BrushFabric mod 与我们的 mod 同时可用已达成
S3NeoForge 版 MC（FML）+ BrushNeo mod 与我们的 mod 同时可用已达成
S4同一实例内 Fabric mod 与 Neo mod 并存—明确不做

推进顺序固定为 S1 → S2 → S3，顺序不可颠倒：未先在 vanilla 上打通启动与注入，就去做宿主适配，会导致核心与宿主耦合，日后无法独立化。

分层架构

层职责位置与关键类
启动管线manifest → version json → 库与 natives 装配 → assets 下载 → 自研 ClassLoader 加载 MC → 反射调用入口org.abstruck.brush.launch.**（Brush / BrushClassLoader / LaunchParams / DependencyAssembler / meta.* / deps.* / assets.*）
注入层类加载期在内存中改写字节码；磁盘 jar 一个字节不动transform.TransformBootstrap / BrushMixinService / BrushGlobalPropertyService / mixin.*
派发层每个 vanilla 方法上唯一一条 Dispatcher.fire(...)；监听器运行时增删transform.Dispatcher / HookEvents / CoreHooks
模组加载扫描 brush-mods/、读 brush.mod.json、依赖拓扑排序、实例化入口mod.*（ModBootstrap / ModResolver / ModClassLoader）
API 层把派发事件包装为语义化、跨运行时一致的 APIorg.abstruck.brush.api.**

宿主相关代码全部收在 .host 子包（host.fabric.* / host.neoforge.* / host.HostSeams），核心不引用任何 net.fabricmc.* / net.neoforged.* 类型。这一条是 S1 不被宿主污染的机械保证，详见三运行时与宿主适配。

与 Fabric / NeoForge 的关系：叠加，不是寄生

差别很关键：寄生是我们变成一个普通 mod、永久依赖宿主；叠加（overlay）是我们作为一层运行在宿主之上，且在 vanilla 上也能独立运行。

  • 宿主生态的 mod 由宿主自己加载，我们不需要去兼容它们。因此只剩一件事要解决：保证我们的 mod 与宿主的 mod 在同一 JVM 中共存。
  • S2 下 Brush 的 fabric.mod.json、S3 下的 META-INF/neoforge.mods.toml 保留不删 —— Brush 仍显示在宿主的 mod 列表里。
  • 宿主适配的经验事实：Fabric 与 NeoForge 都把 mixin.service 显式钉死为各自实现，三家共用同一份 sponge-mixin 制品（sponge-mixin 0.17.4 + Mixin 0.8.7）。

26.1.2 未混淆带来的「无重映射」红利

26.1 是第一个未混淆版本，且自带参数名。官方名即运行时名，Intermediary / Yarn 在 1.21.11 之后停止更新，Fabric 转向官方名，NeoForge 同样用官方名。三个运行时因此共用同一套名字：

运行时命名空间
S1官方名
S2（+Fabric）官方名
S3（+NeoForge）官方名

由此不需要实现：vanilla 侧重映射、mod 侧加载期重映射、映射表下载与合成、MappingResolver 式反射名解析、以及 refmap。同一份 brush.mixins.json 在 S1 由我们的 MixinService 应用、在 S2 由 Knot 应用、在 S3 由 FML 应用，零改动。

代码未混淆 ≠ 开源：EULA 未变，仍不可分发 MC 代码。发行包只保留代码与脚本，MC 文件、assets、natives、构建产物一律写入缓存目录并在 .gitignore 排除。

工程纪律

薄注入

每个 vanilla 方法上恰 1 个注入点，织入恰 1 条 Dispatcher.fire(...)；vanilla 类结构改动 0、控制流改动 0、磁盘文件改动 0。footprint 不随 hook 数量增长。

可链式优先

禁止 @Overwrite / @Redirect / @ModifyConstant / ci.cancel() / @Unique；需要重写方法逻辑时用 MixinExtras 的 @WrapMethod。

必须实测

任何「支持某生态 / 能跑某 mod」的表述都必须附 mod 名称与版本、运行日志、失败清单；未经实测只能写「未验证」，禁止写「应可运行」。

改动面台账

每次新增注入点都要更新注入面台账，并保持基线 / 台账 / 代码镜像 / mixin 实际指令四面一致。

最小改动是最高设计约束，不是审美偏好：footprint 越小，与宿主及其他 mod 撞车概率越低，S2 / S3 才成立。遇到「改动更少」与「实现更省事」冲突时，一律选前者。另有两条熔断规则：S1 必须始终可运行；任何「为了让宿主适配更省事而放宽核心隔离要求」的念头，停下并报告。

仓库形态

发行包由两个各自独立的项目组成：

Brush（加载器本体）
加载器核心 + 4 个宿主 harness/profile 类，另有独立的 bootstrap 自举源集。产出 build/libs/Brush-<version>.jar。
Brush API（能力库 mod）
内容注册 / 网络引擎 / 创造栏 / HUD 与输入 / 屏幕事件 / 键位。以 brush.mod.json 形态的库模组存在，自身可引用宿主类。
两阶段构建
先出加载器 jar，再用它编译库模组；库模组产物的默认位置在兄弟项目 Brush API 的 build/libs/brush-api.jar。
契约 jar（可选）
brush-api-contract.jar 只含 org.abstruck.brush.api.**，给「只想用语义 API」的作者做编译期自我约束；库模组产物缺席时它明确跳过并打印原因与出路，不影响 gradlew build。
API 层的硬约束：其天花板等于最受约束的平台，不得暴露只有在 S1 才做得到的能力，否则「写一次跑三处」是假承诺；语义必须三平台一致；同时必须提供平台特定逃生舱。这条约束直接决定了哪些能力会被否决 —— 例如 Access Widener 因其只能在 S1 生效而被明确不实现。
