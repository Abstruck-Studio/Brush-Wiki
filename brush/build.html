构建、产物与命令

交付里是两个各自独立、都能单独 build 的项目：Brush/与 Brush API/。加载器不依赖库模组即可编译出包；两者只在"作者编译契约 jar"这一处相交。本页给出产物清单、全部可用任务、属性覆盖、自举的真实规模与常见失败的归因。

两个项目与两阶段构建

目录是什么关键源集
Brush/加载器本体加载器核心源集 + 4 个宿主 harness/profile 类 + bootstrap 源集
Brush API/能力库 mod标准 Gradle 布局的单一 src 源集

构建即自举：gradlew build / jar / compileJava 会自动跑一次 metadata，把编译所需的 MC 客户端 jar 下下来—— 不再需要先手动跑 bootstrap。接线点：加载器项目的 verifyVanillaJar、库模组项目的 verifyInputs、MDK 示例项目的 verifyInputs 都默认 dependsOn 'metadata'。运行前本来就自动补齐库 + natives + assets。bootstrap 因此变成可选的"一次性备齐"命令。离线 / CI 逃生阀：传 -Pbrush.autoBootstrap=false 关掉自动自举 —— 那时缺件仍然可读失败，不会静默跳过。

:: ① 直接构建（构建期自动确保 MC 客户端 jar；首次需要联网）
cd "Brush"
gradlew.bat jar

:: ② 库模组：同样直接构建 —— 加载器核心默认从 JitPack 取（主 jar + classifier tools）
::    它的 verifyInputs 会自动带 installNeoForge，MC 侧与宿主产物走共享的用户级缓存
cd "..\Brush API"
gradlew.bat jar

:: ③ 回加载器再 build：契约 jar 自动发现 ② 的产物，无需传属性
cd "..\Brush"
gradlew.bat build

:: 可选：一次性备齐（客户端 jar + 库 + natives + assets），避免首次运行时等
gradlew.bat bootstrap            :: S1/S2 够用；要跑 S3 再补 installNeoForge
gradlew.bat installNeoForge

:: 可选：换落点（项目内、共享盘…）／关掉自动自举（离线、CI）
:: gradlew.bat jar -Pbrush.cache=<缓存目录> -Pbrush.vanillaJar=<26.1.2.jar 路径>
:: gradlew.bat jar -Pbrush.autoBootstrap=false

Brush API 项目的加载器核心默认从 JitPack 取，因此把整个文件夹拷到别的设备也能跑 S1 / S2 / S3：主 jar com.github.Abstruck-Studio:Brush:<版本>与宿主 harness com.github.Abstruck-Studio:Brush:<版本>:tools；仓库里加了 JitPack 源，且依赖解析是惰性的。离线 / 自包含回退：传 -Pbrush.useLocalJars=true 就改用随项目分发的 libs/Brush-<版本>.jar 与 libs/brush-tools.jar。它的 metadata / libraries / assets / bootstrap 用加载器 jar 里的主类（launch.meta / launch.deps / launch.assets）自己下载 MC；三个运行任务与 installNeoForge 都是自包含的 JavaExec，不委托任何兄弟项目。

JitPack 提供不了的那部分照旧本地自举：MC 侧仍走用户级 Gradle 缓存、仍需本项目自己下；NeoForge universal jar 也仍需本地安装产物（installNeoForge）。JitPack 只解决"加载器核心与宿主 harness 从哪里来"。

MC 侧默认落在用户级 Gradle 缓存里：vanilla jar 的默认 = <gradle 用户目录>/caches/brush/<mcVersion>/<mcVersion>.jar、MC 缓存的默认 = <gradle 用户目录>/caches/brush/cache/。因此项目根不再出现 26.1.2/ 与 cache/ 这两个大目录，而加载器项目、库模组项目、MDK 示例项目默认共享同一份下载；run/ 仍留在各自项目根。想换落点照旧传 -Pbrush.vanillaJar= / -Pbrush.cache= 覆盖。本机实测。

清空项目内旧目录后的实测：开发仓 metadata libraries assets = 20s、导出加载器 libraries assets jar = 9s、库模组项目 jar = 8s、MDK 示例项目 tasks = 7s —— 均 BUILD SUCCESSFUL。

开发套件（MDK）已扁平化、且默认从网络库取依赖：解压后项目根就是可运行的 Gradle 工程—— 没有 example-mod/ 这层子目录，也不再自带 libs/。加载器与能力库默认走 JitPack 坐标：com.github.Abstruck-Studio:Brush:26.10.1、com.github.Abstruck-Studio:Brush-API:1.0.0、以及同一加载器坐标的 tools classifier；仓库里加了 JitPack 源，解析是惰性的。离线 / 自包含传 -Pbrush.useLocalJars=true，改用你自己放进 libs/ 的三份 jar，缺件由新增任务 verifyLocalJars 给可读失败；版本可用 -PbrushVersion= / -PbrushApiVersion= 换。任务集 = bootstrap / metadata / libraries / assets / jar / stage / runClient（S1）/ runFabricClient（S2）/ installNeoForge / runNeoForgeClient（S3）/ verifyLocalJars —— 它用加载器 jar 里的 launch.meta / launch.deps / launch.assets 主类直接自举 MC，用 harness 直接拉起宿主，全程不依赖加载器源码。实测：网络模式 gradlew clean jar = BUILD SUCCESSFUL，离线缺件 = 可读失败。上手步骤与接线模板见第一个 mod。

版本单一来源：gradle.properties 的 mcVersion=26.1.2 与 loaderVersion=26.10.1。build.gradle 读它们，并在 processResources 时展开 brush.mod.json / fabric.mod.json / META-INF/neoforge.mods.toml / brush-build.properties 里的 ${version} 等占位符。

构建 JDK 不写死路径：四个 gradle.properties 里已删除写死的 org.gradle.java.home=<本机 JDK 路径>，改为 org.gradle.java.installations.fromEnv=JDK25_HOME —— 只写环境变量名、不含任何绝对路径；四个 settings.gradle 挂了 pluginManagement与 org.gradle.toolchains.foojay-resolver-convention 0.7.0，而 build.gradle 原有的 java { toolchain { languageVersion = JavaLanguageVersion.of(25) } } 保持不变 ⇒ 本机没有 JDK 25 时 Gradle 会自动把它下到 Gradle 缓存。JDK 装在 Gradle 不自动扫描的位置时：setx JDK25_HOME <JDK 25 目录>；临时指定用 gradlew.bat build -Dorg.gradle.java.home=<JDK 25 路径>。

全部可用任务

Brush/（加载器本体）

任务一句话需要网络？幂等？
buildJava 插件的聚合任务：assemble + check；只构建加载器时也能通过。构建期自动跑 metadata 补齐 MC 客户端 jar首次是；已缓存则否是
jar打包本体 → build/libs/Brush-<version>.jar首次是是
assemble装配全部产物；本项目挂了 apiContractJar 与 toolsJar否是
toolsJar把加载器项目的宿主 harness打成 build/libs/brush-tools.jar —— 供 jar 版 MDK 与库模组项目跑 S2 / S3；依赖 toolsClasses，只含自有类否是
publish把 brush 发布物写进默认的本地目录仓库 build/repo/**；默认不碰远程、不需要凭据。要发远程必须显式传 -Pbrush.publishUrl=否；传了 -Pbrush.publishUrl= 才需要是
publishToMavenLocal装进本机 ~/.m2 仓库，供本地联调否是
apiContractJar打包作者编译契约；含"产物里只能有 api 包"的机械校验否是
check验证任务聚合；本项目挂了 compileToolsJava否是
verifyVanillaJarvanilla jar 缺失时给可读失败；默认挂 dependsOn 'metadata'，所以正常构建时它是"自动补齐"而非"报错"否是
generateBrushResourceIndex扫描加载器自身的 assets/ 与 data/ 资源目录，生成 brush-resources.index否是
bootstrap可选的一次性备齐：客户端 jar + 全部库 + natives + assets —— 含 assets，所以能省掉首次运行时的等待是是
metadata取版本元数据（manifest → version json）；缺客户端 jar 时下载，已在则交叉核验 sha1 + size。—— build / jar / compileJava 默认依赖它是是
libraries下载全部 applicable 库并把 natives 解压到 cache/natives是是
assets下载资产索引与全部对象到 cache/assets是是
installNeoForge用官方安装器装宿主产物到 cache/neoforge/install/**，装完即退出、不启动游戏是是
runClientS1：通过 Brush 自己的 ClassLoader 启动本地 MC 客户端。依赖 libraries + assets，启动前清空 run/brush-mods/*.jar，并按可选的 -Pbrush.runMods= 摆入本次要用的 mod首次是，之后否；运行时本身要网否
runFabricClientS2：Fabric 宿主（Knot + Fabric Loader），Brush 作为宿主 mod 装进 run/fabric/mods/；同样先清空 run/fabric/brush-mods/，再按 -Pbrush.runMods= 摆入首次是否
runNeoForgeClientS3：NeoForge 宿主（FML），产物用 installNeoForge 备好；先清空 run/neoforge/brush-mods/，再按 -Pbrush.runMods= 摆入首次是；宿主产物缺件则要网否

Brush API/（库模组）

任务一句话需要网络？幂等？
build / assemble / checkJava 插件的标准聚合任务。构建期自动跑 metadata 与 installNeoForge 补齐编译所需件首次是是
jar产出 build/libs/brush-api.jar首次是是
verifyInputs三类输入缺件都可读失败并给全出路：加载器核心 jar、vanilla jar，以及 NeoForge universal jar。默认挂 dependsOn 'metadata' 与 dependsOn 'installNeoForge'，所以正常构建时它触发的是"自动补齐"而非报错否是
metadata / libraries / assets自包含：用加载器 jar 里的主类（launch.meta / launch.deps / launch.assets）自己下载客户端 jar / 库 / natives / assets，落地到用户级 Gradle 缓存—— 不依赖兄弟项目。其中 metadata 是构建期自动触发的那个是是
bootstrap可选的一次性备齐：自包含，且包含 installNeoForge—— 含 assets，所以能省掉首次运行时的等待是是
installNeoForge自包含（JavaExec）：main = org.abstruck.brush.tools.NeoForgeHostHarness，classpath = 加载器 harness+ 本体 jar + gson/log4j，工作目录 = 本项目 run/，实例目录 run/neoforge；S3 首次要先跑它。会自动找本地安装器，找到就不去连 maven，并打印 local installer -> <路径>是是
runClient（S1）自包含：JavaExec 直接以 org.abstruck.brush.launch.Brush 启动，工作目录 = 本项目 run/，启动前把 brush-api.jar摆进 run/brush-mods/；依赖 bootstrap + jar是否
runFabricClient（S2）/ runNeoForgeClient（S3）自包含（JavaExec）：main = org.abstruck.brush.tools.FabricHostHarness / NeoForgeHostHarness，classpath = 加载器 harness+ 本体 jar + gson/log4j，工作目录 = 本项目 run/，实例目录 run/fabric / run/neoforge；启动前把 brush-api.jar摆进该实例的 brush-mods/；均依赖 bootstrap + jar是否
publish把 brush-api 发布物写进默认的本地目录仓库 build/repo/**；默认不碰远程、不需要凭据；发远程必须显式传 -Pbrush.publishUrl=否；传了 -Pbrush.publishUrl= 才需要是
publishToMavenLocal装进本机 ~/.m2 仓库，供本地联调否是

"整个文件夹拷到别的设备"之后直接构建即可：gradlew.bat jar 会在构建期自动把 MC 客户端 jar 下下来；runClient 之前也会自动补齐库与资产。只有想"一次性备齐、避免首次运行时等"时才需要显式 gradlew.bat bootstrap。传 -Pbrush.autoBootstrap=false 可关掉自动自举 —— 那时缺件仍以可读失败拦下。三个运行时都不需要兄弟项目。

两处"为什么用独立任务而不是 doFirst"的原因相同：挂在 compileJava 上的 doFirst 会在任务 up-to-date 时被跳过，校验就静默失效了。

属性覆盖表

属性含义默认值 / 自动发现顺序
-Pbrush.vanillaJar=vanilla 26.1.2 客户端 jar默认= <gradle 用户目录>/caches/brush/<mcVersion>/<mcVersion>.jar —— 用户级 Gradle 缓存，三个项目共享同一份；传本属性可指到任意位置
-Pbrush.cache=MC 缓存目录默认 = <gradle 用户目录>/caches/brush/cache/ —— 同上，用户级缓存、跨项目共享；传本属性可覆盖
-PbrushCoreJar=库模组项目用：加载器 jar—— 默认模式不用它，那时核心来自 JitPack 坐标① 本属性；② 库模组项目下的 libs/Brush-*.jar；③ 加载器项目的 build/libs/Brush-*.jar。只在 -Pbrush.useLocalJars=true 时参与解析
-Pbrush.useLocalJars=库模组项目用：加载器核心的来源开关。传 true ⇒ 改用项目自带的 libs/Brush-<版本>.jar 与 libs/brush-tools.jar；不传 ⇒ 默认从 JitPack 取坐标默认= 走 JitPack；两份 libs/ jar 仍然保留在项目里，随时可回退
-Pbrush.jitpackVersion=库模组项目用：JitPack 上加载器的版本（tag|branch|commit）—— 同时用于主 jar 与 classifier tools 的 harness默认 test1
-PbrushApiJar=加载器项目用：库模组 jar，仅契约 jar 需要① 本属性；② 加载器项目下的 libs/brush-api.jar；③ 库模组项目的 build/libs/brush-api.jar
-Pbrush.neoforgeInstaller=本机 NeoForge 安装器 jar安装器自动发现顺序：① 本属性；② 缓存目录下的 neoforge/neoforge-*-installer.jar —— 这里的「缓存目录」=-Pbrush.cache= 的值，不传就是共享落点 <gradle 用户目录>/caches/brush/cache/；都没有才从 maven.neoforged.net 下载
-Pbrush.runMods=只对三个 run*Client 生效：本次运行要装进实例的 mod —— 值是 jar 文件或目录，多项之间用平台路径分隔符无
-Pbrush.publishUrl=仅发布用：远程 Maven 仓库地址；不传就不发远程无
-Pbrush.publishUsername= / -Pbrush.publishPassword=仅发布用：远程仓库凭据；只在传了 -Pbrush.publishUrl= 时才起作用，且凭据不写进仓库。两个项目共用同一组属性名无
-Pbrush.autoBootstrap=构建即自举的逃生阀：传 false 关掉"构建期自动跑 metadata"—— 离线 / CI 想完全自己掌控时用；那时缺件仍然可读失败，不会静默跳过默认= 开启自动自举

-Pbrush.runMods= 的时序与细节：任务先清空本次运行对应实例的 brush-mods/，再把指定 mod 摆进去，然后启动游戏 —— 顺序不能反，否则刚复制的 jar 会被清掉。给目录时取该目录下全部 *.jar，并打印一行 run mods staged into <目录>: <文件名列表>；条目既不是文件也不是目录 = 可读失败。用途是让"带自己的 mod 跑起来测试"不必手工拷 jar；不传该属性时行为与改造前逐字一致。

承载任务：brush.vanillaJar 与 brush.cache 被 metadata / libraries / assets / installNeoForge / 三个 run*Client 共用；brush.neoforgeInstaller 被 installNeoForge 与 runNeoForgeClient 读取；brushApiJar 只被 apiContractJar 读取；brushCoreJar 只被库模组项目读取；brush.runMods 只被三个 run*Client 读取；brush.publishUrl / brush.publishUsername / brush.publishPassword 只被 publish 任务读取；brush.autoBootstrap 被三个项目的输入校验任务（verifyVanillaJar / verifyInputs）读取；brush.useLocalJars / brush.jitpackVersion / brushCoreJar 只被库模组项目读取。

:: 只带一个 jar 跑 S1（先清空 run/brush-mods/，再把该 jar 摆进去）
gradlew.bat runClient -Pbrush.runMods=<你的 mod jar 路径>

:: 带一个目录里的全部 *.jar 跑 S2（多项用平台分隔符 ; 或 :）
gradlew.bat runFabricClient -Pbrush.runMods=<装着 mod jar 的目录>

:: 不带该属性 = 干净启动（与改造前行为一致）
gradlew.bat runClient

契约 jar 是可选产物

apiContractJar 的内容 = 核心的 org/abstruck/brush/api/** 加上库模组 jar 里的同名前缀条目。它要取另一个项目的产物，所以：

  • 库模组产物缺席时，任务用 onlyIf 跳过并打印原因与两条出路 —— 不再让 gradlew build 失败。
  • 跳过时的控制台文案形如：apiContractJar SKIPPED -- Brush API jar not found at <path> ; the loader jar does not need it. To also produce the contract jar: build the Brush API project (cd "../Brush API" && gradlew.bat jar -PbrushCoreJar=...), or pass -PbrushApiJar=<path to brush-api.jar>.
  • 产出时执行机械断言：除目录条目与 META-INF/MANIFEST.MF 外，每个文件都必须落在 org/abstruck/brush/api/ 下且不得含 api/impl/**；通过则打印 api contract jar: brush-api-contract.jar (N entries, api package only)。

常见构建失败的可读归因

症状根因出路
vanilla jar not found: <path>只有关掉自动自举（-Pbrush.autoBootstrap=false）或 -Pbrush.vanillaJar= 指到了不存在的路径时才会命中：源码引用 MC 类型，没有 jar 编译不过直接重新构建；或跑一次 gradlew.bat bootstrap 一次性备齐；或传 -Pbrush.vanillaJar=<path to 26.1.2.jar> 指到别处已有的 jar
loader core jar not found -- build it first: ...只在本地模式（-Pbrush.useLocalJars=true）下才可能命中：那时 verifyInputs 找不到项目自带的 libs/Brush-*.jar。默认走 JitPack 时这条不适用把加载器 jar 放进库模组项目的 libs/；或传 -PbrushCoreJar=；或去掉 -Pbrush.useLocalJars=true 回到 JitPack 模式
NeoForge universal jar not found: <path>可读硬失败：S3 载荷转注册桥编译期就要它，缺了 javac 会报成片"找不到符号"。默认只在关掉自动自举、或安装确实失败时才会冒出来四条出路：① 直接重新构建；② 显式跑 gradlew.bat bootstrap或单独 installNeoForge；③ 传 -Pbrush.neoforgeInstaller=<本地安装器 jar> 离线首装；④ 把 -Pbrush.cache= 指向一份已含 neoforge/install 的缓存
maven.neoforged.net 不可达 / 安装器下载超时 / TLS 证书链失败环境网络问题。S3 首次运行前必须先 installNeoForge 把宿主产物备齐三条离线路：① 拷现成的安装产物 —— 把别处已装好的 neoforge/install 整棵拷进缓存目录，harness 识别为"安装已完成"直接跳过安装器；② 用本地安装器；③ 已装好的缓存直接走"安装已完成"快路径，不再联网
brush-api-contract.jar 没产出契约 jar 是可选产物：库模组产物缺席时被明确跳过按上文"跳过时的控制台文案"给出的两条出路之一补上库模组产物
brush-tools.jar 缺席时 S2 / S3 起不来-Pbrush.useLocalJars=true 时 libs/ 少了 brush-tools.jar—— 于是 classpath 上没有 org.abstruck.brush.tools.*HostHarness，runFabricClient / runNeoForgeClient / installNeoForge 起不来。默认 JitPack 模式不受影响从加载器项目拷一份 brush-tools.jar放进本项目 libs/；或去掉 -Pbrush.useLocalJars=true
JitPack 坐标解析失败（Could not find com.github.Abstruck-Studio:Brush:…）JitPack 上该 tag / branch / commit 不存在或构建失败。解析是惰性的，所以 help / tasks 不会暴露这个问题① 用 -Pbrush.jitpackVersion= 换一个可用的 tag / branch / commit；② 或临时用随项目分发的 libs/：-Pbrush.useLocalJars=true
brush.runMods entry not found: <path>该属性指向的条目既不是文件也不是目录改传 jar 文件本身，或传"装着 mod jar 的目录"；先 gradlew.bat jar 确保产物已存在
