三运行时与宿主适配

同一个 Brush-<version>.jar 在三种运行时下形态不同：S1 它是加载器与入口，S2 / S3 它只是一个宿主 mod。本页说明三种形态、宿主隔离的判据、S3 特有的载荷转注册，以及形态 B这条最危险的风险线。

三种形态与启动命令

场景宿主 / 形态入口命令
S1无宿主。vanilla + 自研 BrushClassLoader + 自研 MixinServiceorg.abstruck.brush.launch.Brushgradlew.bat runClient
S2Fabric Loader 0.19.5（Knot）。Brush 作为 mod 放进 run\fabric\mods\Knot 按 fabric.mod.json 加载gradlew.bat runFabricClient
S3NeoForge 26.1.2.114（FML 11.0.15）。Brush 作为 mod 放进 run\neoforge\mods\net.neoforged.fml.startup.Clientgradlew.bat runNeoForgeClient

宿主下 P1 启动管线整体不启动：不调用 TransformBootstrap.install()，只注册派发表监听器；注入由宿主的 mixin 子系统在类加载期施加。fabric.mod.json / META-INF/neoforge.mods.toml 保留，因此 Brush 仍出现在宿主的 mod 列表里。

发行版的三个 run*Client 是交互式纯客户端启动，因此没有自动退出点与退出码断言 —— 它们用于人工观察，不是测试通道。runClient 启动前会清空 run\brush-mods\ 里的 jar，保证「干净 S1」是确定态。

宿主抽象与「核心不引用宿主类型」的判据

核心与宿主严格解耦，靠两条机械判据维持：

  1. 包边界：宿主相关代码全部收在 org.abstruck.brush.host 下（host.fabric.*、host.neoforge.*、host.HostSeams）；核心的 transform / mod / launch 层不 import 任何 net.fabricmc.* / net.neoforged.*。
  2. 通信只经系统属性与 JDK 类型：宿主入口把事实写成系统属性（brush.host / brush.host.version / brush.host.mods / brush.game.version），核心单向读取；跨层调用只经 JDK 类型（Path / String / BiFunction）与反射，不共享自定义类型身份。

唯一的「反向」需求是 S3 的 mod 事件总线：它只有核心的 @Mod 构造器拿得到，若核心去调桥就变成 core → mod。解法是 host.HostSeams 这条接缝 —— 核心只把事件总线当 Object 递出去（fireModEventBus），由库模组注册回调自己接住并挂载载荷转注册。核心因此零 mod 类型引用，「引用宿主类型」留在允许引用宿主类的库模组里。

核心侧的改动面被压到极小：CoreHooks / InjectionLedger 转 public、Selftest 增加 brush.host* 属性读取与宿主守卫位。

brush.standalone 守卫：让自研 MixinService 在宿主下让位

BrushMixinService.isValid() 的实现只有一行语义：仅当系统属性 brush.standalone 为 "true" 时有效。该属性只由 TransformBootstrap.install() 在 standalone 启动时设置，宿主引导路径不会设置它。

但真正让 S2 / S3 结构性安全的不是这个守卫，而是宿主的属性钉死：Fabric 的 FabricMixinBootstrap 与 NeoForge 的 MixinFacade 都在 mixin 引导之前显式 System.setProperty("mixin.service", …)，sponge-mixin 的 MixinService.initService() 优先读该属性 —— 宿主环境根本不走 ServiceLoader 枚举。

运行时实测 mixin.service
S1Brush（org.abstruck.brush.transform.BrushMixinService）
S2Knot/Fabric（net.fabricmc.loader.impl.launch.knot.MixinServiceKnot）

自检里另有一位守卫：宿主模式下若 brush.standalone 意外为 true、或 mixin 服务是 BrushMixinService，即判失败 —— 防「模式切换错误导致后续全部无意义」。实测报告行：host.guard: ok (standalone mark absent, mixin service is not BrushMixinService)。

宿主下 ClassLoader 的分工

  • 宿主有自己的加载器（Knot / FML TransformingClassLoader），MC 类的定义权在宿主。
  • 我们的加载器只服务我们自己的 mod，不抢 MC 类的定义权。
  • 我们自己的 jar 不进宿主 JVM 的 classpath：它以 mod 形态被宿主发现并按元数据处理 —— 这正是「Brush 在宿主下只是一个普通 mod」的形态自证。
  • 依赖重复（ASM / gson / mixin jar）需排查，优先复用宿主提供的。预研实测：三方的 mixin 内核完全同版本（sponge-mixin 0.17.4 + Mixin 0.8.7），风险面因此收缩为类空间归属问题。

两个宿主目录的隔离约定

我们的 mod 放 brush-mods\，不混 mods\：宿主加载器会扫 mods\，而我们的 mod在那边可能被告警或误解析；反过来我们也可能误扫宿主的 mod。双向隔离成本很低。

实测：宿主扫 mods\，我们的加载只看到 brush-mods\ 里的我们生态 mod —— 双向不越界。S1 的目录同样固定为 <game-dir>\brush-mods，三个运行时用同一份实现。

S3 特有：载荷转注册

vanilla 的 CustomPacketPayload 没有方向接口，而 NeoForge 要求自定义载荷先经它的 NetworkRegistry 登记，未登记者 checkPacket 直接拒绝。后果是真实的平台缺口：S3 实机探针首次跑时崩在发载荷上 ——

java.lang.IllegalStateException: [brush] hook listener (order=0, seq=32) for event 'client.tick' failed
  Caused by: java.lang.UnsupportedOperationException: Payload pingnet:ping may not be sent to the server!

修法是把已知通道转登记进 NeoForge：在 mod bus 的 RegisterPayloadHandlersEvent 上对每个通道调用 playBidirectional(type, codec, NOOP, NOOP)。handler 是空实现，登记只为让方向校验放行，投递仍走我们自己的注入点 —— 实测 server.pings=1, client.pongs=1 证明既无双重投递、也未被打包截走。桥与网络引擎现已整体住在库模组 brush-api（org.abstruck.brush.api.impl.host.NeoForgePayloadBridge），核心只经 HostSeams 把事件总线递出去。

已登记的局限：桥只覆盖它收到总线之前已经登记的通道。一次独立评审指出 S3 自检档桥为 1 of 1 而同场报告 network: channels=2 —— 晚登记的通道在 S3 下可能发不出去。当前残留表现是 S3 下 8 条 No registration for payload …; refusing to decode 提示，被定性为良性噪音。

形态 B（静默失效）与防线现状

注入失效可分两形态：形态 A在 require=1 下硬失败，可捕获；形态 B无任何报错，是更坏的形态。项目纪律原设计有三层防御，其中第三层是「启动期扫描 @Overwrite 并告警」。实测两宿主的时间线证明当前形态未触发形态 B：S2 ready 早于 hook fired: client.run，S3 ready 同样早于它。

须知道的现状变更：那层主动扫描器已被用户撤销。自检报告行固定打印 overwrite.scan=not-implemented。形态 B 的防线因此回退为三条：① 注入点 require=1；② mixin / 宿主自身的冲突日志；③ 薄注入 + 可链式选址带来的天然低冲突面。对应的纪律修订提案当时待用户确认 —— 本页以实测记录为准。

另有一条同源的补充证据线：宿主（S2/S3）的 mixin 服务不汇报施加台账，因此「mod 自带 mixin 到底有没有生效」在宿主下没有内省证据。解法是行为断言 —— 在真实运行时驱动被 mod 包装过的方法看结果，三运行时同一条断言全 result=ok。这条证明的是效果，与注入点台账证明的织入互补，缺一不可。

「S1 必须始终可运行」的熔断规则

熔断：一旦 S1 跑不通，说明核心已被宿主污染，立刻停下重构；任何阶段若发现「为了让宿主适配更省事而放宽对核心的隔离要求」，停下并报告，不要自行推进。因此每次宿主适配改动后都要重跑 S1 回归：P6 核心 8 个文件改动后重跑 T1 为退出码 0、host=vanilla、mixin.service=Brush；P7 改动后 T1 与 T2 同批重跑均为退出码 0，三运行时同时绿。

仍未验证 / 需人工确认的项

  • 真实渲染与游玩：自检模式在首个 client.tick 即退出，未进入主菜单；runFabricClient / runNeoForgeClient 的窗口与主菜单属人工验证项，官方口径是不用「未跑」冒充通过。
  • 注入点失配风险：NeoForge 自身改动 vanilla，失配风险高于 Fabric；缓解是更保守的选址与更严的校验。当前目标点实测命中，属本配置结论，不外推。
  • S2/S3 下的 mod mixin 内省：仍是 n/a；效果已由行为断言覆盖，但「内省不到」这一事实保留。
