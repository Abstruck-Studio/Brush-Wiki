资源、数据与界面

Brush 把三类东西接进游戏：mod jar 里的 assets/**、mod jar 里的 data/**，以及 S1 下加载器自身的资源树 —— 三者都挂在同一个注入点上。加载器自己还带来一套 UI。本页讲"有什么、怎么触发"，细节指向 API 部分。

S1 的内建资源包 brush_core

S2 / S3 下宿主会把 brush 制品当资源包挂载，brush 命名空间天然可见。S1没有任何机制挂载我们自己的资源 —— 于是侧栏绘制的 blitSprite("brush:tab_left_*") 全部落空。修复方式是在 standalone 下把加载器自身的类路径资源树作为内建资源包 brush_core 接进资源包仓库（BrushCorePackResources）。

为什么需要构建期索引：类路径条目无法在运行期枚举，而 gui 图集的 directory 源要求逐文件 listResources。所以文件清单由构建期任务 generateBrushResourceIndex 扫描加载器自身的 assets/ 与 data/ 资源目录生成 brush-resources.index，经 processResources 打进类路径根；运行期一次读入充当枚举源。文件内容仍经类路径 getResourceAsStream 直读，目录与 jar 两种形态通用 —— 与默认图标同一通道。

项值 / 语义
包 idbrush_core（BrushCorePackResources.PACK_ID）
索引资源名brush-resources.index
分流守卫Boolean.getBoolean(brush.standalone) —— 与 BrushMixinService.isValid() 同一属性，不新增开关；S2/S3 走宿主分支、不重复挂载
站位required=true + Position.BOTTOM + fixedPosition=false
索引缺失不挂包 + ERROR 告警 + 自检置位，禁止静默降级

加载器自身实际提供 9 个 assets/ 下的 PNG，构建期索引会列出全部。实测日志形如 [brush] core resource index: 9 file(s) 与 attached core resource pack 'brush_core' (standalone; 9 classpath file(s))（run/logs/latest.log，2026-10-16）。早期设计资料记录的是 7 文件档，属纹理增补前的形态 —— 两种数字的差异本身是如实的版本演进痕迹。

S2 / S3 的差异：资源由宿主挂载

同一个注入点（PackRepository#<init> RETURN）在三个运行时都命中，但三档挂载不同：

运行时实测 reload 行（原样 / 节选）我们的包的位置
S1Reloading ResourceManager: vanilla, brush_mods, brush_core最后 = 高于 vanilla
S2Reloading ResourceManager: vanilla, fabric-api, …, fabricloader, sodium, brush_mods最后 = 最高
S3Reloading ResourceManager: brush_mods, vanilla, mod_resources, mod/sodium, mod/brush, mod/neoforge最前 = 最低

查找语义决定这个顺序的意义：openAllSelected() 按选中列表顺序构造 MultiPackResourceManager，getResource 自表尾向前扫描、首个命中者胜出 —— 列表越靠后优先级越高，reload 日志行的顺序即该列表顺序。因此 S1/S2 下 用户资源包 > 模组资源 > vanilla；S3 是已登记的例外：NeoForge 重排包序后我们的包在最底，mod 资源不覆盖 vanilla 与宿主 mod 资源。S2 下与 fabric-resource-loader-v1 在同位置各读 this.sources，任意先后施加互不抹除。

mod 自带资源与数据

每个 mod jar 根下按 vanilla 布局放文件即可，mod 侧零代码、零注入：

brush.mod.json                                 ← 元数据
assets/<mod-id>/items/ruby.json                ← 物品模型定义（26.1.2 格式）
assets/<mod-id>/models/item/ruby.json          ← 模型（item/generated + layer0）
assets/<mod-id>/lang/en_us.json / zh_cn.json   ← 语言（键如 item.example.ruby）
assets/<mod-id>/textures/item/ruby.png         ← 材质（16x16）
data/<包命名空间>/...                          ← 配方 / 进度 / 战利品表 / 自定义注册表条目
// items/ruby.json
{ "model": { "type": "minecraft:model", "model": "example:item/ruby" } }
// models/item/ruby.json
{ "parent": "minecraft:item/generated", "textures": { "layer0": "example:item/ruby" } }
// lang：{ "item.example.ruby": "Ruby" } / { "item.example.ruby": "红宝石" }

机制：一个包聚合全部 mod jar，footprint 恒为 1 个来源、不随 mod 数增长；命名空间天然由 assets/<mod-id>/ 区分。ModPackResources 直接开 mod jar 查条目，读取语义镜像 vanilla 的 FilePackResources；SERVER_DATA 返回空集。pack.png / pack.mcmeta 不参与：包元数据全部由代码程序构造。

数据包注册表扩展（G1）

api.BrushDataRegistries.register(ResourceKey, Codec) 是 mod 自定义数据包注册表的唯一登记入口；读取经 BrushRegistry.dataRegistry(key) 返回 Optional<Registry<T>>。

  • 为什么是 Brush 自有的 RegistryAccess：26.1.2 已无 vanilla 服务器侧"数据包注册表可重载"路径 —— 4 参 RegistryDataLoader.load(ResourceManager,...) 只被 WorldLoader 以 worldgen / dimension 表调用，/reload 只重载 loot 表 ⇒ 把 mod 表并入 vanilla 表清单不可行。
  • 装载机制全部复用 vanilla 公开 API：RegistryDataLoader$RegistryData 公开 record 构造器 + RegistryValidator.NONE、ResourceManagerRegistryLoadTask 的公开构造器与 load / freezeRegistry / validateRegistry、MappedRegistry、RegistryAccess$ImmutableRegistryAccess + freeze()。
  • 装载算法（DataRegistryEngine.reload）：快照登记 → 每项建 load task→ 稀疏跨注册表查找器 → 并行 load + allOf().join()→ 按登记序冻结，再统一校验→ 全通过则原子替换当前视图。
  • 登记时机：内容注册窗口或之后任意时刻；bootstrap 期不得调用。
  • 键身份：ResourceKey 在 26.1.2 是身份相等—— 登记、读取与 codec 中引用它必须用同一键实例。
布局条目路径
vanilla 机制布局data/<包命名空间>/<键路径>/*.json —— mod 侧按此放置即可三运行时通用
宿主命名空间布局data/<包命名空间>/<注册表命名空间>/<键路径>/*.json —— S2/S3 对非 minecraft 注册表会前置注册表命名空间，由桥接层兜住

桥接层 BridgingResourceManager 零注入面：wrapIfNeeded 按每个登记键的运行时 Registries.elementsDirPath(key) 组装层栈，两布局都可读、同名 id 以 vanilla 机制文件优先；无需桥接时原样透传。条目 id 的命名空间来自数据包目录，与键的命名空间无关。多包合并靠后的包优先。标签目录不桥接 —— 需按宿主原生布局放置。

数据加载 / 重载事件：BrushEvents.DATA_LOADED 锚在 MinecraftServer#<init> RETURN，DATA_RELOADED 用 @WrapMethod 包 reloadResources。线程注记：前者派发于服务器构造线程，后者派发于完成线程—— 监听器不得触碰屏幕 / 渲染。

错误语义：任一 freeze / validate 失败 → 逐键 ERROR 日志、保留旧视图、返回 false；首次装载失败则视图保持 null，mod 经 dataRegistry(key) 空判降级。数据错误不中止世界加载 —— Brush 的表独立于 vanilla 数据，不该因一条坏 JSON 让整个存档进不去。已知边界：vanilla 侧看不到我们的注册表；客户端 JVM 无 MinecraftServer 时事件不触发、dataRegistry 为空。

mod 访问器与外部工程接线（结论）

一句话结论：先查已由 Brush 代管的清单 —— 实体类型 / 属性 / 刷怪放置 / 方块实体类型 / 菜单类型 / 实体渲染器 / 方块实体渲染器 / 菜单屏幕这 8 类注册场景一律走 BrushRegistry，mod 不必自己写 accessor mixin 或反射；其余 private 成员用接口型 mixin 的 @Invoker/ @Accessor，成员加 modid 前缀、目标名用官方名，且可见性不变。不要给 vanilla 类加 @Unique 字段 —— 需要关联数据时用外部 WeakHashMap。外部 Gradle 工程不依赖 Brush 源码仓即可编译与本地运行，最小模板见 第一个 mod 与交付说明。
