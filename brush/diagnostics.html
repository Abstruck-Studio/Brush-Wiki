测试矩阵与诊断

Brush 的验收由四道门禁组成：T1–T3 是三场自检，T4 是不启动游戏的静态台账闸门。本页说明每道门禁测什么、在 Windows 上怎么做到可自动化、实机探针覆盖哪些"必须真进世界"的行为，以及出问题时用哪些现有工具归因。发布版不含测试装置，见末节。

1. 四道门禁（T1–T4）

编号场景任务断言通道测什么
T1 S1 冒烟：vanilla + Brush + 示例 mod runSelftest退出码 hook 全命中、无注入失败
T2 S2：Fabric Loader + Fabric API + 真实 Fabric mod runFabricSelftest退出码 T1 全部 + Fabric mod 出现在已加载列表 + 无 Mixin 冲突日志
T3 S3：NeoForge + 真实 Neo mod runNeoForgeSelftest退出码 T1 全部 + Neo mod 出现在已加载列表 + 无 Mixin 冲突日志
T4 footprint 回归 footprintCheck进程退出码 基线 / 注入面台账 / 代码镜像 / 真实注入指令四面一致；注入面变更必须显式登记

自检模式由启动参数 --brush.selftest 打开：跑到预定生命周期点后打印结构化报告并主动 System.exit(退出码)，不等用户操作。退出码即断言通道 —— JavaExec 退出码非 0 直接令构建失败，无需额外判定代码。

2. 退出码位（断言通道的编码）

位序（值）含义状态
—（0）全部通过—
0（1）通用失败在用
1（2）注入审计失败在用
2（4）overwrite 告警已撤销，槽位不再分配
3（8）宿主 / 模式守卫（S2/S3）在用
4（16）内容注册归账审计失败在用
5（32）资源审计失败在用
6（64）入口审计失败在用
7（128）TAB 审计失败在用
8（256）mod 自报自检失败在用
16（65536）mod 实机测试项失败（EXIT_MOD_TEST）在用

按位或组合。记号约定：位序 n 的值为 2 的 n 次幂；早期资料里"退出码位 4"曾指值 4，引用时带上括号里的值即可消歧。

3. Windows 上如何做到可自动化

关键手段是把退出点选址在渲染之前：退出点 = 首个 client.tick。此时五个 hook（bootstrap.early / registries.bootstrap / packs.registered / client.run / client.tick）均已真实触发 ≥1 次，且位于纹理图集烘焙与首帧渲染之前。

如实边界：GL 上下文与窗口由 Minecraft 构造器创建，早于任何 hook 锚点 —— 自检做不到"GPU 初始化之前"。因此纯 headless 的 CI 不可行；本机有显示环境时 T1 全自动可行，窗口短暂闪出即自动退出。Fabric 官方那套 headless 客户端测试依赖 Linux 的 XVFB，Windows 上没有对应机制。

不降严格度：注入点未命中由 require=1 在类加载期直接中止启动；派发链断裂由审计位捕获；期望集为空 = 失败；游戏若在退出点前正常返回，app 侧打印 selftest was armed but the game returned before its exit point 并返回 1。真实渲染与实际游玩行为一律标注"需人工确认"，禁止用"跳过该断言"冒充通过。

4. 实机探针测什么

自检退出点在世界加载之前，覆盖不到"进世界之后"。实机探针（runRealityProbe / runFabricRealityProbe / runNeoForgeRealityProbe）真进世界后逐项断言；宿主形态由 harness 的 --reality 通路 + 预置世界打通。

相位测什么实测判据（日志原文摘录）
网络：恰好一次 + 主线程 服务端钩子生效；客户端恰好一次；投递在主线程 roundTrip: server.pings=1, client.pongs=1 (expected 1/1), mainThread=yes -- result=ok
HUD 像素 监听器每渲染帧在 GUI (6,6) 画 8x8 洋红标记，再截屏读像素 hud: frames=1291, pixels((12,12)=FFFF00FF …)；四角像素全中，画面中心是世界天空色
输入事件 PowerShell 驱动向游戏窗口 PostMessage 一条 OS 级 WM_KEYDOWN('B')，经 GLFW 到达 KeyboardHandler#keyPress 的 HEAD 注入点 key=B(66), action=PRESS, scancode=48
方块放置 服务端线程 setBlockAndUpdate→ 客户端读回 → 60 tick 渲染停留 block-place: … changed=true … client read-back=example:ruby_block (block_update encoded + delivered) -- result=ok (render dwell 60 ticks completed, no crash)
mod 自带 mixin 的行为 在服务端线程驱动 ServerPlayerGameMode#destroyBlock 做差分测试：普通方块须能破坏、基岩须被拒且保持、包装器自记账计数器须按预期增长 mod-mixin: block-guard WRAP_HITS +2, PROTECTED_HITS +1, normal.destroyed=true, bedrock.destroyed=false, bedrock.intact=true -- result=ok
数据锚点 入世界后 data.loaded 命中、/reload 后 data.reload 命中且视图不掉 data.loaded: fired=yes, view=1 registries / 2 entries […] -- result=ok

断言本身也被验证过：临时短路去重后复跑，探针如期把构建打红（client payload delivered 2 time(s), expected exactly 1，exit.code=4），随后恢复并复跑 PASS。

保留的人工边界：像素级观感与操作手感仍是人眼项；26.1.2 集成服务器的传输层是内存通道，socket 级与专有服务器往返不在范围。

5. compatTest 系列与归档产物目录

聚合入口有三个：compatTestFabric（T2）、compatTestNeoForge（T3）、compatTest。

  • footprintCheck 以 mustRunAfter 排在三场 run 之后：同图执行时最后跑，防止 fail-fast 在首个 run 失败时提前掐掉后续归档。
  • 三场 run 按任务名字母序执行（runFabricSelftest → runNeoForgeSelftest → runSelftest）；fail-fast 会让靠后的 run 不执行，排障时以日志里的 > Task :run… 行为准，不要假定 T1 先跑。
归档文件（run/compat-test/）内容机制
t1|t2|t3-console.log 控制台双通道合一：装配器 + 子 JVM 游戏侧，按发生顺序 tee 流同写控制台与归档文件
t1|t2|t3-latest.log 游戏侧 latest.log 的字节级快照 归档任务经 finalizedBy 挂在对应 run 之后 —— run 失败也照常归档

run/ 不进版本库（.gitignore）。实测结论台账里每条结论都附真实日志路径与关键行，其中"现行门禁态"一节只写截至最后一次运行的事实值、每轮刷新。归档是覆盖式快照，历史轮现场不随文件保留 —— 修复史以文档与源码 javadoc 为完整档。

6. footprint 台账的"四面一致"

T4 是跨来源的四面核对：点数求和、被注入类名取并集。四面全部一致才 PASS。

面来源捕获的漂移
基线FootprintCheck 的 BASELINE_POINTS / BASELINE_CLASSES代码镜像改了但基线未同步
注入面台账台账的摘要行 + 表行 / 去重类数文档、摘要、代码三者不一致
代码镜像InjectionLedger镜像与基线 / 台账漂移
真实注入指令ASM 读 mixin 配置列出的 mixin 类：注入器注解方法数 + 注入器承载类的 @Mixin 去重 targets"加了 @Inject 但没登记台账"这类漏改
  • 第 4 面用 ASM 而非反射：@Mixin 是 CLASS 保留，运行期反射看不见。
  • 不解析运行日志：过期档案会假绿 / 假红；运行态数字由三场自检报告各自呈现。
  • 挂进 check：gradlew build 自动跑，也是 compatTest 的 T4 环节。

新增一个注入点要过哪些闸门：① 形态 —— 同一 vanilla 方法最多 1 个点、每点最多 1 条指令、不改类结构与控制流；② 注入器与选址 —— 必须可链式，优先 HEAD / TAIL / RETURN，避免 CONSTANT 与 ordinal 定位，热路径点单独论证；③ 复用评估 —— 先看能否复用已有注入点，复用成功即"零新增注入面"；④ 登记 —— 同一变更内让四面同步并写明理由，可见性改动（access widener / AT）同样逐条登记。

闸门语义是"变更必须显式登记"，不是"禁止增长"：注入面变化不被禁止，未同步的漂移一律 FAIL。失败路径已实测：把台账副本的摘要改成与代码镜像不一致的数字后再跑一次，闸门精确报出 ledger doc summary differs from code mirror 并以 exit 1 / BUILD FAILED 收场。

7. 归因工具箱

工具 / 通道怎么用
自检报告行 格式 [brush] selftest: <key>=<value>，整段由 ===== SELFTEST REPORT/END ===== 包裹 —— grep "selftest:" 即可机器提取。双通道取证：控制台 stdout + 游戏侧 run/logs/latest.log
注入命中清单 设计数 injection.points(ledger) / injected.classes(ledger) + 逐点运行数 hook.<event>: listeners/hits/fired，收束行 injection.audit: N/N expected hook(s) fired, M missing；启动日志另打 injection points: 21, injected vanilla classes: 16
模式切换观察点 host=、mixin.service=、host.guard: ok —— 这一项出问题会让后面的判断全部无意义
overwrite 告警 扫描器已撤销，报告固定打印 overwrite.scan=not-implemented。形态 B的防线回退为 require=1 + mixin / 宿主冲突日志 + 薄注入选址
mixin 审计落盘 -Dbrush.mixin.dump=true打开上游 mixin.debug.export，并注册退出钩子把"哪些 mixin 施加到了哪个目标类"落盘为 .mixin.out/brush-audit-trail.log。S2/S3 直接传上游 -Dmixin.debug.export=true。边界：进程被强杀时钩子不执行，无产物
崩溃报告 实例运行目录下 run/crash-reports/crash-<时间戳>-client.txt；正文末尾由 Brush 追加 -- Brush -- 段。注入点 = CrashReport#getDetails(StringBuilder) TAIL

标准排查顺序：① 看清崩溃栈指向 MC 类 / 库类 / 我们自己的类，还是"无报错只是不生效"；② 跑自检模式拿宿主类型与版本、注入点命中清单、overwrite 告警、已加载 mod 列表；③ 确认 Brush 模式切换正确；④ 最小复现；⑤ 与 S1 逐项对比环境。跨运行时崩溃的结论写进实测结论台账并附真实日志与复现步骤 —— 禁止在没有日志的情况下写"应该是某某问题"。

8. 发布版与完整开发树的差别

导出项目只做两件事：产出本体与自举运行资产。测试装置是有意精简掉的：已移除的测试性运行配置包括 runSelftest(T1) / runFabricSelftest(T2) / runNeoForgeSelftest(T3) / footprintCheck(T4) / compatTest* / modTest / runRealityProbe* / runExampleClient* / archive*Log；已移除的测试代码与夹具链包括单测源码、自检与实机探针源码，以及 compileExampleMod / generateFixtureMod 等夹具任务。

保留：runClient / runFabricClient / runNeoForgeClient，以及 bootstrap / metadata / libraries / assets / installNeoForge / check。产物：build/libs/Brush-<version>.jar 是 gradlew build 的必产出；brush-api-contract.jar 是可选产物。

要跑矩阵就得用含测试装置的完整开发树：四道门禁、实机探针、归档任务与注入面台账都在那一份源码里，发布树只保留"产出本体 + 自举运行资产"。发布树里找不到 runSelftest 不是"任务坏了"，而是发布范围。精简后的本体 jar 与完整开发树的同源产物逐条目零差异。
