模组加载

Brush 的模组加载是"扫描目录 → 解析元数据 → 校验 → 依赖拓扑排序 → 逐 mod 建类加载器 → 实例化入口 → 调 onInitialize()"的一条直线流程，全部由 org.abstruck.brush.mod.ModBootstrap 驱动。本页讲清目录约定、brush.mod.json 字段全表、入口契约与"失败可读"的具体形态；加载器自身也遵循同一套元数据格式。

目录约定与各运行时的实例目录

我们生态的 mod 放在独立的 brush-mods/，不与宿主的 mods/ 混放。理由：宿主加载器会扫 mods/，对我们的 mod可能告警；我们也不该误扫宿主的 mod。

项约定
识别对象仅 *.jar
扫描顺序按文件名字典序
非 jar 项打印 skipping non-jar entry，不报错
目录不存在自动创建，报告 0 jar(s) —— 这是合法状态，不是错误
jar 缺 brush.mod.json报错
运行时实例 mod 目录预处理缓存
S1<工作目录>/brush-mods/<工作目录>/brush-cache/prepared/
S2（Fabric）run/fabric/brush-mods/run/fabric/brush-cache/prepared/
S3（NeoForge）run/neoforge/brush-mods/run/neoforge/brush-cache/prepared/

依据：build.gradle 的 registerBrushRun / registerFabricRun / registerNeoForgeRun 与 ModBootstrap.install 中的 modsDirAbs.resolveSibling("brush-cache")。三个 run*Client 任务在启动前会清空自己实例的 brush-mods/*.jar，因此"干净 S1"是确定态。

brush.mod.json 字段全表

元数据文件名是 brush.mod.json（ModBootstrap.METADATA_ENTRY），位于 jar 根目录。未知字段被 Gson 静默忽略。

字段必需类型 / 语义校验与失败档位
id是模组唯一标识须匹配 [a-z][a-z0-9_.-]*；本次扫描内唯一
version是点分纯数字版本缺 = 失败；格式非法 = 失败
name否展示名缺省回退 id
description否描述仅展示
authors否字符串数组仅展示
icon否jar 内条目路径，如 icon.png 或 assets/example/textures/item/ruby.png展示性，不阻断加载：条目缺失 / 是目录 → 加载期 warn，UI 回退 Brush 默认图标
entrypoints.main是类全名数组类名结构 + 入口契约
entrypoints.client否类全名数组同契约，但实现 BrushClientModInitializer；类不在加载期加载，迟绑定到 client.run 锚点
entrypoints.server否类全名数组只做类名结构校验：类不加载、方法不派发
entrypoints.test否类全名数组类名结构校验在加载期；接口检查（ModClientTest）在 --brush.mod-test 探针实例化时
mixins否按运行时分组的对象：键 brush / fabric / neoforge，值 = jar 根下的 mixin 配置资源名数组功能性，条目缺失即失败；未知键 = 失败；brush 是默认组，fabric / neoforge 缺省时继承它；平铺数组形态已废弃并 fail-fast
depends否对象：mod id → 版本区间硬失败：目标缺失或版本不满足即中止加载
breaks否同上硬失败：目标在场且版本落入区间即拒绝加载
conflicts否同上WARN，不阻断
recommends否同上WARN：缺失或不满足
suggests否同上纯元数据：加载器不读取、不校验、不告警
provides否别名 id 数组格式同 id；不得等于自身 id、不得自重复；跨 mod 冲突由 ModResolver 报硬失败；别名参与拓扑排序
jars否对象数组，沿用 Fabric 形态 [{ "file": "nested/vendor/dep.jar" }]功能性：条目在 mod jar 内不存在 = 加载期可读失败；解出的嵌套 jar 进入该 mod 的类加载范围
testJar否jar 外路径空白值 = 失败；缺省合法

依赖声明的取值支持字符串或字符串数组两形态。版本区间语法（VersionRange）：缺省 / 空串 / * 表任意；裸版本串 = 精确相等；>= > <= < =；^与 ~；空格分隔 = AND；|| 分隔 = OR。两个特殊 id：brush 比对加载器自身元数据的 version，minecraft 比对 version json 的 id。

加载顺序

  1. 扫描：Files.createDirectories 保证目录存在 → 收集 *.jar → 字典序排序。
  2. 解析 + 校验：逐 jar 用 ZipFile 读根条目 brush.mod.json → Gson 解析 → ModBootstrap.validate 结构校验 → 同一次 ZipFile 作用域内做 checkIconEntry（warn）与 checkMixinEntries。
  3. 依赖解析：ModResolver.resolve —— id 去重 → 别名登记 → 依赖存在性与版本区间 → breaks / conflicts / recommends → Kahn 拓扑排序。
  4. 运行时接面：经 RuntimeBridge 逐个做平台桩预处理（ModJarPreparer）→ 解嵌套 jar（NestedJarExtractor）→ 建该 mod 的 ModClassLoader → exposeModJar 暴露进共享类空间 → 注册当前运行时生效组的 mod mixin 配置。
  5. 实例化入口：按拓扑序逐个实例化 entrypoints.main 的类，登记进 loadedMods()。
  6. 调 onInitialize()：紧跟构造之后，在同一 ModContext 内调用。
  7. 报告：打印 order: / 逐条 loaded: / 摘要行与双版本行。client 入口留到 client.run 锚点。

入口契约

三个条件缺一不可，任一不满足都转为可读失败：

  • public 具体类 —— 接口或抽象类被拒绝（must be a concrete class）。
  • public 无参构造器。
  • 实现对应接口 —— entrypoints.main → org.abstruck.brush.api.BrushModInitializer#onInitialize()；client → BrushClientModInitializer#onInitializeClient()；server → BrushDedicatedServerModInitializer。

初始化期早于 Main.main，不得假定任何游戏状态已就绪，也不得触碰 BuiltInRegistries。这是"注册期"：注册 L2 事件监听器，游戏交互走监听器。

失败可读：依赖缺失 / 循环 / 版本不符

失败语义是 fail-fast + 一次列全：所有问题先汇总成报告块打印，再抛 IOException 中止启动 —— 一个 mod 都不实例化，不抛裸异常、不静默跳过。循环依赖给出真实环路径（a -> b -> a），不是笼统"有环"。

[brush] MOD LOADING FAILED -- 2 problem(s) (<工作目录>\brush-mods, 3 jar(s)):
[brush]   - bad-nojson.jar: missing brush.mod.json at jar root (only Brush mods belong in brush-mods/; Fabric/NeoForge mods are loaded by their own loader)
[brush]   - mod 'example' requires 'brush' >=99.0.0, found 26.10.1
[brush] no mods were instantiated; aborting launch before the game starts
[brush] FATAL: mod loading failed: 2 problem(s); no mods were instantiated (details in log)

上引为实测原样；其中 brush.mod.json 与 mod id 已按现行命名改写。入口类层面的失败另有专句，例如 mod 'x': entry class Foo must declare a public no-arg constructor、... must implement org.abstruck.brush.api.BrushModInitializer (entrypoint interface contract)。

读 ModBootstrap 的加载报告

[brush] --- mod loading (P3) ---
[brush] mod dir: <工作目录>\brush-mods (0 jar(s))
[brush] runtime kind: BRUSH (bridge org.abstruck.brush.transform.StandaloneBridge, loader org.abstruck.brush.launch.BrushClassLoader)
[brush]   order: brush-api -> example
[brush]   loaded: brush-api 1.0.0 entry=org.abstruck.brush.api.impl.BrushApiMod
[brush] mod loading complete -- mods: 2 loaded (brush-api 1.0.0, example 1.0.0)
[brush] (loader version 26.10.1, game version 26.1.2)

逐行含义：mod dir = 本次扫描的绝对目录与 jar 数；runtime kind = 判定出的运行时与它选中的 RuntimeBridge 及父类加载器；order: = 依赖拓扑序；loaded: = 每个入口一行；mod loading complete = 摘要；最后一行给出加载器版本与游戏版本。零 mod 时摘要为 mods: none found in <dir>。

加载器自身也是列表里的一个 mod

Brush 本体的元数据同样写在 jar 根 brush.mod.json：

{
  "id": "brush",
  "name": "Brush",
  "version": "${version}",
  "description": "The Brush mod loader itself",
  "icon": "assets/brush/textures/gui/icon.png"
}

与普通 mod 的两点差异：① 不跑结构校验与依赖检查；② 不进 loadedMods() / 加载报告 / 归账口径。消费者是 ModBootstrap.loaderMetadata()：依赖解析中 brush id 的比对对象、模组列表的自身条目、以及默认图标路径。元数据缺失或畸形时 loaderVersion() 回退 "unknown"。

已加载 mod 列表在 UI 里的位置

标题界面会挂一枚 20×20 的 Mods 图标按钮。点它打开 ui.ModsScreen：卡片网格展示 Brush 自身条目 + ModBootstrap.modEntries()，点击卡片原地展开为整行详情条。头部副标题给出 Brush <版本> | Minecraft <版本> | runtime: <vanilla|fabric|neoforge> | N brush mod(s)。界面细节见 资源、数据与界面。
