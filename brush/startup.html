启动管线与自举

Brush 不依赖任何第三方启动器：自己解析 version json、装配库与 natives、下载 assets，再用自研 ClassLoader 在本进程内加载 Minecraft 并反射调用入口。本页讲清全流程、五个自举/构建命令各自做什么、以及「没有 vanilla jar 也能先自举」的结构原因。

全流程一览

  1. 版本元数据：GET version manifest → 在版本条目中按 id 找到目标 → 用该条目给出的 url + sha1 拉取 version json → 解析 libraries（name / rules / natives / extract.exclude）、assetIndex、arguments.game、arguments.jvm、arguments.default-user-jvm。
  2. 依赖装配：按 rules 过滤 → classifier 修正（x64）→ 按 version json 给定的 URL 下载全部适用库→ 解压 natives。
  3. assets 装配：独立步骤，索引 + 全部对象，内容寻址布局。
  4. 启动：校验本地 client jar → 装配参数 → 构造 BrushClassLoader → 注册注入管线 → 最早锚点统一引导→ 反射调用入口类。
全流程唯一硬编码 URL是 manifest 入口 https://piston-meta.mojang.com/mc/game/version_manifest_v2.json —— 它是信任根、无上游可提供；version json 与库的 URL 一律取自元数据。26.1.2 起链条中已无 remap 步骤。

依赖装配的关键决策

必须在 rules 之外再按 classifier 筛一次

26.1.2 的库 rules 只写 os.name=windows，x64 / x86 / arm64 三变体全部通过过滤。因此按名称第 4 段再筛：保留无 classifier 或 natives-windows，剔除 16 条 natives-windows-x86 / -arm64，每条都打印登记。

URL 一律取元数据，不拼主机名

26.1.2 实测：59 个保留库的 URL 主机全部是 libraries.minecraft.net，而 client jar 来自 piston-data.mojang.com ——「拼主机名」是错误做法。

natives 解压 + 保留 jar 在 classpath

默认排除前缀 META-INF/；实测排除的 38 个条目全部是 META-INF/*，无任何 DLL 被排除，最终写入 10 个条目 = 9 个 DLL + 1 个许可文件。

LWJGL 从 jar 内自行提取

native jar 内载荷位于嵌套路径 windows/x64/org/lwjgl/<模块>/<name>.dll；version json 的 -Dorg.lwjgl.system.SharedLibraryExtractPath 表明运行期提取是主路径，因此 natives jar 必须留在 classpath 上。

启动流程（Brush.run）

实际执行序：

  1. 读 version json；校验 Java 版本 ≥ javaVersion.majorVersion。
  2. 校验本地 client jar 存在且 sha1 / size 与 downloads.client 一致 —— 不一致即拒绝启动；vanilla 磁盘文件只读。
  3. 库装配；按 logging.client.file 的实测 argument 模板设置 log4j 系统属性，形态不符即报错、不猜。
  4. arguments.jvm / arguments.default-user-jvm / arguments.game 分别处理：可用的 -D 经 System.setProperty 在类加载前设置；game 参数经 rules 过滤 + 占位符替换。
  5. 构造 BrushClassLoader，设为主线程 ContextClassLoader，并校验入口类条目存在于 classpath。
  6. 注册注入管线，随后执行最早锚点统一引导。
  7. 反射调用入口类的 main(String[])；返回后 System.exit(code)，避免残留线程拖住 JVM。

BrushClassLoader 的四条设计约束：parent 为平台类加载器、registerAsParallelCapable()、可插入 ClassTransformer 链、逐类日志见证。

为什么是进程内启动而不是 spawn 子 JVM：注入层要求「在类首次加载前完成注入」，这只有由我们的 ClassLoader 亲自加载 MC 类才能做到。代价如实登记：-cp 不设置；纯 JVM 旗标进程内无法在运行中追加，日志打印 skipped —— 26.1.2 新增的 --sun-misc-unsafe-memory-access=allow 与 --enable-native-access=ALL-UNNAMED 已在 runClient 任务的 jvmArgs 中直传本 JVM。

五个自举 / 构建命令

命令做什么幂等与校验
gradlew.bat metadata拉 manifest → version json；客户端 jar 缺失则下载，存在则交叉核验（sha1 + size）缓存命中即跳过；校验失败即报错停止
gradlew.bat libraries下载全部 applicable 库并解压到 cache/natives/；dependsOn metadata逐件 sha1 / size 校验；已就位即命中缓存
gradlew.bat assets下载 asset index 与全部对象到 cache/assets；dependsOn metadata内容寻址，已存在的对象跳过
gradlew.bat bootstrap可选的一次性备齐：metadata + libraries + assets —— 构建已自动做 metadata，这一步是为了连 assets 一起备好、省掉首次运行时的等待三个子任务全部幂等，可重复执行
gradlew.bat installNeoForge下载官方 NeoForge 安装器并安装到缓存；只装不启动装完即退出；三类完成判据齐全即跳过安装器
为什么自举能先于编译跑：P1 启动器侧不引用 MC 类型，已被拆成独立的 bootstrap 源集 —— 下载任务只需要 JDK + gson/log4j。这解掉了「没有 jar ⇒ 编译不过 ⇒ 下不了 jar」的死锁。2026-10-16 起 metadata 由构建自动触发，所以这个死锁连「手动第一步」都不再需要 —— bootstrap 只剩「连 assets 一起备好」这种锦上添花的作用。想关掉自动自举传 -Pbrush.autoBootstrap=false，那时缺件仍可读失败、不会静默跳过。
前置：构建 JDK 不写死路径。各 gradle.properties 里已删除写死的 org.gradle.java.home=<本机 JDK 路径>，改为 org.gradle.java.installations.fromEnv=JDK25_HOME —— 只写环境变量名、不含任何绝对路径；各 settings.gradle 挂了 pluginManagement与 org.gradle.toolchains.foojay-resolver-convention 0.7.0，build.gradle 的 java { toolchain { languageVersion = JavaLanguageVersion.of(25) } } 不变 ⇒ 本机没有 JDK 25 时 Gradle 会自动把它下到 Gradle 缓存。JDK 装在 Gradle 不自动扫描的位置时：设环境变量 JDK25_HOME 指向它；临时指定用 -Dorg.gradle.java.home=<JDK 25 路径>。四处项目 gradlew help 实测全部 BUILD SUCCESSFUL（10–17 s）；本机实测时用 -Dorg.gradle.java.home=… 显式指定，而仓库里已无任何绝对路径。
IDEA 用户的连带提示：打开项目时 IDE 可能报「找到无效的 Gradle JDK 配置 / Invalid Gradle JDK configuration」。原因：IDEA 的 Gradle JDK 原先是特殊值 #GRADLE_JAVA_HOME，而那一行已按上面的修订删除 ⇒ 这个引用悬空了。这是 IDE 侧设置，与仓库 / 构建无关 —— 命令行 gradlew 走 toolchain，完全不受影响。两个做法任选：① 在 Settings → Build, Execution, Deployment → Build Tools → Gradle → Gradle JDK 里显式选中本机的 JDK 25；② 把 .idea/gradle.xml 的 gradleJvm 改成具体的 JDK 名。改完需要 Reload Gradle Project才生效。另：本机已设环境变量 JDK25_HOME 指向本机 JDK 25，因此命令行侧四个项目只靠该变量即可构建成功，且 Gradle 自己的 jdks 缓存目录下没有下载任何 JDK。

实测规模：assets 4750 个对象 / 457.7 MB + 库 59 个 / 65.1 MB + natives 10 个 + 客户端 jar 38.1 MB，整条约 2 分 26 秒，assets 最耗时。只跑 S1 的话，installNeoForge 可以跳过 —— 它只在编译 Brush API 或跑宿主运行时才需要。

离线、续跑与断点语义

  • 下载先写临时文件（.part），sha1 / size 校验通过后才落盘。
  • 有界重试：单次 fetch 最多 3 次尝试，退避 1 秒 × 尝试次数；超过即抛异常，绝不吞错。
  • 可续跑：再次执行同一命令时，已就位且校验通过的文件被跳过，只补缺的 —— 中断后重跑即可继续，不需要清目录。assets 因为内容寻址，天然如此。
  • 强制刷新：三个入口程序各自支持 --refresh 参数。发行版的 Gradle 任务未透传该参数，因此 gradlew.bat metadata --refresh 这种写法在本发行版下未验证。
  • 离线首装：-Pbrush.neoforgeInstaller=<path> 给本机 NeoForge 安装器副本时直接用本机文件，装不上时不再只能干等超时；不传则从 maven.neoforged.net 下载，sha1 仍校验。

属性覆盖表

-Pbrush.vanillaJar=
vanilla 26.1.2 客户端 jar。默认 <gradle 用户目录>/caches/brush/<mcVersion>/<mcVersion>.jar —— 用户级 Gradle 缓存，不在项目根，多项目共享同一份。
-Pbrush.cache=
MC 缓存目录。默认 <gradle 用户目录>/caches/brush/cache/ —— 同上，跨项目共享；传本属性可覆盖到任意位置。
-Pbrush.neoforgeInstaller=
本机 NeoForge 安装器 jar，用于离线首装。默认无。
-PbrushApiJar=
库模组 jar，仅可选的契约 jar 需要。默认按查找顺序：本项目的 libs\brush-api.jar → 兄弟项目 Brush API 的 build\libs\brush-api.jar。

启动日志怎么读

加载器侧日志每行以 [brush] 为前缀。典型开场：

[brush] === Brush launch (P1.5 + P2.2 injection) ===
[brush] version=26.1.2, cache=…, game-dir=…
[brush] client jar verified: …\26.1.2.jar
[brush]   sha1=4e618f09a0c649dde3fdf829df443ce0b8831e65 size=38113927
[brush] libraries: 59 jars, natives dir: …\cache\natives\26.1.2
[brush]   skipped: -cp (classpath is held by BrushClassLoader)
[brush] default-user-jvm: 2/3 group(s) apply (os.versionRange evaluated against 10.0.26200)
[brush] BrushClassLoader active: parent=platform, classpath entries=69 (game libs + MC + 9 injection-stack entries)
[brush] injection pipeline registered as BrushClassLoader transformer #1
[brush] BrushClassLoader defines net.minecraft.client.main.Main   <-- entry class  [main]
日志行含义 / 判据
client jar verified本地 vanilla 本体的 sha1 / size 与 downloads.client 一致；不一致不会走到这里
libraries: N jars, natives dir库装配结果的 classpath 条数与 natives 目录
skipped: -cp / skipped: <flag>进程内形态的如实登记，不是错误
default-user-jvm: k/n group(s) apply仅审计打印；os.versionRange 的取值串同时输出
BrushClassLoader defines <入口类>启动路径经过我们的 ClassLoader 的直接证据
游戏侧 injection points: N, injected vanilla classes: M注入面计数，应与注入面台账一致
游戏侧 hook fired: <事件>派发链触发的见证行
验收结论：全部纹理图集 Created、tick 稳定到 1000+/2000+，即已进入主菜单；全量日志中 [brush] 前缀的 FATAL / ERROR = 0。起始的少量 401 / Realms 报错是离线会话（--accessToken 0）下 vanilla 自身的必然行为。

开发形态的如实边界

  • 离线身份固定为用户名 Dev + 固定 UUID + userType=msa、accessToken 0：可复现，但服务端鉴权必然失败，只能停留在离线模式。
  • 入口类全名取自 version json，不硬编码；26.1.2 未混淆，net.minecraft.client.main.Main 即运行时名，无任何映射环节。
  • 未做：多实例隔离、崩溃自动诊断、启动性能优化。
