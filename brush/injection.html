注入层

注入层在类首次加载前改写 vanilla 字节码，并在每个目标方法上只织入一条 Dispatcher.fire(...) 静态调用。它由 sponge-mixin与 MixinExtras 承担，经自研 BrushMixinService 接进 Brush 自己的 ClassLoader。指令之后发生的事见 派发层与事件，形态约束见 最小改动原则与禁止清单。

为什么必须「类加载期改写」

Java 方法调用的语义在类加载时即固定：调用点编译为 invokevirtual / invokestatic，目标已解析，运行时没有可插手的中间环节。

机制能拿 / 能改入参为何不可用
JVMTI MethodEntry否 / 否每次方法调用都触发同步回调，VM 退出大量 JIT 优化路径
JDI / 调试器断点能 / 否须跑在调试模式；setValue 只对挂起线程有效
JFR / AsyncGetCallTrace否 / 否只能观测
动态代理 Proxy仅接口 / 否vanilla 不给替换实现的机会

决定性反证：连 Arthas 也是靠字节码织入拿参数。 它的 watch 走 retransformClasses 重定义目标类，再用 ASM 往方法体里织入 AdviceListener 调用，由织入的字节码把参数回传 —— 不是运行时监控。这是本项目对外部进程 / 外部监控方案的评估结论。

Mixin 本来就是运行时变换。 它跑在 Java Agent 之上，于类加载时在内存中改写字节码，磁盘 jar 一个字节没动；所谓「静态」仅指注入点写死在代码里。真正的痛点是「加一个 hook 就要重新 transform，还容易和别人冲突」，薄注入 + 运行时派发正是对它的解法。

为什么必须抢在「首次加载前」？retransformClasses 不能增删方法 / 字段、不能改签名 / 继承，只能改方法体；ClassFileLoadHook能力最全。这条限制使 load-time 成为唯一完整路线，也是 Fabric / Mixin 的选择。

服务栈怎么接进自研 ClassLoader

硬约束：注入栈必须与游戏类同处一个类加载器 —— 被注入的 vanilla 字节码会引用注入点两侧的类，跨类加载器会产生类型身份错位。

Brush（app 侧：只做装配）
  │  ① new BrushClassLoader(urls = 库 + MC 产物 + mixin/mixinextras/asm/本工程类与资源)
  │  ② 反射 Class.forName("org.abstruck.brush.transform.TransformBootstrap", true, loader)
  │  ③ 经 JDK 类型桥接拿到游戏侧 transformer 函数
  │  ④ 注册为 BrushClassLoader 的 ClassTransformer
  ▼
BrushClassLoader（游戏侧）
   findClass ── bytes ──► MixinTransformer.transformClassBytes(name, name, bytes)
  ▼
net.minecraft.client.main.Main（反射调用）

app 侧与游戏侧不共享任何自定义类型身份：交界只有 JDK 类型 BiFunction<String,byte[],byte[]>。

  • BrushMixinService 是必需件：sponge-mixin 的 jar 只注册 LaunchWrapper / ModLauncher 两个 IMixinService，没有通用服务。本类 extends MixinServiceAbstract，补齐剩余抽象方法并实现四个子接口；经工厂创建活动 IMixinTransformer。Fabric 的 Knot 走同一条路 —— 取舍依据见该服务的 javadoc。
  • BrushGlobalPropertyService 是强制件：mixin 的 GlobalProperties 无可用 provider 时 initPropertyService() 直接抛 ServiceNotAvailableError，而 MixinBootstrap 启动路径立即触碰；自带两个 provider 分别依赖 LaunchWrapper / ModLauncher 类。实现为 map-backed，按对象引用原样存取 —— MixinExtras 的 Blackboard 用 new Object[1] 值容器惯用法，复制值会坏。
  • standalone 守卫：BrushMixinService.isValid() 仅当系统属性 brush.standalone=true 时返回 true，而该属性只由 TransformBootstrap.install() 设置 —— S2/S3 下宿主的引导路径不会设置它，宿主因此跳过我们的服务。
  • classpath 顺序是正确性前提：S1 扫描会看到三个候选，而 ServiceLoader.hasNextService 只捕获 NoSuchMethodException，其余 Throwable原样上抛；LaunchWrapper 服务的构造器需要 S1 下不存在的 net.minecraft.launchwrapper.LaunchClassLoader。故我方条目必须排在 sponge-mixin jar 之前，这条顺序已固化在 build.gradle 的运行任务里并就地注释。

TransformBootstrap：引导顺序与快速排除

install() 的顺序即契约，不可换：

  1. setProperty("brush.standalone","true") —— 必须是第一条语句：下一行 MixinBootstrap.init() 就会实例化我们的服务并立即调用 isValid()。
  2. MixinBootstrap.init() —— 注册子系统、offer MixinTransformer.Factory、初始化环境并下发 phaseConsumer。
  3. createTransformer() —— 取工厂创建活动 transformer。
  4. MixinExtrasBootstrap.init() —— 必须晚于第 3 步：其内部访问「活动 transformer」，未创建会空指针。
  5. setSide(CLIENT) —— 无平台 agent 时 getSideName() 为 UNKNOWN，显式设为客户端以启用 side stripping 语义。
  6. gotoDefaultPhase() —— gotoPhase 为包私有，宿主唯一合法推进通道是 wire() 保存的 phaseConsumer。
  7. Mixins.addConfiguration("brush.mixins.json") 并复核注册结果。
  8. CoreHooks.install() —— 注册核心监听器，至此派发表可用。
配置注册必须复核。 Mixins.createConfiguration 在解析失败时只记一条 ERROR 就丢弃配置 —— 不复核会表现为「启动正常、日志干净、hook 全不存在」。MixinConfigRegistry.registerAndVerify 因此确认新配置确实入了待选队列，否则硬失败。

引导前的一次「提前触碰」：install() 开头先调一次 FastExclusion.enabled()，把该嵌套类定型。否则管线回调内首次引用它 → 经 BrushClassLoader.findClass 重入回调 → 无限递归（StackOverflowError），且递归发生在放行前缀判定之前。此刻安全：Brush 在 install() 返回后才注册 transformer，findClass 尚未触达管线。

快速排除（FastExclusion）：启动期经本加载器定义的类数以万计，绝大多数是纯库 / JDK 类，不可能含我们的注入点。管线在进入 transformClassBytes 前做白名单制前缀判定：

  • 放行：net.minecraft.*、org.abstruck.brush.*、宿主包（net.fabricmc.* / net.neoforged.* / cpw.mods.*）、mixin 与 ASM 工具库，以及所有其余未知命名空间。
  • 排除：java. / javax. / jdk. / sun. / com.sun. / com.google.gson. / com.google.common. / com.mojang. / io.netty. / org.apache.logging. / org.lwjgl. / it.unimi.dsi. / org.slf4j. / kotlin.。
  • 开关：-Dbrush.fast.exclusion=false 整体关闭，全部类照送管线，零行为变化；这是加载期短路，不改 footprint。

required / defaultRequire
required: true + defaultRequire: 1 —— 见下节硬失败语义。
compatibilityLevel
JAVA_25：26.1.2 类文件主版本 69（Java 25），所用 sponge-mixin 0.17.4 的 CompatibilityLevel 枚举含 JAVA_25。
mixins 段
共同目标（server.Bootstrap / BuiltInRegistries / PackRepository / MinecraftServer / CrashReport）。
client 段
目标全在 net.minecraft.client.* 的类。MixinConfig.prepare() 按 env.getSide() 备选数组（CLIENT → client）；setSide(Side.CLIENT) 与 addConfiguration 共用同一 env 实例，故三运行时 client 段均被备选。
accessor / invoker
包内的 ScreenAccess / CreativeScreenAccess / KeyboardAccess / MouseAccess 只产生访问桥接方法，不产生注入指令、不计入被注入类。
无 refmap
三运行时统一官方名，注入点定义一套即可，配置永不声明 refmap 键。库模组 brush-api 用自己的 mixin 配置，经 brush.mod.json 的 mixins 字段注册。

注入器选择表：可链式 vs 不可链式

「可链式」= 多个注入器作用于同一位置时能否叠加共存 —— 这是 S2/S3 能否成立的技术前提。

注入器可链式说明
@Overwrite否完全替换方法体、丢弃原实现，破坏同一方法上的一切 —— 本项目禁止
@Redirect / @ModifyConstant否同一目标只能重定向一次
@Inject(HEAD) + ci.cancel()否会阻止其他注入运行，非必要不要用
@Inject是可堆叠，最安全，首选
@ModifyExpressionValue / @ModifyReturnValue / @WrapOperation / @WrapWithCondition是MixinExtras 提供
@WrapMethod是MixinExtras 提供，@Overwrite 的可链式替代；多个 mod 可依次包装同一方法形成调用链

注入面台账里的真实分布正是这张表的结果：多数点是 @Inject，少数用 MixinExtras 包装类注入器。

一条实测硬限制： 键位注册首选的 @WrapOperation 包 PUTFIELD 撞 JVM 限制 —— IllegalAccessError: Update to non-static final field … attempted from a different method (mixinextras$bridge$…)：非静态 final 字段只准在初始化它的方法内写，而字段写包装必经桥方法。故对 final 实例字段的字段写包装一律不可行。

require=1 的硬失败语义

所有 hook 默认 require = 1，配置声明 required: true / defaultRequire: 1：启动期校验全部注入点命中，未命中即中止启动并指明是哪个 hook，不允许 required=false 静默降级。

它针对的是形态 A：别人的 @Overwrite 若先于我们的 @Inject 施加，方法体已被换掉、注入点可能不复存在，require=1 会报 Critical injection failure 并可被捕获；required=false 则静默跳过 —— 那是最危险的做法。日志里 failed injection check … (0/1) succeeded 的典型含义是「找到了，但被别的东西抢先 / 改变了」。

形态 B由启动期扫描并告警捕获，priority 顺序控制是第二层 —— 三层防御的完整口径属项目纪律的《注入共存与冲突防御》一节。

一个真实注入点剖析：CrashReport#getDetails

@Mixin(targets = "net.minecraft.CrashReport")
public abstract class CrashReportMixin {

    @Inject(method = "getDetails(Ljava/lang/StringBuilder;)V", at = @At("TAIL"), require = 1)
    private void brush$appendBrushSection(StringBuilder builder, CallbackInfo callback) {
        Dispatcher.fire(HookEvents.CRASH_REPORT_DETAILS, builder);
    }
}
为什么是这个方法
getDetails(StringBuilder) 是 26.1.2 里报告正文的唯一组装点。TAIL 处追加即可把 Brush 段写进用户看到的崩溃报告 —— 「混合环境出问题时能自证我们做了什么」的最短路径。
选址档位
TAIL 属选址纪律的第 2 档首选（HEAD / TAIL / RETURN）：只依赖方法存在，不依赖方法内部结构；避开更深的 INVOKE 与 CONSTANT / 高 ordinal 这类脆弱定位。
织入了什么
恰好 1 条 Dispatcher.fire(...) 调用指令；不改控制流、不改返回值、不动 vanilla 类结构。目标是实例方法，handler 同为实例；targets= 用字符串而非类字面量，使配置解析期不需要加载 MC 类型。
共存性
@Inject(TAIL) 可链式：不抢占、不替换，其他 mod 在同一方法的注入互不抹除。handler 侧语义是只追加不清空载荷内容（CoreHooks.registerInfoCrashReport）—— 清空 / 重排才是独占式语义，正是可链式纪律要避免的。
冷热
纯冷路径：只有真崩溃且有人取报告正文时才走一次，正常游玩与自检（T1/T2/T3）中恒 0 次，因此计入自检的信息集而非期望集 —— 否则注入命中审计会在三场里误报缺失。
另两个选址样例： ① BootstrapMixin 钉在 Bootstrap.bootStrap() 的 HEAD —— vanilla 最早且必然执行的方法，HEAD 先于同一方法内的 BuiltInRegistries.bootStrap()，使「引导先于内容注册」成为结构性事实；织入指令为 EarlyBoot.onBootstrap()。② MinecraftMixin 在 run()V / tick()V 各一个 HEAD 点：run 非热路径，织入 ClientBoot.onClientRun()；tick 是热路径（约 20 次/秒），无监听器时只是一次 ConcurrentHashMap 查找加空判断。
