常见问题

本页收集构建、自举与运行期最常见的 9 个问题，每条按"问题 → 结论 → 依据"写：结论只写能查到的东西，"未验证"就写未验证。构建与命令全貌见 构建、产物与命令，矩阵与归因工具见 测试矩阵与诊断。

1. 新机器上 gradlew build 报"找不到符号: Identifier / ItemStack"

结论
不是代码坏了，是 vanilla jar 缺失：main 源集引用 MC 类型，没有 jar 编译不过。先 gradlew bootstrap，或显式指路 -Pbrush.vanillaJar=<26.1.2.jar 路径>。
依据
发布版 build.gradle 有独立的 verifyVanillaJar 任务，缺件时抛 vanilla jar not found: … -- run `gradlew.bat bootstrap` first … or pass -Pbrush.vanillaJar=<path>；注释里写明此前不拦会报出成片"找不到符号: Identifier / ItemStack"，让人误以为代码坏了。自举的下载逻辑在独立 bootstrap 源集里、只需要 JDK + gson/log4j，所以"没有 jar ⇒ 编译不过 ⇒ 下不了 jar"的死锁被解掉。

2. gradlew build 报 "Brush API jar not found"

结论
契约 jar brush-api-contract.jar 是可选产物，而它要取库模组里的那部分 api 类。库模组产物缺席时现在会明确跳过并打印原因与出路，不再让 build 失败。要真的产出它，就先构建 ../Brush API，或传 -PbrushApiJar=<brush-api.jar 路径>。
依据
apiContractJar 的 onlyIf 分支：缺件时打印 [brush] apiContractJar SKIPPED -- Brush API jar not found at …; the loader jar does not need it 并给出两条出路；查找顺序 = ① -PbrushApiJar= ② <本项目>/libs/brush-api.jar ③ ../Brush API/build/libs/brush-api.jar。构建脚本注释记录：2026-10-16 修 —— 此前把"另一个项目的产物"设成了必需依赖，只构建加载器时报的就是这句话。

3. installNeoForge / runNeoForgeClient 长时间卡住或超时

结论
大概率是 maven.neoforged.net 不可达。已装好的机器不会再碰网络 —— 安装产物完整时直接跳过下载。三条出路：(a) -Pbrush.cache=<dir> 指向已含 neoforge/install 的缓存；(b) 把准备好的 neoforge/install 目录拷进安装目录；(c) -Pbrush.neoforgeInstaller=<本机 neoforge-26.1.2.114-installer.jar>。
依据
宿主安装器：先判完整性，已装好即打印 NeoForge installation already present -- installer download skipped (offline OK)；旧实现无条件先下载，于是已装好的机器也会白等 3×2 分钟并以 exit 1 收场。下载失败的异常消息里逐条列出上面三条出路。发布版 build.gradle 也把 -Pbrush.neoforgeInstaller= 登记为"离线首装用"。

4. runFabricClient 卡在 "MC libraries: …" 之后

结论
历史上这里是重复下载注入栈，来源站不通时会静默等满 3×2 分钟。现在改为本地已解析的 jar 直接复制，缺件才退化为下载。看到 [brush] staged locally (no download): <文件名> <- <本地路径> 就说明走了新路径。
依据
Fabric 宿主装配器：按 Gradle 通过 --inject-libs= 传入的本地清单先复制再下载，日志行即上句；build.gradle 的注释记录了动机与"给出去之后 harness 直接复制，缺件才退化为下载"。MC 库装配本身命中缓存。

5. IDEA 里 mixin 的 method = "run()V" 报红 "Cannot resolve method … in target class"

结论
这是插件侧限制，不是代码错误：在无映射配置的手写构建下，插件无从解析 mixin 目标。运行时不受影响 —— 字符串与类字面量在字节码层面等价，所以本加载器的 11 个 mixin 统一用字符串目标名。
依据
目标 mixin 类的源码 javadoc：2026-10-16 曾试改类字面量以消 IDEA 报红，实测无效；按用户决定回退为字符串。运行时证据不受影响：require = 1 命中即证明。

6. 两个项目要各下一份 500 MB 缓存吗？缓存放在哪？

结论
不用，也不必放进项目里：MC 侧文件默认落在用户级 Gradle 缓存 —— <gradle 用户目录>/caches/brush/<mcVersion>/<mcVersion>.jar 与 <gradle 用户目录>/caches/brush/cache/**。加载器项目、Brush API 与 MDK 示例项目默认共享同一份下载；项目根不再出现 26.1.2/ 与 cache/。要换位置用 -Pbrush.vanillaJar= / -Pbrush.cache=。
依据
与 Fabric Loom（caches/fabric-loom）、NeoForge neoform 同款做法；两个项目的候选链里都已无兄弟项目回退。迁移实测：三处旧的项目内目录（合计约 2.9 GB）已合并进共享落点后删除；四个项目在新默认下 metadata / libraries / assets / jar 全部 BUILD SUCCESSFUL。run/仍在项目根；libs/ 里的 jar 不动。

7. 我的 mod 放进 mods/ 不生效

结论
约定目录是 brush-mods/，不是宿主的 mods/：S1 用 run/brush-mods，S2/S3 用 run/fabric/brush-mods 与 run/neoforge/brush-mods。这样与宿主 mods/ 双向隔离 —— 宿主加载器不会误扫我们的 mod，我们也不会误扫宿主的。
依据
项目设计约定与开发速查表的"目录隔离"行；BrushProperties.GAME_DIR javadoc 写明"mods 目录 = 本属性值 + /brush-mods"。另外注意：Brush 的启动任务会管理 run/brush-mods/，验证第三方 mod 请用独立工程与独立 run 目录，避免被清。

8. 为什么发布版没有 runSelftest / compatTest？

结论
有意精简：发布树只保留"产出本体 + 自举运行资产"。T1–T4、实机探针、夹具链与单测、自检源码都留在含测试装置的完整开发树里；需要矩阵时用那一份。
依据
发布版 build.gradle 头部逐项列出已移除的测试性运行配置（runSelftest / runFabricSelftest / runNeoForgeSelftest / footprintCheck / compatTest* / modTest / runRealityProbe* / runExampleClient* / seed*RealityWorld / generateRealityDriver* / archive*Log）与测试源集；runClient / runFabricClient / runNeoForgeClient 保留。发布说明同样登记"已移除的测试/开发装置"与"等价性核验：精简后本体 jar 与完整开发树的同源产物逐条目零差异"。细节见 测试矩阵与诊断 末节。

9. 能不能把 Fabric 和 NeoForge 的 mod 装在同一个实例里？

结论
Brush 明确不做。不存在两个 loader 平起平坐的并列共存：一个实例只能装一个 loader。Fabric mod 与 Neo mod 要同场，本质是"一个宿主 + 一个翻译层"的移植工程，工作量与本项目同级。
依据
项目已拍板的运行模式结论：Fabric 与 NeoForge 互斥；唯一成功的跨生态先例 Sinytra Connector 的真实机制是 NeoForge 当唯一宿主、把 Fabric mod 翻译/适配，并依赖 Forgified Fabric API，兼容性逐 mod 三档判定；反向方案 Kilt 作者自称 very experimental。场景表里 S4 一栏即"明确不做"。Brush 要做的是 S2 / S3 的叠加共存：宿主生态的 mod 由宿主自己加载，我们只保证两边在同一 JVM 里不打架。
