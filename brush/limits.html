最小改动原则与禁止清单

「改得少」不是审美偏好，而是 S2 / S3 能否成立的技术前提：footprint 越小，与宿主及其他 mod 撞车的概率越低。页面给出量化上限表、禁止清单、允许的替代方案、footprint 台账与四面一致性闸门（T4）的工作方式、新增注入点的流程，以及已废弃方案的清单。机制侧见 注入层与 派发层与事件，闸门的运行方式见 测试矩阵与诊断。

为什么「改得少」是共存的技术前提

混合环境里最糟的结果不是崩溃，而是静默失效：别人的 @Overwrite 把我们的注入抹掉，日志干净、功能消失、无任何报错。

薄注入把风险压到结构上最小：每个 vanilla 方法上我们只占恰好一条指令，撞的是这一条而非 N 条；可链式注入器让多方注入能叠加共存而不是互相替换。而且不必抢地盘 —— 决策逻辑都在派发表里，加删监听器不重新 transform 任何类。这也是「叠加层」定位能自洽的原因。

设计选择的排序是明确的：任何设计决策遇到「改动更少」与「实现更省事」冲突时，一律选前者。这不是建议，是最高设计约束。

禁止清单

禁止项为什么
@Overwrite完全替换方法体、丢弃原实现。形态 A：方法体已被换掉，我们的注入点可能不复存在；形态 B：overwrite 后于我们的注入 → 已织入的代码随方法体一起被抹掉，静默消失、无任何报错
不可链式注入器（@Redirect / @ModifyConstant / @Inject(HEAD)+ci.cancel()）同一目标只能重定向或取消一次 —— 多方注入天然互斥。这三者与 @Overwrite 一样属自研代码与示例 mod 的禁止项，除非先写明为何 MixinExtras 包装类注入器不可用
用 @Unique 给 vanilla 类加字段最隐蔽的污染源：改了类结构、占了名字空间、与其他 mod 的同类做法天然冲突
脆弱定位越深入方法内部越脆弱，vanilla 一重构就失配，还会与其他 mod 抢同一处
未登记的 access widener / access transformer不改字节码，但改变了 vanilla 成员的可见性契约，属于改动面；每条都要登记目标成员、原可见性、改为何、为何必需。不得「顺手」放宽一批成员
NeoForge 侧带 refmap 的 mixin 配置三运行时统一官方名，无需转换；NeoForge 不做 runtime refmap detection，配了会坏
任何形式的重映射26.1 起游戏未混淆，官方名即运行时名；Intermediary / Yarn 已在 1.21.11 后停止更新
让注入点未命中时静默跳过（required=false）require=1 是捕获形态 A 的唯一手段；静默降级会把「注入没生效」藏成「功能不存在」
声称「外部进程可以运行时劫持方法参数」JVM 没有这种机制，连 Arthas 也是靠字节码织入拿参数。外部监控 / attach 不得作为 hook 的常规实现路径

完整清单另含编造依赖坐标 / 类名 / 数字、未探测就假定路径、未经实测宣称兼容、为让测试变绿而放宽断言等工程纪律项。

footprint 台账与四面一致性（T4）

注入面台账只有一处。它登记的是对 vanilla 的全部改动面—— 能力型 API 拆成第一方库模组后注入点跨 jar 分散，但总数不变，归属由行末 [source=…] 标注。每个注入点登记五个字段：注入点、注入位置、注入器类型、用途、是否热路径。

启动日志必须打印注入点总数与被注入的 vanilla 类数；当前两个数字是 21 点 / 16 类。早期资料写 18 点 / 13 类，以当前台账与基线为准

四个面

FootprintCheck 是纯静态、秒级的闸门，挂进 check，也是兼容测试矩阵的 T4 环节。四面对上才 PASS：

面内容
1. 基线FootprintCheck.BASELINE_POINTS / BASELINE_CLASSES 两个常量。改它 = 一次需要说明的变更，必须与台账、代码镜像同处一份 diff
2. 台账文档台账本身：摘要行与表格逐行自洽，且与代码一致 —— 摘要行与表行的格式即校验接口
3. 代码镜像InjectionLedger.ENTRIES：设计侧数字。跨 jar 仍只有一份镜像 —— 两份必然漂移
4. 真实注入指令按 brush.mixins.json列出的全部 mixin 类，用 ASM 逐个读类文件：注入器注解方法数求和、@Mixin 目标类名取并集。它最接近「实际有几个注入点」，专门捕获「加了 @Inject 但没登记台账」
  • 为什么第 4 面用 ASM 而不是反射：@Mixin 是 RetentionPolicy.CLASS，运行期反射不可见；读类文件对 @Mixin 与 @Inject 一视同仁，且与 mixin 自己消费注解的方式同源。
  • 计数口径：注入点 = 被注入器注解直接标注的方法数；@At / @Slice 是成员注解、不计。契约是每注入器方法恰一个注入点。
  • 被注入类口径：只算注入器承载类的 @Mixin 目标并集；accessor / invoker 承载类只产生访问桥接方法，不计入。这条口径 2026-10-10 经用户批准修订。
  • 配置驱动枚举：mixin 只会施加配置里列出的类，配置即权威清单 —— 新增 mixin 类时检查自动纳入，不需硬编码类名。
闸门的语义是「变更必须显式登记」，不是「禁止增长」。 2026-10-08 已删除原「注入点总数只减不增」要求。

新增注入点的流程

  1. 评估复用 —— 现有 20 多个点里有没有语义相同或更早的锚点？能复用就零新增。这正是派发器的价值：加订阅不用加锚点。
  2. 选址 —— 生命周期边界 → 方法 HEAD / TAIL / RETURN → 谨慎用 INVOKE → 避免 CONSTANT / 高 ordinal。锚在热路径时必须单独论证并说明性能影响。
  3. 写 mixin —— 可链式注入器、require = 1、每点 1 条指令、不改控制流与类结构；目标名用官方名并人工复核。
  4. 登记 —— 同一次变更里改三处：注入面台账的表行与摘要行 + 变更记录、InjectionLedger.ENTRIES 镜像条目、四面校验基线的两个常量。库模组提供的点另在 brush-api.mixins.json 登记。
  5. 跑门禁 —— gradlew footprintCheck必须 PASS；未登记漂移 = FAIL 并列出问题清单。
  6. 三运行时实测确认 —— 「新增 / 修改注入点时仍必须实测确认，不得假定」：宿主改过的字节码可能让注入点失配。每个阶段汇报都要附 footprint 台账的变化。
