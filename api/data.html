数据与资源

本页覆盖 Brush API 的数据与资源面：自定义数据包注册表、 DATA_LOADED / DATA_RELOADED 两个数据生命周期事件、资源包仓库事件 PACKS_REGISTERED，以及客户端资源约定与 mod 元数据查询 （BrushMods）。三运行时（S1 / S2 / S3）共用同一份实现与同一套语义。

1. 全貌：一次自定义数据包注册表的生命周期

阶段谁做入口时机
① 登记注册表modBrushDataRegistries.register(ResourceKey, Codec) 内容注册窗口或之后任意时刻；bootstrap 期不得调用
② 放条目 JSONmodjar 内 data/<包ns>/<键路径>/*.json 随资源栈接入
③ 装载Brushregistry.DataRegistryEngine 集成服务器构造完成 / 数据重载完成 —— 先装载后派发
④ 读取modBrushRegistry.dataRegistry(key) 装载完成后任意时机
一句话记住它和内容注册的区别。 物品 / 方块那类走的是 vanilla 注册表—— 必须在唯一的合法窗口注册，晚了就被 freeze 挡住。 数据包注册表不经 vanilla 注册表：Brush 自有一个引擎和一份 RegistryAccess， 所以登记没有窗口约束、装载时机由 Brush 决定。代价是vanilla 侧看不到它。 出处：BrushDataRegistries / BrushRegistry#dataRegistry javadoc、设计文档记载。

2. 登记：BrushDataRegistries

2.1 签名（以源码为准）

public static <T> void register(ResourceKey<? extends Registry<T>> key, Codec<T> codec)
key
注册表键。要求是静态常量单实例 —— ResourceKey 在 26.1.2 为身份相等 登记、读取与 codec 里引用该注册表 必须用同一个键实例；不同实例即使标识符相同也不会命中。
codec
条目 codec。建议只用 JDK 类型做字段， 避免「装载期 codec 内嵌 vanilla 注册表查找」这一已知边界。
抛出
IllegalStateException：无 mod 上下文，或标识符与已登记注册表重复。NullPointerException：key / codec 为 null。

2.2 完整示例

下面的代码能编译，也是 MDK 里那个配套示例 mod 的实际形态：

// DemoMaterial
import com.mojang.serialization.Codec;
import com.mojang.serialization.codecs.RecordCodecBuilder;

public record DemoMaterial(String displayName, int tier) {
    public static final Codec<DemoMaterial> CODEC = RecordCodecBuilder.create(instance -> instance.group(
            Codec.STRING.fieldOf("displayName").forGetter(DemoMaterial::displayName),
            Codec.INT.fieldOf("tier").forGetter(DemoMaterial::tier)
    ).apply(instance, DemoMaterial::new));
}

// 入口类（implements BrushModInitializer）里：
import net.minecraft.core.Registry;
import net.minecraft.resources.Identifier;
import net.minecraft.resources.ResourceKey;

import org.abstruck.brush.api.BrushDataRegistries;
import org.abstruck.brush.api.BrushEvents;
import org.abstruck.brush.api.BrushRegistry;

static final ResourceKey<Registry<DemoMaterial>> DEMO_MATERIAL =
        ResourceKey.createRegistryKey(Identifier.fromNamespaceAndPath("example", "demo_material"));

@Override
public void onInitialize() {
    BrushEvents.CONTENT_REGISTRATION.register(event -> {
        // 内容注册窗口内登记（也可放在之后的任意时机 —— 迟登记下次装载生效）
        BrushDataRegistries.register(DEMO_MATERIAL, DemoMaterial.CODEC);
    });

    BrushEvents.DATA_LOADED.register(server -> {
        // 装载先于派发 —— 这里读到的已是最新视图
        BrushRegistry.dataRegistry(DEMO_MATERIAL).ifPresent(registry -> {
            registry.keySet().forEach(id -> {
                DemoMaterial material = registry.getValue(id);
                // ...
            });
        });
    });
}
bootstrap 期不得调用 BrushDataRegistries。 该类引用 MC 类型，必须遵守与 BrushRegistry 相同的类加载纪律： 只能被「注册窗口内会执行的代码」引用—— 不得在引导期路径的方法体或字段初始化器里引用它。 出处：BrushDataRegistries javadoc、BrushRegistry javadoc「类加载纪律」节。

3. 条目 JSON 放哪：两种布局

条目文件放在 data/<数据包命名空间>/<键路径>/*.json。关键在于 条目 id 的命名空间来自数据包目录，与注册表键的命名空间无关。

布局路径模板本项目夹具实例说明
vanilla 机制布局 data/<包ns>/<键路径>/<名>.json data/example/demo_material/ruby.json 三运行时通用
宿主命名空间布局 data/<包ns>/<注册表ns>/<键路径>/<名>.json data/example/example/demo_material/steel.json S2 / S3 对非 minecraft 注册表原生就是这个形状；由桥接层读取

同名 id 同时存在于两种布局时，以 vanilla 机制布局的文件优先。上面的两条夹具路径 反序列化的条目 id 分别是 example:ruby 与 example:steel。

为什么需要桥接层。 26.1.2 的 vanilla 把条目读在 data/<包ns>/<键路径>/；但 Fabric 的 RegistriesMixin 与 NeoForge 的补丁会给非 minecraft 注册表前置一段注册表命名空间 —— 两个宿主独立同向。 Brush 的 registry.BridgingResourceManager 在执行期按宿主实况布局组装层栈， 于是两种布局在两个宿主下都能读到，且对 vanilla 零改动、零注入面。 实证链见实测日志。

标签目录（tagsDirPath）不桥接：数据包注册表的标签需按宿主原生布局放置。 本轮无标签夹具，属未验证项。

4. 读取：BrushRegistry.dataRegistry(key)

public static <T> Optional<Registry<T>> dataRegistry(ResourceKey<? extends Registry<T>> key)

返回最近一次成功装载的只读视图：未装载 / 未知键时为空。 无窗口约束、无 mod 上下文约束，任意时机可调用。

多包合并且同名条目冲突时，包列表里靠后的包优先级更高。 这条方向是实测钉死的：早期 javadoc 曾写「先者优先」并声称有 javap 实证，方向是错的 —— 由自动断言首轮判红暴露后按实测订正，现已纳入自动断言。实测两条对照： [overlayA, overlayB, mod] 取到 overlayB 的值； [overlay, mod] 取到 mod 的值。 出处：设计文档记载与实测结论台账。

5. 数据生命周期事件：DATA_LOADED vs DATA_RELOADED

DATA_LOADEDDATA_RELOADED
监听器方法onDataLoaded(MinecraftServer server) onDataReloaded(MinecraftServer server, Optional<Throwable> error)
L1 来源MinecraftServer#<init> RETURN（@Inject） MinecraftServer#reloadResources 整方法 @WrapMethod
触发时机集成服务器构造完成 —— server.getResourceManager() 已非空；每服务器实例一次 /reload 或数据包变更触发的 reloadResources future 完成；每次重载一次
线程服务器构造线程 重载 future 的完成线程
载荷语义装载先于派发 —— 监听器读到的就是最新视图 error 为空 = vanilla 重载与 Brush 表重载均成功；非空 = 失败原因
可取消否否
三运行时一致一致

5.1 典型用法

BrushEvents.DATA_LOADED.register(server -> {
    rebuildCache();                     // 世界首次加载：建你的缓存
});

BrushEvents.DATA_RELOADED.register((server, error) -> {
    if (error.isPresent()) {
        // vanilla 重载失败 或 Brush 表重载失败（旧表保留）——
        // 逐键原因在加载器 ERROR 日志里；这里按降级处理，不要抛
        return;
    }
    rebuildCache();                     // 重载成功：按新视图重建缓存
});
两个容易踩的点。
  • DATA_RELOADED 在异步完成线程上。 监听器不得触碰屏幕 / 渲染 / 未同步的游戏状态； 需要主线程语义的工作请转交调度。 另有一条有意偏离并已记录在案：该上下文里重抛的异常会被 CompletableFuture 静默吞掉， 所以引擎在这一处 catch + ERROR，不是静默失败。
  • DATA_LOADED 不要做重活。 它是同步调用，长时间工作会阻塞服务器构造 —— 重活转交异步或后续生命周期事件。

出处：DataLoadedEvent / DataReloadedEvent javadoc、 HookEvents#DATA_LOADED / #DATA_RELOADED javadoc、设计文档记载。

6. 资源：PACKS_REGISTERED 与客户端资源约定

6.1 事件语义

L1 来源
PackRepository#<init> RETURN（0 新增 footprint）—— 在 ModResourcePacks.attach 的 finally 中派发。
触发时机
每个 PackRepository 实例构造完成时：客户端主仓库 1 次 + 世界创建界面的数据包选择仓库若干次。派发条件是「注入点命中」， 不是「挂包成功」—— 命中即派发，含无 mod / 非客户端仓库的情形。
线程
构造该仓库的线程。
可取消
否
三运行时
事件点一致。附带差异： S3 下客户端注册的 flush 落地点推迟到首个 PACKS_REGISTERED。

6.2 S1 会挂自己的内建资源包 —— 这个事件给 mod 什么机会

先把事实说清：

运行时客户端资源仓库服务端数据仓库
S1（brush.standalone=true） 挂 Brush 核心资源包 brush_core + 模组资源包 brush_mods 挂 模组数据包 brush_mod_data
S2 / S3 核心资源包由宿主挂载 brush 制品资产；模组资源包仍由 Brush 挂 同上

于是这个事件给 mod 的机会是「观测与响应」，不是「再挂一个包」：

  • 确认资源栈已就绪。 事件触发时「模组资源包已接入来源集合」，vanilla 随后的 reload() 会把它们纳入发现与选中 —— 这是你能拿到的最早的「我的资源已经进栈」信号。
  • 做与包状态相关的初始化。 注意：此刻是仓库构造完成，初始资源 reload 通常尚未完成 —— 真正读取资源要等资源管理器就绪。
  • 做诊断 / 自证。
  • 该事件不提供「注册一个自定义资源包」的 L2 API —— 本事件是无载荷单例， 只做「通知」；追加资源包来源是加载器自身的行为。
你自己的资源怎么进栈？ 什么都不用做：把资源文件按下面的约定放进 mod jar， 加载器的 omnibus 模组资源包会在仓库构造时把它们接进资源栈。 出处：ModResourcePacks javadoc。

6.3 客户端资源约定

mod jar 内的资源路径就是 vanilla 的资源包路径：

类型路径示例（MDK 示例 mod）
模型 / 材质 / 语言assets/<id>/… assets/example/models/item/ruby.json、assets/example/textures/item/ruby.png、 assets/example/lang/zh_cn.json
方块状态 / 物品定义assets/<id>/blockstates/…、assets/<id>/items/… assets/example/blockstates/ruby_block.json、assets/example/items/ruby_block.json
数据data/<id>/… data/example/recipe/ruby_block.json

「资源在三个运行时都由资源系统提供」的意思是：你不需要为 S1 / S2 / S3 准备三份资源， 也不需要代码分支 —— 上面这些路径在三个运行时都经同一套资源系统（PackRepository → ResourceManager）被发现与读取。S1 与 S2/S3 的差别只在「谁把包挂进去」，mod 侧完全一致。

出处：ModResourcePacks javadoc、设计文档记载与实测结论台账。

7. BrushMods：查询已加载的 mod

7.1 API（签名以源码为准）

方法返回说明
public static List<ModInfo> list()不可变列表 已加载的全部 Brush mod，依赖拓扑序。数据源在实例化任何入口之前就已全量登记 —— 因此在任意 mod 的 onInitialize() 里调用，看到的是本次加载的全部 mod。
public static Optional<ModInfo> find(String id)Optional 按 id 查询；不存在 = 空 Optional。
public static boolean isLoaded(String id)booleanid 是否已加载。
public static String loaderVersion()String 加载器（Brush）版本串 —— 与依赖解析中 brush id 的比对对象同源。
public static String gameVersion()String 游戏版本串；加载器尚未初始化时返回 "unknown"。

元数据视图是一个只读快照 record：

public record ModInfo(String id, String name, String version, String description,
        List<String> authors, Path jar) { }

name 在元数据缺省时回退为 id；description 可为空串； authors 可为空列表；jar 是磁盘路径。

7.2 用法与两个注意点

import org.abstruck.brush.api.BrushMods;

// 在 onInitialize() 里即可用：已是本次加载的全量（含自身）
BrushMods.list().forEach(info ->
        LOGGER.info("[mymod] loaded: " + info.id() + " " + info.version()));

if (BrushMods.isLoaded("brush-api")) {
    // 依赖的库模组在场
}
LOGGER.info("[mymod] loader=" + BrushMods.loaderVersion()
        + ", game=" + BrushMods.gameVersion());
两个注意点。
  • 不含加载器自身。 brush 不在 list() 里—— 加载器版本走 loaderVersion()，游戏版本走 gameVersion()。
  • 零注入点。 纯查询，构建在加载器自身的登记表之上，不触碰任何 vanilla 类，因此天然三运行时一致。 加载失败时进程在中止路径上，本 API 不参与失败语义。

8. 已知边界（如实登记，别误读）

边界含义
对 vanilla 查询不可见 Brush 的数据包注册表装在自己的 RegistryAccess 里，vanilla 侧看不到它 —— 26.1.2 没有服务器侧「数据包注册表可重载」的公开扩展路径。
远端联机不触发 客户端 JVM 没有 MinecraftServer，所以远端多人服务器下 DATA_LOADED / DATA_RELOADED 不触发、dataRegistry(...) 恒为空。集成服务器/ LAN 主机正常。Brush 无 dedicated 运行时。
装载失败不中断世界加载 条目 JSON 坏 → 逐键 ERROR 日志、保留旧视图、事件照发。 mod 侧应经 dataRegistry(...) 空判降级。
标签不桥接 数据包注册表的标签需按宿主原生布局（tagsDirPath）放置 —— 本轮无标签夹具，未验证。
存档目录发现环节 「目录形 PackResources → 引擎装载 → 包序合并」已自动断言； 但 vanilla 从真实存档目录发现 / 挑选玩家数据包这一步仍需真实世界 + 真实存档， 列为人工验证项。
