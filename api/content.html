内容注册

内容注册只能在 BrushEvents.CONTENT_REGISTRATION 的监听器体内执行 —— 那是 vanilla 注册表唯一的合法窗口。本页给出窗口的边界与真实报错、BrushRegistry 的完整公开方法表、创造栏的两条路径，以及一段可编译的注册代码。

一、唯一的注册窗口：不是约定，是硬约束

vanilla 把注册夹在一对守卫之间，两个方向都会失败 —— 报错原文如下：

  • 太早：IllegalArgumentException: Not bootstrapped (called from registry ...)。更早触碰注册表类就会被拦，随后 ExceptionInInitializerError 会污染该类。
  • 太晚：IllegalStateException: Registry is already frozen。

合法窗口 = BuiltInRegistries.bootStrap() 的 HEAD（L1 注入点 registries.bootstrap）。此时 Bootstrap.isBootstrapped 标志已置位、注册表尚未 freeze()。L1 派发链是 mixin → Dispatcher.fire → 你的监听器，三运行时施加同一份 mixin 配置。

频率
每进程恰一次。
触发线程
执行 bootstrap 的线程。实测：S1 为游戏主线程；S2 为 Render 线程；S3 为宿主 bootstrap 线程（pool-9-thread-1）。
插入序
vanilla 的方块 / 物品等内容类已在 Bootstrap 流程前段完成自注册 ⇒ 你的条目追加在 vanilla 条目之后。
异常
监听器异常经 Dispatcher 包装上抛 → 启动快速失败，不会静默。

二、ContentRegistrationEvent 携带什么

答案是：什么都不带。它是无载荷单例（ContentRegistrationEvent.INSTANCE），既没有注册表上下文，也没有"是否客户端"标志。javadoc 明确要求：请勿依赖对象身份做去重或状态存储 —— 需要用闭包或自己的静态字段带状态。

归账归属不来自事件对象，而来自 ModBootstrap 在入口构造期设置的 mod 上下文：Event#register 把该上下文包进 L1 监听器，窗口到达、监听器执行时再恢复 —— 所以 S3 下即使 bootstrap 在别的线程，归属依然正确。

需要"当前是客户端还是专用服务端"时，当前 L2 面没有这个信息。Brush 现有三种运行时（S1/S2/S3）全是客户端，entrypoints.server 只被校验、不被派发。

三、BrushRegistry 公开方法表

类别短名来自注册表标识的路径段（minecraft:item → item），所以泛型核心对任意 Registry<T> 可用，类别扩张零核心改动 —— 便捷形只是糖。

签名用途 / 调用窗口
static <T> T register(Registry<T> registry, Identifier id, T value)泛型注册核心：向任意注册表注册一个值。等价于 Registry.register(registry, ResourceKey.create(registry.key(), id), value)。内容窗口内。
static Item registerItem(Identifier id, Item.Properties properties)注册物品：properties.setId(key) → new Item(props) → 注册。窗口内。
static Item registerItem(Identifier id, Function<Item.Properties, Item> factory)注册自定义 Item 子类；工厂收到已 setId 的 properties。窗口内。
static Block registerBlock(Identifier id, Function<BlockBehaviour.Properties, Block> factory, BlockBehaviour.Properties properties)注册方块 + 同名 BlockItem 配对。窗口内。
static Block registerBlock(Identifier id, Function<BlockBehaviour.Properties, Block> factory, BlockBehaviour.Properties properties, BiFunction<Block, Item.Properties, Item> itemFactory)同上，但配对物品由你生产。工厂返回 null = 失败，不是"无物品"。
static Block registerBlockWithoutItem(Identifier id, Function<BlockBehaviour.Properties, Block> factory, BlockBehaviour.Properties properties)"有方块无物品"的具名入口：不构造物品、不写 Item.BY_BLOCK，但窗口守卫 / 归账 / finalizeBlockStates 与配对形一致。
static <T extends Entity> EntityType<T> registerEntityType(Identifier id, EntityType.Builder<T> builder)实体类型：builder.build(key) + 注册。窗口内。
static <T extends LivingEntity> void registerAttributes(EntityType<T> type, Supplier<AttributeSupplier.Builder> builder)延迟内容组：参数是 supplier，不在现场求值 —— 缓冲到客户端注册 flush 才执行。
static <T extends Mob> void registerSpawnPlacement(EntityType<T> type, SpawnPlacementType placement, Heightmap.Types heightmapType, SpawnPlacements.SpawnPredicate<T> predicate)刷怪放置规则。窗口内。
static <T extends BlockEntity> BlockEntityType<T> registerBlockEntityType(Identifier id, BrushRegistration.BrushBlockEntitySupplier<T> supplier, Block... blocks)方块实体类型；blocks 至少一个。窗口内。
static <M extends AbstractContainerMenu> MenuType<M> registerMenuType(Identifier id, BrushRegistration.BrushMenuSupplier<M> supplier)菜单类型，requiredFeatures 取空集。窗口内。
static <M extends AbstractContainerMenu> MenuType<M> registerMenuType(Identifier id, BrushRegistration.BrushMenuSupplier<M> supplier, FeatureFlagSet requiredFeatures)显式特征门控变体。窗口内。
static <T extends Entity> void registerEntityRenderer(EntityType<? extends T> type, EntityRendererProvider<T> provider)客户端组：写 EntityRenderers 的私有 Map；任意时机可调用，内部缓冲到 CLIENT_REGISTRATION 统一落地；过晚显式拒绝。
static <T extends BlockEntity, S extends BlockEntityRenderState> void registerBlockEntityRenderer(BlockEntityType<? extends T> type, BlockEntityRendererProvider<T, S> provider)方块实体渲染器（26.1.2 为双参 provider）。时机同上。
static <M extends AbstractContainerMenu, S extends Screen & MenuAccess<M>> void registerMenuScreen(MenuType<M> type, BrushRegistration.BrushScreenFactory<M, S> factory)菜单屏幕映射。时机同上。
static <T> Optional<Registry<T>> dataRegistry(ResourceKey<? extends Registry<T>> key)数据包注册表读取。无窗口约束，任意时机可调用；装载前为空。注册表在 Brush 自有 RegistryAccess 中，对 vanilla 服务器注册表查询不可见；远端多人服务器下恒为空。

方块的 finalizeBlockStates 不是可选项：26.1.2 不在 Block 构造时分配 state 的网络 id 与渲染缓存，而是在 Blocks 类初始化末尾对"当时已注册的全部方块"集中补做。我们的注册晚于那个集中点，所以门面替你补 Block.BLOCK_STATE_REGISTRY.add(state) 与 state.initCache()。漏做的实机后果是两个：放置方块的玩家被踢（Can't find id ... IdMapper）与邻居面遮挡查询 NPE。

因此不要用通用形 register(BuiltInRegistries.BLOCK, id, block) 表达"无物品方块" —— 那会漏掉 finalizeBlockStates。用 registerBlockWithoutItem。

四、BrushRegistration 的定位

BrushRegistration 不是注册入口，而是注册辅助函数式接口的容器。存在的理由很具体：26.1.2 的对应 vanilla 参数类型是包私有的，mod 侧连书写都做不到。所以 Brush 暴露收窄到公开类型的等价接口，运行时经 MethodHandles 适配到 vanilla 的包私有形。

接口方法对位的 vanilla 类型
BrushRegistration.BrushMenuSupplier<M>M create(int containerId, Inventory inventory)MenuType$MenuSupplier
BrushRegistration.BrushScreenFactory<M, S>S create(M menu, Inventory inventory, Component title)MenuScreens$ScreenConstructor
BrushRegistration.BrushBlockEntitySupplier<T>T create(BlockPos pos, BlockState state)BlockEntityType$BlockEntitySupplier

签名镜像语义而非 1:1 抄 vanilla，并收窄到公开类型：vanilla 侧包私有签名一变，改的是 registry 包内的桥接，不动这些接口。这些工厂对象在构造期不得触碰游戏状态 —— 它们只在菜单 / 屏幕 / 方块实体被创建时回调。

五、归账与自检里的佐证

每次成功注册都会落进 ContentLedger 并打一行日志：[brush] content: registered <type> <id> (by <modId>)。被拒绝的注册同样归账（recordRejection），并抛带指引的可读异常。自检报告里的行是 content.registered: items=N, blocks=M, tabs=T；退出码位 16 = 内容归账不自洽。

一个容易踩的算术：registerBlock 的配对物品本身就是一条 ITEM 注册表条目。所以示例 mod 注册 1 个物品 + 1 个方块，实测行是 items=2, blocks=1, tabs=0：

[brush] content: registered item example:ruby (by example)
[brush] content: registered block example:ruby_block (by example)
[brush] content: registered item example:ruby_block (by example)   <- BlockItem 配对
[brush] selftest: content.registered: items=2, blocks=1, tabs=0

registerBlockWithoutItem 只记 block 一条 —— 自检报告据此能把"有方块无物品"与"漏配物品"区分开。

六、创造栏：两条路径

vanilla 14 个标签页的 (row, column) 槽位全部占满，而 Bootstrap#bootStrap() 在生产路径上无条件调用 CreativeModeTabs.validate() —— 自注册新标签页会产生重复槽位并直接中止启动。因此 Brush 走两条完全不同的路径：

向原版标签页追加条目注册自有标签页
入口BrushCreativeTabs.entriesOf(Identifier) 或 entriesOf(ResourceKey<CreativeModeTab>)，返回一个 EventBrushCreativeTabs.register(BrushCreativeTab)
落到哪里原版标签页的内容集合，条目出现在标签页末尾不进任何注册表：进 Brush 自维护列表，展示在创造栏左侧的 Brush 侧栏
调用时机订阅与其它事件同一时机须在 onInitializeClient() 的上下文内
每次构建回调是（CreativeTabOutputEvent）是
可否注册进 CREATIVE_MODE_TAB—不可以：BrushRegistry 对该注册表直接拒收，理由与指引写进异常

追加条目：CreativeTabOutputEvent 的时机

L1 来源是 CreativeModeTab#buildContents 的 TAIL（creative.tab.output）。TAIL 时 displayItems 与 displayItemsSearchTab 两个集合都已赋值完毕，所以句柄能对同一个集合实例原位追加。回调发生在每次构建：标签页首建 / 重开创造界面重建 / 搜索刷新批量重建。

不跨构建累积
vanilla 每次构建都重建内容集合，所以对同一构建的重复调用不会累积条目。
同一构建内重复 add
同一 ItemStack 加两次会在标签页内容里产生重复项；搜索页是 Set，自动去重。
写入线程
调用线程 = 触发线程，与 vanilla 生成器写同一集合同线程。

自有页与创造搜索栏：自有页不进注册表，而原版搜索页是在 CreativeModeTabs#buildAllTabContents 的第二趟里由注册表页签聚合而成的 —— 若不做处理，自有页的物品在创造搜索栏里搜不到。 现在核心会在首次注册自有页时装一个内部监听器观察同一钩子： 当被构建的页签是搜索页时，用同一份显示参数重建各自有页、并把它们的 搜索集合并入搜索页 —— 因此 TAB_AND_SEARCH 与 SEARCH_ONLY 的条目 都能搜到，而 TAB_ONLY 的仍只在页签里可见。

CreativeTabEntries 是句柄，只在一次监听器调用内有效：

成员说明
ResourceKey<CreativeModeTab> tab()本次构建的标签页键。
void add(ItemStack stack)追加条目，等同 TAB_AND_SEARCH。
void add(ItemStack stack, Visibility visibility)按可见性追加。
boolean shouldShowOpRestrictedItems()当前显示参数是否放行 OP 限定条目。
FeatureFlagSet enabledFeatures()当前显示参数启用的特征集。
enum VisibilityTAB_AND_SEARCH/ TAB_ONLY / SEARCH_ONLY。

自有标签页：BrushCreativeTab

BrushCreativeTabs.register(BrushCreativeTab
        .builder(Identifier.fromNamespaceAndPath("example", "rubies"))
        .title(Component.translatable("example.tab.rubies"))
        .icon(() -> new ItemStack(MY_ITEM))          // 每次渲染求值：勿在供应商里做重活
        .contents(entries -> entries.add(new ItemStack(MY_ITEM)))
        .build());

三个要素（title / icon / contents）都必需，缺一即构造期 IllegalStateException。title / icon / contents 全部惰性：图标供应商与内容生成器都在游戏就绪后才求值 —— 因此入口构造期注册是安全的。自有页在 S2 下还需为桥页补 Fabric 分页页码，这是宿主特有情形的已知差异。

自有页不调用 vanilla buildContents：Fabric API 对该方法的 TAIL 注入里有一句 getResourceKey(this).orElseThrow(() -> new IllegalStateException("Unregistered creative mode tab"))，未注册页调用它必抛。Brush 改为在公开集合访问面上 clear 后全量重填 —— 三运行时同一代码路径，副作用是 creative.tab.output 不为自有页触发。

七、一段完整的注册代码

物品 + 方块 + 向原版「原材料」页追加条目。这是完整可编译的类：

package com.example.mdk;

import net.minecraft.resources.Identifier;
import net.minecraft.world.item.Item;
import net.minecraft.world.item.ItemStack;
import net.minecraft.world.level.block.Block;
import net.minecraft.world.level.block.state.BlockBehaviour;

import org.abstruck.brush.api.BrushCreativeTabs;
import org.abstruck.brush.api.BrushEvents;
import org.abstruck.brush.api.BrushModInitializer;
import org.abstruck.brush.api.BrushRegistry;
import org.apache.logging.log4j.LogManager;
import org.apache.logging.log4j.Logger;

public final class ExampleContentMod implements BrushModInitializer {

    private static final Logger LOGGER = LogManager.getLogger("mdkexample");

    public static final String MOD_ID = "mdkexample";
    private static final Identifier WAND = Identifier.fromNamespaceAndPath(MOD_ID, "wand");
    private static final Identifier WAND_BLOCK = Identifier.fromNamespaceAndPath(MOD_ID, "wand_block");

    /** 内容窗口内写入、更晚的创造栏构建期读取 —— 跨线程读，故 volatile。 */
    private static volatile Item wand;

    @Override
    public void onInitialize() {
        LOGGER.info("[mdkexample] onInitialize -- 只注册监听器，不碰注册表");

        // ① 内容注册：窗口（BuiltInRegistries.bootStrap HEAD）到达时才真正执行
        BrushEvents.CONTENT_REGISTRATION.register(event -> {
            wand = BrushRegistry.registerItem(WAND, new Item.Properties());

            // 方块 + 同名 BlockItem 配对（item id 由 block id 派生）
            Block block = BrushRegistry.registerBlock(WAND_BLOCK,
                    props -> new Block(props.strength(2.0F, 6.0F)),
                    BlockBehaviour.Properties.of().requiresCorrectToolForDrops());
            LOGGER.info("[mdkexample] content: wand=" + wand + ", block=" + block);

            // 数据包注册表（可选）：登记 + 用 BrushRegistry.dataRegistry(key) 读取
            // BrushDataRegistries.register(MY_REGISTRY_KEY, MyType.CODEC);
        });

        // ② 创造栏条目：向原版「原材料」页追加（官方名键经 Identifier 构造）
        BrushCreativeTabs.entriesOf(Identifier.fromNamespaceAndPath("minecraft", "ingredients"))
                .register(entries -> entries.add(new ItemStack(wand)));
    }
}

执行时机：onInitialize() 在 bootstrap.early 锚点跑，此时只做两件声明 —— 订阅内容窗口、订阅创造栏条目。① 的 lambda 在 BuiltInRegistries.bootStrap() HEAD 被调用，那里才是合法注册窗口；② 的 lambda 在每次「原材料」页构建时被调用，读的是 ① 写下的 wand —— 所以它必须晚于 ①，而这个顺序由 vanilla 的生命周期本身保证。别在 ② 里访问注册表取值以外的东西。
