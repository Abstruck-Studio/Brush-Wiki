事件总表

本页是工具页：把 BrushEvents 的全部 16 个事件字段做成一张表，并补充 Event<T> 与 EventRegistration 的用法、 L1 hook 与 L2 语义事件的分层，以及「注册时机」通则。

1. 全部事件字段（16 个，以源码为准）

表内「线程」列写的是事件被派发时所在的线程。S2 / S3 下宿主可能改变 bootstrap 类事件的执行线程（S1 = 游戏主线程），已在表中标注。 「三运行时」列的一致性指的是事件点与语义，运行时差异另在 §5 单列。

2. Event<T> 与 EventRegistration

2.1 Event<T>

项契约（源码 javadoc）
实例从哪来只能由 Brush 自身创建：BrushEvents 的静态字段与 BrushCreativeTabs—— 对 mod 而言事件是封闭集合，你拿不到也造不出别的事件
注册方法public EventRegistration register(T listener)； listener 为 null 抛 NullPointerException
注册线程线程安全，可在任意线程 —— 含 mod 入口类构造期。 注册只触碰 L1 派发表，不解析任何 MC 类型
是否允许重复注册允许。 可链式：同一事件可注册任意多监听器， 按注册先后调用；一个监听器的异常或注销不影响其他监听器。 不提供任何独占语义
取消 / 拦截没有取消机制。 Event / 各监听器接口都不带取消位 —— 事件是「通知」语义，不是「拦截 / 改写」语义
调用线程监听器在事件触发线程上被调用
异常传播不吞异常。 监听器抛出的异常被派发器包装为 IllegalStateException 并立即上抛 —— 快速失败，绝不让 hook 错误静默消失
不暴露的东西L2 不暴露 order，也没有「按 order 排序」的 L2 API —— 保证的只有「按注册序派发」

2.2 EventRegistration

成员语义
public void unregister()注销该监听器。幂等：重复调用无副作用
public boolean isActive()该监听器当前是否仍会被派发；注销后恒为 false
public void close()等价于 unregister()
L2 契约「宁小勿全」。 通过 EventRegistration 暴露的能力只有「注销」—— 注册顺序与开关属内部实现，需要时再按真实需求开放。也就是说： 你拿不到「临时关闭再打开」的开关，只能注销。需要这种语义时请自己在监听器对象里持一个 boolean。 
import org.abstruck.brush.api.BrushEvents;
import org.abstruck.brush.api.EventRegistration;

EventRegistration registration = BrushEvents.CLIENT_TICK.register(event -> {
    // 每帧
});

registration.unregister();     // 幂等
boolean active = registration.isActive();   // false

// 或者用 try-with-resources（退出块即注销）
try (EventRegistration scoped = BrushEvents.SCREEN_INIT.register(screen -> { })) {
    // ...
}

3. 事件命名与分层：L1 hook 与 L2 语义

一句话：L1（transform.HookEvents）是注入点的内部事件 id，可随版本调整、 是加载器自己的实现细节；L2（BrushEvents）是对 mod 的稳定语义契约， mod 只依赖 L2。

L1 · HookEventsL2 · BrushEvents
形态HookEvent 强类型 key Event<XxxListener> 类型化句柄
角色注入点与派发表之间的内部标识；拼错在编译期即失败 mod 唯一合法注册入口；载荷类型安全
稳定性内部标识，可随版本调整对外契约，尽量稳定
数量17 个 id 常量 16 个事件字段
桥接每个 L2 字段构造时绑定一个 L1 id + 一个 bridge 函数 注册最终落到同一张 L1 派发表上 —— 引擎只有一张，L2 是类型化包装

出处：HookEvents javadoc、 Event javadoc、设计文档记载。

4. 注册时机通则

  1. 注册监听器的地方 = BrushModInitializer#onInitialize() 或 BrushClientModInitializer#onInitializeClient()。 两者都在游戏就绪之前执行，注册动作本身安全。 客户端入口注册的 CLIENT_READY 监听器同批送达。
  2. 内容注册必须在监听器体内。 物品 / 方块 / 实体等内容注册只能写在 CONTENT_REGISTRATION 的监听器体内—— 窗口外调用会被 vanilla 守卫拒绝或 freeze 挡住，BrushRegistry 会把它包装成带指引的可读异常。 数据包注册表（BrushDataRegistries）不受这个窗口约束，但bootstrap 期同样不得调用。
  3. 「注册监听器」与「注册内容」是两件事：前者在初始化期，后者在监听器体内。把两者混在一处是新手最常见的错误。
import org.abstruck.brush.api.BrushEvents;
import org.abstruck.brush.api.BrushModInitializer;

public final class MyMod implements BrushModInitializer {

    @Override
    public void onInitialize() {
        // ① 注册监听器 —— 此刻游戏未就绪，这是「注册期」
        BrushEvents.CLIENT_TICK.register(event -> { /* ... */ });

        // ② 注册内容 —— 必须推迟到窗口到达（监听器体内）
        BrushEvents.CONTENT_REGISTRATION.register(event -> {
            // BrushRegistry.registerItem(...) 等等
        });
    }
}

5. 三运行时一致性的准确说法

「三运行时一致」在本页指的是：事件点、载荷语义、线程语义由同一份字节码提供，不随宿主变化 —— S1 / S2 / S3 共用同一份 mixin 配置与同一张派发表。以下是已知的、如实登记的运行时差异：

差异说明
CONTENT_REGISTRATION / CLIENT_REGISTRATION 的执行线程 S1 为游戏主线程；S3 为宿主的 bootstrap 线程（实测 pool-9-thread-1）； S2 在 Minecraft 构造中途。事件点本身三运行时相同， 监听器不应假定线程名，只应假定「事件点」。
S3 的客户端注册 flush 落地点 事件点（bootStrap TAIL）三运行时一致，但 S3 的落地推迟到首个 PACKS_REGISTERED —— 原因是宿主自身的内容注册晚于该 TAIL，在 TAIL 处求值属性 Supplier 会因未绑定的 holder 而失败（T3 实测）。
mod 入口的构造线程 S1 / S2 为 main，S3 为 modloading-worker-0。与事件派发线程无耦合。
宿主自省能力 S2 / S3 下宿主 mixin 服务不汇报「mod mixin 已施加」，台账那行为 n/a； 该缺口已由行为断言覆盖，不靠自省。
本页不含的两个事件。 BrushCreativeTabs.entriesOf(...) 的事件（CreativeTabOutputEvent.Listener）与 BrushCreativeTab 自有标签页不在 BrushEvents 字段表内 —— 前者按标签页键动态创建、后者是模型对象。两者见 界面与输入 §5。
