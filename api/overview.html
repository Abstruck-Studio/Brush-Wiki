契约面与设计原则

Brush API 是加载器项目自己发布的可选能力库 mod：加载器只保留"加载器的事"，游戏能力做成一个能被装配、也能缺席的 mod。本页给出版图：契约面是什么、编译期与运行期各由谁提供、三条不可让步的设计原则，以及库模组与加载器之间的边界是怎么划的。

1. Brush API 是什么

它是一支第一方能力库 mod。判据来自一句很朴素的话："这是加载器的事，还是游戏的事？" —— 在 Fabric 世界里，前者对应 Fabric Loader，后者对应 Fabric API。

它是可选的，不是必需的。加载器本体不依赖它即可编译与出包；"纯核心"实例也能启动，只是没有内容注册 / 网络 / 创造栏 / HUD 与输入这些能力。反过来要如实知道代价：自检矩阵里的探针测的正是这些能力，所以跑矩阵的实例必须把 brush-api.jar 放进 brush-mods/。

项目纪律里那条"mod 不得依赖 L1"已于 2026-10-14 作废：加载器不规定 mod 能用哪一层，直接用加载器产物或任何 Brush 类都是作者的正当选择。库模组的实现引用 L1 属于 mod → core 方向，合法；被禁止的方向始终是 core → mod。

2. 契约面：org.abstruck.brush.api.**

阶段用什么说明
编译期 brush-api-contract.jar（gradlew apiContractJar） 只含 org.abstruck.brush.api.**，不含 api/impl/**，也不含 L1 的 transform/ 与加载器内部 mod/ / launch/ / host/ / ui/。它把"只用对外契约面"变成机械保证：构建守卫逐个条目校验产物，出现 api 包之外的条目就失败；另有单测用"只给契约 jar + vanilla"的 classpath 实弹编译一个碰到 30 个 api 类型的样本
运行期 库模组 brush-api.jar 能力实现住在库模组；实例的 brush-mods/ 里没有它，对应能力就缺席

契约 jar 是可选产物：想自我约束"只用对外契约面"的作者可以用它，但用它不再是要求。库模组产物缺席时该任务明确跳过并打印原因与出路，不会让 gradlew build 失败。

在 MDK里没有契约 jar —— 作者的编译面就是能力库坐标 com.github.Abstruck-Studio:Brush-API 所提供的 org.abstruck.brush.api.**；org.abstruck.brush.api.impl 是能力库的内部实现，不要依赖。契约 jar 仍存在于完整的加载器项目里，供想机械地把自己约束在契约面上的作者使用。

3. 三条设计原则

① API 天花板 = 最受约束的平台

S1 下 Brush 是加载器、能力最强；S2/S3 下 Brush 只是宿主上的一个 mod，只能做 mixin 允许的事。API 不得暴露只有在 S1 才做得到的能力 —— 否则"写一次跑三处"是假承诺。

② 三运行时语义必须一致

同一 API 调用在三个平台的行为、时机、参数语义必须一致，否则 mod 作者仍要写平台分支，"写一次"退化成"写一次 + 三处调试"。

③ 必须提供平台逃生舱

有些事本质上因平台而异。硬统一会把 API 撑畸形 —— 这不是失败，是必要的泄压阀，用 @BrushExpectPlatform 承载。

语义一致怎么落地：事件 id、注册与派发机制只依赖 JDK 与 Brush 自身的派发表（L1），同一份字节码在 S1/S2/S3 行为一致；api 包对 MC 类型的引用是惰性载荷引用 —— 注册路径（Event.register）不解析任何 MC 类型，载荷只在事件真正触发、监听器被调用时才解析。触发线程也在契约里：CLIENT_READY / CLIENT_TICK / SCREEN_INIT / SCREEN_RESIZE 在游戏主线程；CLIENT_STOPPING 在 JVM 关闭线程；DATA_LOADED 在构造该服务器的线程，DATA_RELOADED 在重载 future 的完成线程。

逃生舱的契约（BrushExpectPlatform）：标注在静态桩方法上；平台实现类命名 = <桩类全名>Impl + Brush / Fabric / NeoForge，必须声明同名同签名的 static 方法；加载期把桩方法体替换为对实现类的委托调用 —— 运行期成本就是普通 invokestatic，无反射、无查表，注解 CLASS 保留、运行时不可见。缺失即硬失败：当前运行时找不到实现类或方法 = 该 mod 加载失败并指明缺哪个，不允许静默回退。

已登记的风险：G1、G2、G6。

4. 库模组与加载器的边界

留在加载器核心（加载器契约）属能力面（游戏的事）
入口点契约 BrushModInitializer / BrushClientModInitializer / BrushDedicatedServerModInitializer；自检契约 ModSelfTest / ModClientTest / ClientTestContext；加载器状态查询 BrushMods；平台逃生舱 BrushExpectPlatform；事件骨架 Event / EventRegistration / BrushEvents；生命周期与数据事件；关闭期留痕 RawStdout 内容注册、网络、创造栏、HUD 与输入、客户端注册窗口、屏幕事件

已执行的搬家（Phase C）与它撞出的真回归。搬走的是"能力实现 + 承载它的注入点"：网络引擎（BrushPayload / BrushChannels / ReplyGuard / DispatchDedupe）与 S3 宿主桥 NeoForgePayloadBridge、HUD 与输入的三个 mixin、创造栏的两个 mixin、键位的 OptionsMixin —— 包名与类名保持不变。留下的两类东西都有明确理由：

  • L2 事件类型留核心：BrushEvents（L2 事件枢纽）持有它们的监听器类型；一旦搬走，BrushEvents 就反向依赖 mod，方向非法。所以接口留核心、实现归库模组，事件字段留在 BrushEvents —— 这同时让 mod 作者既有写法 BrushEvents.NETWORK_PAYLOAD.register(...) 一行都不用改。
  • 门面与中性接缝留核心：BrushNetwork 以门面留核心，实现 BrushNetworkImpl 住库模组；核心另有一层中性接缝 host.HostSeams，只把宿主 mod 事件总线当 Object 递出，由库模组入口去挂 S3 的桥。
门面不是洁癖，是一次实机回归换来的。搬家后 T1/T2/T4 与 S1/S2 实机全绿，唯独 S3 实机在 mod 构造期崩：NoClassDefFoundError: org/abstruck/brush/api/BrushNetwork。根因是 FML 的包归属规则 —— org.abstruck.brush.api 是核心模块拥有的包，宿主加载的代码只在该模块里找，找不到也不回退；而 org.abstruck.brush.net.* 搬走后已非核心包，回退可达。于是得出可复用判据：核心 → mod 搬家时，"包归属"与技术可行性同等重要。惰性解析还去掉了一个隐式依赖：门面不要求库模组的 onInitialize 比别的 mod 早跑。

注入点归属：搬家不是减少。注入面台账的语义是"对 vanilla 的全部改动面"，不是"核心 jar 的改动面"。因此四面核对跨来源进行：点数求和、被注入类名取并集，总数不变（当前 21 点 / 16 类）。禁止把"核心点数下降"写成成果。派生纪律：凡动注入点归属，必须同时跑实机探针 —— T1–T3 的退出点都在世界加载之前。

5. 依赖声明：brush.mod.json 的 depends

用到 API 能力的 mod，应在自己的 brush.mod.json 里声明 brush-api —— 例如随附的示例夹具 mod ping-net 与 durability-hud，元数据里都写 "depends": { "brush": "^26.10.0", "brush-api": "^1.0.0" }。理由两条：运行期该能力由库模组提供，实例的 brush-mods/ 里必须有 brush-api.jar；诊断上缺席时自检原本会甩出难懂的 ClassCastException: BrushPayload cannot be cast to DiscardedPayload，现在改为点名库模组的可读归因，已在暴露该问题的实例上实测生效。

依赖区间语法与元数据字段全表见 第一个 mod 与 API 参考索引。

7. 流体与能量能力（增量语义）

从 2026-10-17 起，库模组提供一组方块级的流体 / 能量能力接口。三者都在 org.abstruck.brush.api：

类型成员
BrushFluidStorage tankCount() / fluidIn(int) / amountIn(int) / capacityOf(int) / insert(int tank, Fluid, long maxAmount, boolean simulate) / extract(...) —— 移动类方法返回实际移动量；另有默认 isValid(int tank, Fluid)
BrushEnergyStorage stored() / capacity() / receive(long maxAmount, boolean simulate) / extract(long maxAmount, boolean simulate)+ 默认 canReceive() / canExtract()
BrushCapabilities 注册：registerFluidBlock / registerFluidBlockEntity / registerEnergyBlock / registerEnergyBlockEntity；查询：fluid(Level, BlockPos, Direction) / energy(...) 返回 Optional；诊断：registeredCounts()

平台适配全部用宿主本体 API，没有第三方依赖：S3（NeoForge）= Capabilities.Fluid.BLOCK（ResourceHandler<FluidResource>）与 Capabilities.Energy.BLOCK（EnergyHandler）；S2（Fabric）= FluidStorage.SIDED（Storage<FluidVariant>）；S1 只有 Brush 自己的注册表。查询与注册是双向的：我们注册的储能会暴露给宿主 mod，宿主 mod 的储能也能被 BrushCapabilities 查到。

两点如实登记的边界：① Fabric 的 transfer v1 没有能量模块 ⇒ S1 与 S2 的能量只能查 Brush 自己的注册表；NeoForge 侧才有宿主能量。② 注册时机是硬约束：必须在你的方块 / 方块实体类型已经存在之后注册；不要在 onInitialize() 里引用 Blocks / BlockEntityType。NeoForge 的能力事件只触发一次，晚于它新增的条目不会被转登记。

事务语义：用 Brush 接口去操作宿主的 handler时，桥会自己开事务 —— 真实写入 commit、模拟 abort / close，不参与调用者的外层事务。

有意不做：物品级能力、带数据组件的流体变体、以及把原版方块暴露成能力。
