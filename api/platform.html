平台适配与自检

Brush API 的天花板是最受约束的平台，因此平台差异必须有一个受控的泄压阀。本页讲三件事：逃生舱 @BrushExpectPlatform 的契约与纪律、自检契约（ModSelfTest / ModClientTest / ClientTestContext）与裸输出 RawStdout，以及同一份 API 在 S1/S2/S3 下的行为对照。

1. 为什么需要逃生舱

结论先行：有些事本质因平台而异，硬统一会把 API 做畸形。注册时机、网络通道、启动时序在三运行时确实不同；把它们塞进一套签名，得到的会是一套"为了兼容而谁也不像"的接口。

这是 Brush API 设计原则的第三条：API 只暴露三平台共同可实现的能力，而平台特定部分走 Architectury @ExpectPlatform 模式的等价物。设计文档把动因写得更直白 —— "有些事本质因平台而异，硬统一会导致 API 畸形，'写一次跑三处'必须有泄压阀"。

同期存在的另一条约束是天花板问题：S1 下 Brush 是加载器、能力最强；S2/S3 下 Brush 只是一个 mod，只能做 mixin 允许的事。API 不得暴露只有 S1 才做得到的能力，否则"写一次跑三处"是假承诺。

逃生舱不是失败，是必要的泄压阀。但它是有代价的：每多一个逃生舱，跨平台承诺就多一个缺口 —— 因此才有下面第 4 节的纪律。

2. @BrushExpectPlatform 的用法

契约一句话：注解在静态桩方法上，方法体在 mod 加载期被替换为对当前运行时实现类的委托调用；mod 代码照常直接调用桩方法。

项契约
标注位置静态方法；所在类不得是接口 / 抽象类
实现类命名<桩类全名>Impl + Brush / Fabric / NeoForge，与桩同包
实现方法与桩方法同名同签名的 static 方法
缺失语义硬失败：当前运行时找不到实现类或方法 = 加载失败，报错指明缺哪个类 / 哪个方法，不静默回退
运行时成本委托调用是普通 invokestatic，无反射、无查表
注解保留RetentionPolicy.CLASS
预处理对象mod jar（mod.ModJarPreparer），不是 vanilla 类 —— 不产生注入点、不进 footprint 台账
参数 / 返回值类型须三运行时同名可及；26.1.2 三运行时统一官方名，直接用官方名类型即可
不支持恒为空 body 的实现不受支持

出处：BrushExpectPlatform javadoc 与 mod jar 预处理实现。

真实用例：示例 mod 的 Platform

这是 MDK 示例 mod 里的真实代码（org.abstruck.brush.example.Platform），两个桩方法：

package org.abstruck.brush.example;

import org.abstruck.brush.api.BrushExpectPlatform;

public final class Platform {

    private Platform() {
    }

    /** 当前加载器平台的名字（三实现分别返回 "Brush" / "Fabric" / "NeoForge"）。 */
    @BrushExpectPlatform
    public static String loaderName() {
        throw new AssertionError("Platform.loaderName() stub body must have been replaced at load time"
                + " (BrushExpectPlatform; mod jar preprocessing did not run -- regression!)");
    }

    /** 当前运行时种类（与 mod.RuntimeKind 枚举名同口径：BRUSH / FABRIC / NEOFORGE）。 */
    @BrushExpectPlatform
    public static String runtimeKind() {
        throw new AssertionError("Platform.runtimeKind() stub body must have been replaced at load time"
                + " (BrushExpectPlatform; mod jar preprocessing did not run -- regression!)");
    }
}

桩体写成"抛 AssertionError"是有意的：万一预处理未生效，调用当场失败，而不是静默返回假值 —— 失败要响亮。

当前运行时的实现类：

package org.abstruck.brush.example;

public final class PlatformImplBrush {

    private PlatformImplBrush() {
    }

    public static String loaderName() {
        return "Brush";
    }

    public static String runtimeKind() {
        return "BRUSH";
    }
}

三运行时各自挑哪个实现

运行时选中的实现类loaderName()runtimeKind()
S1 纯 BrushPlatformImplBrush"Brush""BRUSH"
S2 Fabric 宿主PlatformImplFabric"Fabric""FABRIC"
S3 NeoForge 宿主PlatformImplNeoForge"NeoForge""NEOFORGE"

同一份 mod 字节码、同一个桩方法调用点，三运行时得到三个实现 —— 逃生舱机制端到端成立。

三个 PlatformImpl* 的差异（读源码后的如实描述）

只有返回的字面量不同。三个实现类都是 public final、都有 private 无参构造器、都声明了同名同签名的两个 public static String 方法，方法体各自 return 一个常量字符串。类 javadoc 也只差"S1/S2/S3 实现"一句话。没有任何一个实现引用平台特有的类型或 API —— 这恰好说明示例 mod 的逃生舱只用于演示机制本身，不是真实的能力需求。

S1 的命名曾经历一次修订：RuntimeKind.VANILLA → BRUSH、实现类后缀 ImplVanilla → ImplBrush、展示串去掉 (standalone) 标记。修订后的 T1 证据为 loaderName=Brush, runtimeKind=BRUSH。源码与修订后的口径一致。

3. 写逃生舱的纪律

每个逃生舱都要有存在理由；数量要审计。项目风险登记册把"平台特定逃生舱被滥用"列为中风险，缓解措施就是两条：每个逃生舱登记理由、定期审计数量。

落地的可操作口径如下：

  1. 先论证"能不能不写"。能被 L2 现有事件 / 注册面表达的需求，一律不加逃生舱。
  2. 一个桩，一个理由。桩类里每多一个桩方法，就是一处"三平台语义可能不同"的声明，需要在文档与代码注释里写明理由。
  3. 别把逃生舱当 API 的补丁。如果某个能力在三平台都有对应实现、只是签名难对齐，那是 API 设计问题，不是逃生舱问题。
  4. 数量可审计。示例 mod 现有 1 个桩类 / 2 个桩方法（Platform），这是目前唯一的逃生舱真实用例。
  5. 不留静默回退。找不到实现就是加载失败 —— 静默回退会让"三平台一致"变成运行时惊喜。

4. 自检契约

自检能力本身就是 API 面的一部分 —— 这是"可测试性"作为能力的体现。三个类型的分工是：ModSelfTest 管装载期，ModClientTest + ClientTestContext 管进世界之后。

4.1 ModSelfTest —— 装载期端到端断言

签名
Map.Entry<String, Boolean> selfTest()
调用时机
仅在 --brush.selftest 运行中；自检退出点 = 首个 client.tick，对每个入口实例恰一次
调用时刻的既成事实
内容注册窗口与客户端注册 flush 均已过去、Minecraft 实例已构造 —— 注册表、DefaultAttributes、SpawnPlacements、渲染器 / 屏幕映射都可直接读取断言
实现位置
自检对 ModBootstrap.loadedMods() 的入口实例做 instanceof 探测 —— 主入口 BrushModInitializer 或客户端入口 BrushClientModInitializer 实例实现本接口均可
失败语义
实现方不得抛出；抛出= 记为 FAIL 并如实上报异常栈。任一 FAIL 置退出码位 256（Selftest.EXIT_MOD_SELFTEST）
无实现时
报告为信息行，不是失败

实现最小形：

import java.util.Map;
import org.abstruck.brush.api.BrushModInitializer;
import org.abstruck.brush.api.ModSelfTest;

public final class MyMod implements BrushModInitializer, ModSelfTest {

    @Override
    public void onInitialize() {
        // 注册事件监听器 / 内容
    }

    @Override
    public Map.Entry<String, Boolean> selfTest() {
        boolean ok = /* 端到端断言：例如注册表里查得到自己的条目 */ true;
        return Map.entry("my_check", ok);
    }
}

4.2 ModClientTest + ClientTestContext —— 进世界之后的断言

与 ModSelfTest 的差异是覆盖面：ModSelfTest 覆盖装载期；ModClientTest 覆盖进世界之后的一切。

项契约
签名Map<Map.Entry<String, Boolean>, ?> runClientTest(ClientTestContext context)
调用时机仅 --brush.mod-test 运行中；CLIENT_READY 之后由加载器（selftest.ModTestProbe）对每个声明了测试入口的 mod 入口实例恰一次
声明方式经 brush.mod.json 的 entrypoints.test 列出实现类全名。源码：ModMetadata.Entrypoints.test javadoc。注意：ModClientTest 的 javadoc 原文写的是"经 brush.mod.json 的 test 附加节声明"，与实现的 entrypoints.test 键名不一致 —— 以源码为准
缺省不声明则该 mod 在本模式下不运行任何测试，加载照常
失败语义实现方不得抛出；抛出 = 该 mod 全部检查项 FAIL；返回 null / 键为 null / 值为 null = 格式非法 FAIL
常规运行零加载、零调用、零成本

ClientTestContext 是把"进世界"的样板代码收编成的只读上下文 —— 由加载器侧构造，mod 实现只读使用，不得自行 new。它提供四项能力：

Minecraft minecraft();                       // 当前客户端实例（CLIENT_READY 之后必然非 null）
void quickPlayOrCreateWorld(String worldName); // 建/进临时世界并等"可玩"（含关掉首启辅助功能屏）
boolean awaitServerReady(long timeoutMs);    // 轮询"服务端 tick 已启动且集成服务器非 null"；超时返回 false，不抛
Path gameDirectory();                        // 游戏目录（mod 测试装置写产物用）
void screenshot(String name);                // 统一截屏落盘到 <gameDirectory>/mod-test-screenshots/<name>.png

线程语义：方法在游戏主线程被调用；screenshot 与 awaitServerReady 可阻塞主线程。失败不静默降级 —— quickPlayOrCreateWorld 失败抛 IllegalStateException，screenshot 失败抛 RuntimeException。

退出码协议：加载器保留 bit 0..15；bit 16+（值 65536 起）交 mod 自定测试项位组合 —— mod 实现若需要位组合，用 1 << 16 起算。

4.3 为什么把自检放进 API

  • 没有它，"三平台语义一致"只能靠人眼。语义漂移是最高风险之一（G2），而端到端断言是唯一机械的验证手段。
  • 断言的知识只有 mod 自己有。加载器能查"注册了几个条目"，但查不出"这个条目在我的 mod 里是不是真的能用"—— 后者必须由 mod 写。
  • 它是零成本的。ModSelfTest/ModClientTest 只在对应模式下被探测与调用；常规运行零监听、零调用。
  • 它不需要 mod 引进新依赖。两个接口的返回值都是纯 JDK 类型（Map / Map.Entry），ModSelfTest 因此零 MC 引用，自检源集可直接引用而不破坏其"零 MC 引用"类加载不变量。
  • 它让 mod 的断言进退出码，从而进自动化矩阵。

5. RawStdout：受控的裸输出

用途只有一条：在日志系统已经不可靠的时刻，仍然留下证据。

具体场景是 CLIENT_STOPPING 的监听器 —— 它在 JVM 关闭序列中执行，此时游戏侧 log4j 已关闭，且 MC 启动时已把 System.out 换成 log4j 承接的流。经 log4j 或 System.out 的关闭期输出会被静默丢弃。RawStdout.println(String) 改为经 FileDescriptor.out 直写进程 fd 1，绕开这两个环节。

语义
输出直达进程 stdout—— 不进 latest.log；不经过 log4j、不经过 System.out 的重定向 —— 任意线程、任意时刻可用；永久不抛异常
降级行为
fd 打开失败时回退 System.out —— 降级而非失败，证据通道绝不因打印失败中断关闭序列
实现位置
API 面是薄委托，实现为 org.abstruck.brush.transform.RawStdout
使用纪律：RawStdout 不是日志的替代品。其余事件触发时 log4j 正常存活，常规 log4j 日志即可。只有"机器可读的报告行 / 关闭期证据"才走这条通道 —— 因为它绕过了日志系统，也就绕过了日志的采集、轮转与分级。

S3 唯一的"必须在哪注册"硬约束：BrushNetwork.register(...) 必须放在主入口点，不要放在 entrypoints.client。原因：S3 只给一次载荷登记机会，宿主适配器在那一刻把当时已知的通道桥接进 NeoForge 注册表，而客户端入口点比它晚 —— 在那里登记的通道在 S3 下发不出去。该情形会由引擎的发送守卫响亮失败并给出补救指引（S1/S2 无此限制）。出处：BrushNetwork#register javadoc、NeoForgePayloadBridge javadoc。

6.2 哪些能力只在 S1 有，因此不进 API

判据是"这个能力在 S2/S3 下还成立吗"。不成立的，一律留在加载器内部，不做成 L2。

只在 S1 成立的能力为什么进不了 API
以下条目由加载器内部持有
P1 启动管线S2/S3 下启动由宿主（Fabric Loader / FML）完成，Brush 只是被装载的一个 mod。暴露它等于让 mod 依赖"自己是启动器"这个前提
自研 ClassLoader / Mixin 服务（BrushMixinService）宿主有 Knot / FML 自己的加载器与 mixin 子系统；brush.standalone 守卫让我们的服务在宿主下让位
--brush.selftest 的进程退出与退出码协议（Selftest）报告与退出码属加载器自身的验证装置，是"加载器怎么证明自己"，不是 mod 的能力面。mod 侧只经 ModSelfTest 往里贡献检查项
mod jar 预处理（ModJarPreparer）的细节它是发现并重写逃生舱桩的机制本体；mod 需要知道的只有"桩方法会被替换"这条契约

对照：ClientTestContext 的退出码协议则确实是 API 面的一部分 —— 它把 bit 16+ 显式让给 mod 自定测试项，这是加载器与 mod 之间的公开约定，与上表最后两行不矛盾。
