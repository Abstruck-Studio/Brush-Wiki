第一个 mod（MDK 上手）

MDK 是扁平的一体化开发包：解压后 项目根就是可运行的 Gradle 工程，加载器与能力库默认从网络库取。两条命令跑通 S1，之后 S2 / S3 各一条命令 —— 三种运行时都在这一个文件夹里跑。读完后你知道每个任务做什么、依赖从哪里来、日志里哪一行证明加载成功，以及初始化期为什么只能注册监听器。

下载 MDK：Brush-MDK-26.10.1.zip（约 66 KB）—— 解压即得本页描述的那个扁平项目。

一、MDK 里有什么

路径是什么
项目根（build.gradle / settings.gradle / gradle.properties / gradlew.bat / src/）你的 mod 项目本体：源码、资源、brush.mod.json 与 Gradle Wrapper 全在根目录，并带一个可运行的示例 mod。
依赖来源：com.github.Abstruck-Studio:Brush:26.10.1加载器—— 同时是游戏启动器与自举工具：运行时由它拉起游戏、加载你的 mod；下载 MC 的自举主类（metadata / libraries / assets）也在它里面，而 metadata 由构建期自动触发。
依赖来源：com.github.Abstruck-Studio:Brush-API:1.0.0能力库—— 作者契约面的来源之一。
依赖来源：同加载器坐标的 tools classifier宿主 harness：FabricHostHarness / NeoForgeHostHarness 及其 profile —— S2 / S3 的运行靠它装配并拉起宿主。它只依赖加载器 jar 的 launch/** 与 gson / log4j，不含任何第三方二进制。
libs/*.jar只在传 -Pbrush.useLocalJars=true 时使用：把上面三份 jar 放进 libs/ 即可完全离线。
项目根的 gradlew.bat 是 Gradle 官方 Wrapper，不是本 MDK 的配置脚本 —— 除此之外 MDK 没有任何 .bat 脚本，一切通过这个 Gradle 工程的命令完成。依赖解析是惰性的：gradlew help / tasks 不会联网，只有编译或运行才去取坐标。

前置两件事：JDK 25；首次构建需要联网。

二、两条命令：从零到能跑

命令都在项目根目录下执行。构建即自举（2026-10-16 起）：jar 会在构建期自动把 MC 客户端 jar 下下来，所以不需要先手动跑 bootstrap；runClient 之前也会自动补齐库与资产。

:: ① 编译你的 mod（构建期自动确保 MC 客户端 jar；产物 build\libs\mdkexample.jar）
gradlew.bat jar

:: ② 启动游戏并加载你的 mod（S1：vanilla + Brush）
gradlew.bat runClient

可选：想"一次性备齐"就显式跑 gradlew.bat bootstrap（S3 再补 installNeoForge）。离线 / CI 想完全自己掌控，可传 -Pbrush.autoBootstrap=false 关掉自动自举 —— 那时缺件仍然可读失败，不会静默跳过。

这个项目一共 11 个任务，全部在项目根目录下执行：

任务作用与落地
metadata / libraries / assets自举的三个子步骤：版本元数据 + 客户端 jar（sha1 + size 校验）→ 库与 natives → 资产索引与全部对象。其中 metadata 是构建期自动触发的那个。
bootstrap可选的一次性备齐：一次跑完上面三个子步骤：客户端 jar 到 <gradle 用户目录>/caches/brush/26.1.2/，库 / natives / 资产到 <gradle 用户目录>/caches/brush/cache/。落点是用户级 Gradle 缓存，与 Fabric Loom / NeoForge neoform 同款 —— 项目根不再出现 26.1.2/ 与 cache/，而且加载器 / 能力库 / 本示例项目默认共享同一份下载。
jar编译打包你的 mod→ build/libs/mdkexample.jar。依赖默认从 JitPack 解析。
verifyLocalJars只在传了 -Pbrush.useLocalJars=true 时生效：校验 libs/ 下三份 jar 是否齐全，缺件给可读失败。网络模式下它什么都不做。
stage只摆放不启动：把你的 mod + brush-api 摆进 S1 的 run/brush-mods/。
runClientS1：重置 run/brush-mods/ 并摆入「你的 mod + brush-api」，以 org.abstruck.brush.launch.Brush 拉起 vanilla + Brush。
runFabricClientS2：重置 run/fabric/brush-mods/，由 FabricHostHarness 装配并拉起 Knot + Fabric Loader。
installNeoForge把 NeoForge 宿主产物装进缓存（--install-only）—— S3 首次运行前跑一次。
runNeoForgeClientS3：重置 run/neoforge/brush-mods/，由 NeoForgeHostHarness 装配并拉起 FML。
运行 = 当前代码。三个 run* 都会先清空对应实例的 brush-mods/，再摆入「你的 mod + brush-api」，所以改完代码直接再跑一次即可 —— 不存在"陈年 jar 干扰"，也没有单独的清空命令。只想摆放不启动：gradlew.bat stage。
-Pbrush.useLocalJars=
传 true ⇒ 离线模式：不再从网络取坐标，改用你自己放进 libs/ 的三份 jar。不传 = 默认网络模式（JitPack）。
-PbrushVersion=
加载器坐标的版本（默认 26.10.1）：com.github.Abstruck-Studio:Brush:<版本>。
-PbrushApiVersion=
能力库坐标的版本（默认 1.0.0）：com.github.Abstruck-Studio:Brush-API:<版本>。
-PbrushCoreJar= / -PbrushApiJar=
本地模式下显式指定加载器 / 能力库 jar 的路径。
-Pbrush.vanillaJar=
指定 vanilla 客户端 jar；默认 = 用户级 Gradle 缓存里的 <gradle 用户目录>/caches/brush/26.1.2/26.1.2.jar。
-Pbrush.cache=
指定 MC 缓存目录；默认 = <gradle 用户目录>/caches/brush/cache。
-Pbrush.autoBootstrap=
传 false 关掉"构建期自动跑 metadata"；缺件仍以可读失败拦下。
-Pbrush.neoforgeInstaller=
指定本地 NeoForge 安装器 jar：installNeoForge / runNeoForgeClient 会用它，跳过联网下载。不传时按"<缓存>/neoforge/ → libs/"自动发现。

缺件不要猜：verifyInputs 会把"缺哪个 jar、怎么补"写在异常里；本地模式下的 verifyLocalJars 同理。

三、S1 / S2 / S3：一个 jar 跑三种运行时

你的 mod 只编译一次，同一份字节码三个运行时通用 —— 26.1 起游戏未混淆，三个运行时的类名与方法名完全一致，因此不需要重映射、不需要 refmap、也不需要写平台分支。

三种运行时都能在 MDK 里直接跑 —— 宿主 harness 来自加载器坐标的 tools classifier，不需要回到加载器项目。
运行时命令实例目录我们的 mod 目录谁拉起游戏
S1 纯 Brushgradlew.bat runClient项目根 run/run/brush-mods/加载器自身（org.abstruck.brush.launch.Brush）
S2 Fabric 宿主gradlew.bat runFabricClient项目根 run/fabric/run/fabric/brush-mods/FabricHostHarness 装配后拉起 Knot
S3 NeoForge 宿主gradlew.bat installNeoForge→ gradlew.bat runNeoForgeClient项目根 run/neoforge/run/neoforge/brush-mods/NeoForgeHostHarness 装配后拉起 FML
S3 首次要装宿主产物：先跑一次 gradlew.bat installNeoForge。离线首装可以传本地安装器：-Pbrush.neoforgeInstaller=<本地安装器 jar>；不传则按「<缓存>/neoforge/ → libs/」自动发现。

MDK 是自包含的：整个文件夹拷到别的设备，jar → 三个 run* 都能跑。想完全离线就传 -Pbrush.useLocalJars=true 并自备 libs/ 三份 jar。三个 run* 都会先把对应实例的 brush-mods/ 清空，再摆入「你的 mod + brush-api」—— 所以运行的就是你当前的产物。

我们的 mod 放独立目录（brush-mods/）而不是宿主的 mods/，是刻意的项目纪律：宿主加载器会扫它自己的 mods/，对我们的 mod可能告警或误解析；反向我们也可能误扫宿主的 mod。双向隔离成本很低。

四、元数据：brush.mod.json

加载器按 jar 内 根目录的 brush.mod.json 识别 mod。MDK 模板里的真实文件如下：

{
  "id": "mdkexample",
  "name": "MDK Example Mod",
  "version": "1.0.0",
  "description": "Brush MDK 示例 mod：在内容注册窗口注册物品 mdkexample:wand，并在初始化期打一条日志。把本项目的 id / 入口类 / 内容改造成你自己的 mod 即可。",
  "authors": [
    "<你的名字>"
  ],
  "entrypoints": {
    "main": [
      "com.example.mdk.ExampleMod"
    ]
  }
}

字段语义：

id
模组唯一标识，小写字母开头，允许 [a-z0-9_.-]；同时是你的资源命名空间。
name
展示名，可选；缺省时报告回退用 id。
version
点分纯数字版本；依赖解析的比对对象。
entrypoints.main
必需：入口类全名列表，每类须为 public 具体类 + public 无参构造器 + 实现 BrushModInitializer。
entrypoints.client
可选：实现 BrushClientModInitializer 的类，只在客户端时机被加载——可以安全引用客户端类型。
entrypoints.server
可选：实现 BrushDedicatedServerModInitializer。当前只被校验、不被派发，自检报告以 entrypoints.server: declared=N 如实列出。

其余可选字段：description、authors、icon、mixins、depends、breaks、conflicts（WARN）、recommends（WARN）、suggests、provides、jars。

五、入口类：完整示例与逐行解释

MDK 示例 mod 项目的入口类 ExampleMod.java 正文贴在这里：

package com.example.mdk;

import net.minecraft.resources.Identifier;
import net.minecraft.world.item.Item;
import org.abstruck.brush.api.BrushEvents;
import org.abstruck.brush.api.BrushModInitializer;
import org.abstruck.brush.api.BrushRegistry;
import org.apache.logging.log4j.LogManager;
import org.apache.logging.log4j.Logger;

public final class ExampleMod implements BrushModInitializer {

    private static final Logger LOGGER = LogManager.getLogger("mdkexample");

    /** 你的 mod id（须与 brush.mod.json 的 id 一致，也用作资源命名空间）。 */
    public static final String MOD_ID = "mdkexample";

    /** 示例物品 id：mdkexample:wand。 */
    public static final Identifier WAND = Identifier.fromNamespaceAndPath(MOD_ID, "wand");

    @Override
    public void onInitialize() {
        LOGGER.info("[mdkexample] onInitialize -- 游戏尚未就绪，这里只注册监听器");

        // 内容注册：窗口到达时才真正执行（监听器体内）
        BrushEvents.CONTENT_REGISTRATION.register(event ->
                BrushRegistry.registerItem(WAND, new Item.Properties()));

        // 想再加生命周期行为？例如每帧 tick：
        // BrushEvents.CLIENT_TICK.register(event -> { ... });   // 热路径：注意节流（勿每帧打日志）
        // 其它可用事件见 org.abstruck.brush.api.BrushEvents 的字段表。
    }
}

上段与 MDK 的 ExampleMod.java 正文逐字一致，便于你直接对照修改。

逐点解释：

  1. public final class ... implements BrushModInitializer：入口契约三件套 —— public 具体类、public 无参构造器、实现该接口。不实现接口的主入口类 = 加载失败。final 不是要求，只是习惯。
  2. onInitialize() 的时机：Brush 在 bootstrap.early 锚点构造入口实例并调用它 —— 早于 Main.main、早于内容注册窗口、早于一切游戏生命周期事件，S1/S2/S3 一致（BrushModInitializer javadoc）。所以这里是"注册期"，不得假定任何游戏状态已就绪。
  3. MOD_ID / WAND：Identifier.fromNamespaceAndPath(ns, path) 是 26.1 起 ResourceLocation 更名后的官方 API。id 必须与元数据 id 一致，否则资源命名空间与归账归属对不上。
  4. BrushEvents.CONTENT_REGISTRATION.register(...)：这里只注册监听器。注册动作只触碰 L1 派发表，不解析任何 MC 类型 —— 所以入口构造期调用是安全且规定的用法（Event#register javadoc）。
  5. BrushRegistry.registerItem(...) 在 lambda 体内：这才是真正碰注册表的一步，它在窗口到达时才执行。这就是"声明与执行分离"：声明在引导期，执行在窗口内。
为什么初始化期不能碰注册表。vanilla 有一对硬守卫把注册夹在中间：更早触碰注册表类会被抛 IllegalArgumentException: Not bootstrapped (called from registry ...)；更晚注册会被抛 IllegalStateException: Registry is already frozen。唯一合法窗口在 Bootstrap.bootStrap() 执行流内部，外部代码不可达 —— 因此只能经 BrushEvents.CONTENT_REGISTRATION 进窗口。Brush 把这个窗口以 L2 事件的形式交给你，细节见 内容注册。

六、编译面与依赖

你的编译面 = 两个 jar 里的 org.abstruck.brush.api.**：加载器 jar 与能力库 jar 一起进 compileOnly，javac 同时看两边，所以你不用关心某个类具体住在哪个 jar 里。

org.abstruck.brush.api.impl 是能力库的内部实现：不要依赖它。它随加载器版本变动，不属于契约；需要平台差异时用契约面里的 BrushExpectPlatform。
依赖（全部 compileOnly）用途来源与许可
files(vanillaJar)MC 类型（Identifier / Item / Block…）用户级 Gradle 缓存里的 <gradle 用户目录>/caches/brush/26.1.2/26.1.2.jar，由构建期自动触发的 metadata 获取
files(apiJar) + files(coreJar)Brush 作者契约面（org.abstruck.brush.api.**）默认来自 JitPack 坐标 com.github.Abstruck-Studio:Brush-API 与 :Brush；离线模式（-Pbrush.useLocalJars=true）下是 libs/brush-api.jar 与 libs/Brush-<版本>.jar
com.mojang:datafixerupper:9.0.19Registry 等类型的父接口链（Keyable）libraries.minecraft.net，MIT
com.mojang:brigadier:1.3.10Component 的类型链libraries.minecraft.net，MIT
io.netty:netty-buffer:4.2.7.Final自定义网络载荷里 ByteBuf 的父类型Maven Central，Apache-2.0
org.apache.logging.log4j:log4j-api:2.22.1日志；运行时由游戏提供Maven Central，Apache-2.0
sponge-mixin / mixinextras-common要写 mixin 时打开这两行FabricMC maven（MIT）/ Maven Central（MIT）

项目里的 bootstrapRuntime（加载器 jar + gson / log4j）与 brushRuntime 是运行装置，harness 是 S2 / S3 的 harness —— 三者都不是你的依赖面，别往自己的 mod 里抄。

要写 mixin：打开那两行依赖，在资源目录（resources/）下加 yourmod.mixins.json，并在 brush.mod.json 里声明 "mixins": { "brush": ["yourmod.mixins.json"], "fabric": ["yourmod.mixins.json"] }。目标名用官方名，不要写 refmap（S3 下写了会坏）。

七、如何确认加载成功

加载成功后，游戏日志里有这几行。注意三个 run* 都会把能力库一起摆进去，所以 mod 数是 2。S1 实测：

[brush] --- mod loading (P3) ---
[brush] mod dir: ...\run\brush-mods (2 jar(s))
[brush]   loaded: brush-api 1.0.0 entry=org.abstruck.brush.api.impl.BrushApiMod
[brush]   loaded: mdkexample 1.0.0 entry=com.example.mdk.ExampleMod
[brush] mod loading complete -- mods: 2 loaded (brush-api 1.0.0, mdkexample 1.0.0)
[brush] (loader version 26.10.1, game version 26.1.2)

同一份 jar 在 S2下的实测输出：

[brush] S2 ready: hooks installed, brush-mods loaded
[brush] host mods: brush@26.10.1, fabric-api@0.155.3+26.1.2, fabricloader@0.19.5, minecraft@26.1.2, modmenu@18.0.2, sodium@0.9.2+mc26.1.2 ...
[brush] mod loading complete -- mods: 2 loaded (brush-api 1.0.0, mdkexample 1.0.0)
:: 资源重载日志里还会出现 brush_mods 资源包

host mods: 一行是宿主侧的已加载清单：它同时列出 brush@… 与宿主自己的 mod（fabric-api / sodium …）—— 这就是"我们的 mod 与宿主生态 mod 在同一 JVM 共存"的可见证据。

loaded: <id> <version> entry=<类名>
逐 mod 一行：id、版本、被实例化的入口类。这一行出现 = 元数据被解析、入口类被构造过。
mod loading complete -- mods: N loaded (...)
汇总行，括号里是 id 版本 列表。N 就是本次加载的 mod 数 —— 三个运行时下正常都是 2。
order:
依赖拓扑序，另一行输出；出问题先看它是否符合预期。

如果加载失败，输出是一次列全的问题清单、并且一个 mod 都不实例化：

[brush] MOD LOADING FAILED -- 2 problem(s) (...\run\brush-mods, 3 jar(s)):
[brush]   - bad-nojson.jar: missing mod.json at jar root (only Brush mods belong in brush-mods/; ...)
[brush]   - mod 'brush.example.baddep' requires 'brush' >=99.0.0, found 26.10.1
[brush] no mods were instantiated; aborting launch before the game starts

八、调试建议

  • 先读日志，再猜代码。当次运行的控制台与游戏侧 run/logs/latest.log 是唯一证据源；轮转后的历史在 run/logs/*.log.gz，别只盯着 latest.log 的尾部窗口。
  • mod 没进去？先确认 mod dir: 是你以为的目录、(N jar(s)) 数目对：S1 是 run/brush-mods，S2 是 run/fabric/brush-mods，S3 是 run/neoforge/brush-mods。
  • "改了代码没变化"：三个 run* 都会先清空对应实例的 brush-mods/ 再摆当前产物，正常不会残留旧 jar。若你手工往那些目录放过别的 jar，会被清掉 —— 要保留多个 jar，就改 build.gradle 里对应的那几行。
  • IDEA 里 mixin 的 method = "run()V" 报红可忽略：这是 Minecraft Development 插件在无映射配置的手写构建下无法解析 mixin 目标所致，运行时不受影响。
  • 缺件不要手工拼错误信息：verifyInputs 已经把"缺什么、怎么补"写在异常里。
  • 磁盘与离线复用：MC 侧文件都在用户级 Gradle 缓存里 —— 客户端 jar 约 38 MB（<gradle 用户目录>/caches/brush/26.1.2/），库 / natives / 资产约 600 MB；本机把 GRADLE_USER_HOME 设在非默认位置，默认机器上就是 ~/.gradle。加载器 / 能力库 / 本示例项目默认共享这一份，所以已经下过就零下载命中。要复用别处的下载或换落点，用 -Pbrush.cache= / -Pbrush.vanillaJar= 指过去。
  • 用到网络 / 创造栏 / HUD 与输入时：这些能力住在能力库 brush-api 里。三个 run* 与 stage 都会把它一起摆进对应实例的 brush-mods/，正常不需要你手工处理；只有当你自己手工搭运行目录而漏了它时，BrushNetwork 才会给出"库模组未安装"的可读异常。
