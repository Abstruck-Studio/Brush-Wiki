界面与输入

本页覆盖 Brush API 的界面与输入面：屏幕事件（SCREEN_INIT / SCREEN_RESIZE）、 HUD 抽取事件（HUD_EXTRACT）、键位注册（BrushKeybinds）与三个原始输入事件 （INPUT_KEY_PRESS / INPUT_MOUSE_BUTTON / INPUT_MOUSE_SCROLL）， 以及创造栏相关的两个面。 每个事件都标出触发时机、所在线程、可取消性与三运行时一致性。

0. 先说结论：这一层的四件事

面入口你拿到的载荷典型用途
屏幕BrushEvents.SCREEN_INIT / SCREEN_RESIZEvanilla Screen 实例本身往标题界面加自己的按钮、随缩放重排布局
HUDBrushEvents.HUD_EXTRACTGuiGraphicsExtractor + DeltaTracker在 vanilla HUD 之后追加绘制
键位BrushKeybinds.register / registerCategory—注册一个出现在原版「控制」界面、可改键、写 options.txt 的按键
输入BrushEvents.INPUT_KEY_PRESS 等三个GLFW 原始值原始按键回调、滚轮、鼠标键
统一前提。 这些监听器都通过 Event#register(listener) 注册，注册动作线程安全、 可在 mod 入口构造期完成，且不解析任何 MC 类型—— 与加载期无关的注册安全性见 事件总表「注册时机」节。

1. 屏幕事件：SCREEN_INIT 与 SCREEN_RESIZE

1.1 触发点

两个事件都锚在 vanilla Screen 的方法 TAIL，0 新增 footprint：

事件L1 注入点触发时机的精确含义线程可取消三运行时
SCREEN_INIT Screen#init(int,int) TAIL 该屏 widget 已就绪：首次显示 = 子类 init() 完成态；同一实例重复 init = 「先清后建」完成态。对所有屏幕派发 游戏主线程 否 一致
SCREEN_RESIZE Screen#resize(int,int) TAIL 窗口缩放完成，widget 已按新尺寸「先清后建」完毕 游戏主线程 否 一致

两条路径互不覆盖：缩放走 Minecraft.resizeGui() → Window.setGuiScale → Screen#resize，不经过 init(II)。所以只订阅 SCREEN_INIT 会在窗口缩放后丢失布局。

1.2 用法：往标题界面加自己的按钮

事件对所有屏幕派发，类型过滤是监听器的职责。下面的模式是幂等的， 能同时承受重复 init 与缩放：

import net.minecraft.client.gui.components.Button;
import net.minecraft.client.gui.screens.Screen;
import net.minecraft.client.gui.screens.TitleScreen;
import net.minecraft.network.chat.Component;

import org.abstruck.brush.api.BrushEvents;

private static Button myButton;

// 注册期 = mod 入口（onInitialize / onInitializeClient），游戏尚未就绪
BrushEvents.SCREEN_INIT.register(screen -> {
    if (!(screen instanceof TitleScreen)) {
        return;                       // 类型过滤：只处理标题界面
    }
    if (myButton != null) {
        screen.removeWidget(myButton); // 先移除：重复 init 不会留下第二个按钮
    }
    myButton = Button.builder(Component.literal("My Button"), b -> {
        // 点下去做什么
    }).bounds(4, 4, 100, 20).build();
    screen.addRenderableWidget(myButton);
});
两个坑。
  • 初始化期不要碰 MC 类。 屏幕事件是「注入点的 TAIL」，TAIL 时刻 widget 已就绪 —— 但 Brush 事件注册路径本身不解析 MC 类型，所以入口构造期注册监听器是安全的； 真正不安全的是在入口构造期就直接引用注册表 / 客户端单体。MC 类型只能出现在监听器 lambda 体内。
  • 窗口缩放会重建控件。 vanilla 的 rebuildWidgets() = clearWidgets() + clearFocus() + init() + setInitialFocus() —— 你上一次添加的 widget 会被清掉。所以「只在 SCREEN_INIT 里加一次、之后不管」的写法在缩放后会失效。 订阅 SCREEN_RESIZE 或采用上面的幂等挂载模式。

出处：BrushEvents javadoc、ScreenInitEvent / ScreenResizeEvent javadoc、 HookEvents#SCREEN_INIT / #SCREEN_RESIZE javadoc、 以及界面层设计记载与实测日志。

2. HUD：HUD_EXTRACT

2.1 语义

触发时机
每个渲染帧的 vanilla HUD 提取完成之后—— 此刻准星 / 快捷栏 / 聊天等原版元素已全部写入 extractor，你可以继续追加绘制。
线程
渲染线程。
载荷
GuiGraphicsExtractor extractor 与 DeltaTracker deltaTracker —— 就是目标方法的两个原始参数，对象同一性、每次触发零分配。
频率
热路径：每渲染帧 1 次（约 60–260 次/秒）。无监听器时加载侧零开销； 有监听器时也零分配。监听器内部应保持廉价。
可取消
否。这是「追加绘制」语义，不是「拦截 / 改写」语义。
三运行时
一致。

2.2 坐标系

用 extractor 自己的 guiWidth() / guiHeight() 定位，不要用物理窗口像素 —— 那是未缩放尺寸，与绘制坐标系不是一套。 左上角为原点、y 向下增长。

2.3 画文字的示例

import net.minecraft.client.DeltaTracker;
import net.minecraft.client.Minecraft;
import net.minecraft.client.gui.GuiGraphicsExtractor;
import net.minecraft.network.chat.Component;

import org.abstruck.brush.api.BrushEvents;

private static final int COLOR_WHITE = 0xFFFFFFFF;

BrushEvents.HUD_EXTRACT.register((extractor, deltaTracker) -> {
    Minecraft minecraft = Minecraft.getInstance();
    if (minecraft.player == null) {
        return;                                  // 不在世界里：不画（廉价早退是热路径纪律）
    }
    int x = 6;
    int y = 6;
    extractor.text(minecraft.font, Component.literal("Hello HUD"), x, y, COLOR_WHITE);
});

签名依据： GuiGraphicsExtractor.text(Font, Component, int x, int y, int color)、 fill(RenderPipeline, int, int, int, int, int)、guiWidth() / guiHeight()。 可参考的真实用例：耐久 HUD mod 的 onHudExtract 与 Brush 自检探针的 drawMarker。

自检口径。 自检退出点位于首帧渲染之前， 因此本事件在自检报告里必然 0 次 —— 加载器只对目标类做强制加载 + 方法存在断言， 实际绘制效果由实机探针覆盖，「好不好看」仍是人工项。 出处：HudExtractEvent javadoc 与实测日志。

3. 键位：BrushKeybinds

3.1 注册 API（签名以源码为准）

方法签名说明
登记键位public static KeyMapping register(KeyMapping mapping) 返回同一个实例。抛 NullPointerException（null）/ IllegalArgumentException/ IllegalStateException。
登记分类public static KeyMapping.Category registerCategory(Identifier categoryId) 26.1.2 起按键分类是注册式 record；不注册则「控制」界面里无处安放。返回值交给 KeyMapping 构造器。
诊断public static int registeredCount()已登记的键位数量。
import com.mojang.blaze3d.platform.InputConstants;

import net.minecraft.client.KeyMapping;
import net.minecraft.resources.Identifier;

import org.abstruck.brush.api.BrushEvents;
import org.abstruck.brush.api.BrushKeybinds;

// 推荐在 mod 主入口（onInitialize）执行一次 —— 必须早于 Options 构造
KeyMapping.Category category = BrushKeybinds.registerCategory(
        Identifier.fromNamespaceAndPath("mymod", "keys"));
KeyMapping toggle = BrushKeybinds.register(new KeyMapping(
        "key.mymod.toggle", InputConstants.Type.KEYSYM, 75 /* GLFW_KEY_K */, category));

// 之后在每帧 tick 消费点击（vanilla KeyMapping 的标准用法）
BrushEvents.CLIENT_TICK.register(event -> {
    while (toggle.consumeClick()) {
        // 切换你的开关
    }
});
为什么键码写 75 而不写 GLFW.GLFW_KEY_K。 LWJGL 不在 mod 的编译类路径上，实测编译报 程序包 org.lwjgl.glfw 不存在。GLFW 文档规定「可打印键的键码 = 该键在 US 布局下的 ASCII 值」， 故 K = 75；本项目日志也实证过这条规则（注入 B 时输出 key=B(66)）。 com.mojang.blaze3d.platform.InputConstants 属于官方名类空间，可以正常 import。 出处：BrushKeybinds javadoc、设计文档记载与实测日志。

3.2 持久化与「控制」界面

注册之后一切交给 vanilla：键位进入 Options.keyMappings，于是 （a）出现在原版「控制」界面；（b）玩家可改键；（c）经 KeyMapping#saveString() 写进 options.txt 并在下次启动载入； （d）可用 KeyMapping#isDown() / consumeClick() 查询。 这与 Fabric（KeyMappingHelper.registerKeyMapping）和 NeoForge（RegisterKeyMappingsEvent#register） 的口径相同：mod 交一个 vanilla KeyMapping，加载器负责拼进原版数组。

必须在初始化期登记，否则响亮失败。 Options.keyMappings 是 public final KeyMapping[]，只在 Options#<init> 里赋值一次，而同一构造器随后还会读它。 所以构造结束后补写既不可能生效、也会错过那次读。Brush 的选择是： 这种情况下 register 抛 IllegalStateException。 三运行时一致：S1 由核心注入点拼接，S2/S3 下我们的注入点与宿主 同时拼接 —— 都是「把数组接长」，互不抹除。 出处：BrushKeybinds javadoc、keybind/KeybindRegistry javadoc、设计文档记载。

4. 输入事件：三个 GLFW 原始回调

先看枚举：InputAction 是 GLFW 动作值的语义化，RELEASE(0) / PRESS(1) / REPEAT(2) / UNKNOWN(-1)。 另有 int id() 取原始值、static InputAction of(int id) 做转换。 键盘事件可取 RELEASE / PRESS / REPEAT；鼠标按键只有 RELEASE / PRESS。

事件常量监听器方法L1 注入点触发时机线程可取消三运行时
INPUT_KEY_PRESS onKeyPress(InputAction, int key, int scancode, int modifiers) KeyboardHandler#keyPress HEAD 每次按键回调 游戏主线程否一致
INPUT_MOUSE_BUTTON onMouseButton(InputAction, int button, int modifiers) MouseHandler#onButton HEAD 每次鼠标按键回调 游戏主线程否一致
INPUT_MOUSE_SCROLL onMouseScroll(double xOffset, double yOffset) MouseHandler#onScroll HEAD 每次滚轮回调 游戏主线程否一致

三条语义细节：

  • 载荷是 GLFW 原始值，与 vanilla 的 KeyEvent record（key / scancode / modifiers） 和 MouseButtonInfo record（button / modifiers）字段一一对应，原样透传。
  • 不携带窗口句柄。注入点在方法 HEAD， 先于 vanilla 方法头部的窗口句柄守卫执行 —— 所以即使是其它窗口发来的回调，你也能看到事件。
  • 滚轮给的是「选项处理之前」的原始增量：vanilla 会在此基础上应用 discreteMouseScroll 等选项， 你拿到的是 HEAD 处的原值。
什么时候用输入事件，什么时候用 BrushKeybinds。 想要「玩家可以在控制界面改键、绑定持久化、用 isDown() 查询」→ 用 BrushKeybinds； 想要「原始回调 / 不占用键位 / 感知修饰键与扫描码」→ 用 INPUT_* 事件。 两者可以同时用。

自检口径：自检运行无人输入，退出点前这三个事件计数为 0 是正常态；探针以伪窗口句柄 0L + 哨兵键码 live-fire 真实调用一次并断言计数增长。 出处：KeyPressEvent / MouseButtonEvent / MouseScrollEvent / InputAction javadoc、实测日志。

5. 创造栏相关：两个面别混

名字都带「注册」，但它们是两个不同层的东西：

CreativeTabOutputEventClientRegistrationEvent
它是什么一个监听器接口类型，不是 BrushEvents 上的顶层字段 BrushEvents.CLIENT_REGISTRATION 的事件对象
怎么订阅BrushCreativeTabs.entriesOf(tabKey | Identifier).register(listener) —— 按标签页键订阅 BrushEvents.CLIENT_REGISTRATION.register(listener) —— 全局一次
L1 来源CreativeModeTab#buildContents TAIL BuiltInRegistries#bootStrap() TAIL
触发时机每次该标签页构建时—— 可突发、非热路径 vanilla 内容注册完成之后、Minecraft 构造之前 —— 每进程恰一次
线程调用 buildContents 的线程 执行 bootstrap 的线程
可取消否否
三运行时一致 事件点一致；客户端注册的 flush 落地点在 S3 推迟到首个 PACKS_REGISTERED
典型用途把自己的物品塞进某个现有标签页 最后一批客户端注册
import net.minecraft.core.registries.BuiltInRegistries;
import net.minecraft.resources.Identifier;
import net.minecraft.world.item.ItemStack;

import org.abstruck.brush.api.BrushCreativeTabs;
import org.abstruck.brush.api.BrushEvents;

BrushCreativeTabs.entriesOf(Identifier.fromNamespaceAndPath("minecraft", "ingredients"))
        .register(entries -> {
            entries.add(new ItemStack(BuiltInRegistries.ITEM.getValue(
                    Identifier.fromNamespaceAndPath("mymod", "my_item"))));
        });

BrushEvents.CLIENT_REGISTRATION.register(event -> {
    // 此刻：经 BrushRegistry 客户端组提交的注册已被统一 flush 落地
    // 监听器内仍可做最后一批客户端注册（S1/S2 下 flush 后到场立即执行）
});
为什么创造栏只能「追加」。 vanilla 14 个标签页的 (row,column) 槽位已全部占满， 而 Bootstrap#bootStrap() 在注册窗口之后会无条件调用 CreativeModeTabs.validate()， 重复槽位直接中止启动。因此 BrushRegistry 对 CREATIVE_MODE_TAB 注册表直接拒收并给出指引 Brush 自有的标签页走另一条路： BrushCreativeTabs.register(BrushCreativeTab.builder(...).build()) 展示在创造栏左侧的 Brush 侧栏， 进不了任何注册表，也因此不会触发 CreativeTabOutputEvent。 出处：BrushCreativeTabs / BrushCreativeTab / CreativeTabEntries javadoc、设计文档记载。

5.1 顺带一提：PACKS_REGISTERED 与界面无关

它属于资源包仓库构建完成，与界面 / 输入无关，放在「数据与资源」页讲。 这里只提醒一句：它是 S3 下客户端注册 flush 的落地点，所以 S3 的 CLIENT_REGISTRATION 事件监听器触发时，「最后一批注册」可能仍在缓冲里。
